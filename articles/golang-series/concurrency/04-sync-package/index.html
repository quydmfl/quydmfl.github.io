Bài 03 dùng channel để multiplex và đồng bộ hoá. Nhưng không phải lúc nào channel cũng là công cụ tự nhiên nhất — nhiều bài toán chỉ cần “bảo vệ 1 biến dùng chung” hoặc “chờ N goroutine xong việc”, và sync package giải quyết gọn hơn hẳn.

Mutex — bảo vệ shared state đơn giản

counter++ trông như 1 thao tác, nhưng thực chất là 3 bước: đọc giá trị, cộng 1, ghi lại. 1000 goroutine cùng làm việc này trên cùng 1 biến, không có gì đồng bộ hoá:

counterUnsafe := 0
var wg sync.WaitGroup
for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        counterUnsafe++ // đọc-cộng-ghi, không nguyên tử
    }()
}
wg.Wait()
Không khoá, 1000 lần tăng, kết quả: 952 (thường < 1000)

952, không phải 1000 — nhiều goroutine đọc cùng giá trị cũ trước khi goroutine khác kịp ghi giá trị mới, một số lần tăng bị “mất”. Chạy lại nhiều lần cho số khác nhau mỗi lần (đã thử 3 lần liên tiếp: 952, 979, 950) — đặc trưng của race condition: sai, nhưng sai không theo cách đoán trước được.

Thêm sync.Mutex bảo vệ đúng đoạn code đọc-cộng-ghi:

counterSafe := 0
var mu sync.Mutex
var wg sync.WaitGroup
for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        mu.Lock()
        counterSafe++
        mu.Unlock()
    }()
}
wg.Wait()
Có Mutex, 1000 lần tăng, kết quả: 1000 (luôn đúng = 1000)

Luôn đúng 1000, mọi lần chạy. mu.Lock() đảm bảo tại 1 thời điểm chỉ đúng 1 goroutine được vào vùng code giữa Lock()/Unlock() — các goroutine khác gọi Lock() cùng lúc sẽ tự động block chờ tới khi goroutine đang giữ lock gọi Unlock(). Không có phép màu nào khác: Mutex chỉ đơn giản là hàng đợi tuần tự hoá quyền truy cập.

WaitGroup — chờ nhiều goroutine hoàn tất

WaitGroup đã xuất hiện âm thầm trong mọi demo ở trên. Cơ chế: Add(n) cộng thêm n vào bộ đếm nội bộ, Done() trừ đi 1 (tương đương Add(-1)), Wait() block cho tới khi bộ đếm về 0.

var wg sync.WaitGroup
var mu sync.Mutex
completed := 0

for i := 0; i < 5; i++ {
    wg.Add(1) // ĐÚNG: Add gọi TRƯỚC go func(), trong main goroutine
    go func(n int) {
        defer wg.Done()
        mu.Lock()
        completed++
        mu.Unlock()
    }(i)
}
wg.Wait()
completed = 5 (luôn đúng = 5)

Chú ý thứ tự: wg.Add(1) nằm trước go func(), chạy trên chính main goroutine — mỗi vòng lặp cộng bộ đếm lên trước khi goroutine mới được tạo ra. Thứ tự này quan trọng hơn nhìn tưởng, xem phần bẫy bên dưới.

Once — đảm bảo 1 đoạn code chỉ chạy đúng 1 lần

var once sync.Once
var wg sync.WaitGroup
var mu sync.Mutex
initCount := 0

for i := 0; i < 10; i++ {
    wg.Add(1)
    go func(n int) {
        defer wg.Done()
        once.Do(func() {
            mu.Lock()
            initCount++
            mu.Unlock()
            fmt.Println("init chạy, gọi bởi goroutine", n)
        })
    }(i)
}
wg.Wait()
init chạy, gọi bởi goroutine 9
Số lần init thực sự chạy: 1 (dù 10 goroutine cùng gọi once.Do)

10 goroutine cùng gọi once.Do(), nhưng closure bên trong chỉ chạy đúng 1 lần — lần này goroutine số 9 “thắng” (chạy lại nhiều lần sẽ ra goroutine khác nhau tuỳ ai tới Do() trước, nhưng luôn đúng 1 goroutine). 9 goroutine còn lại gọi once.Do() cùng closure đó nhưng Do() trả về ngay lập tức, không chạy lại — không cần if !initialized { ... } thủ công dễ tự viết sai (chính bản thân check thủ công đó cũng cần khoá để tránh race). Đây là pattern chuẩn cho khởi tạo lazy singleton, load config 1 lần, hoặc mở connection pool dùng chung.

Bẫy kinh điển: gọi wg.Add() bên trong goroutine

wg.Add(1) ở demo trên nằm trước go func() một cách cố ý. Đổi vị trí — gọi Add(1) bên trong chính goroutine vừa tạo:

var wg sync.WaitGroup
completed := 0

for i := 0; i < 5; i++ {
    go func(n int) {
        wg.Add(1) // SAI: Add gọi BÊN TRONG goroutine, race với Wait() ở main
        completed++
        wg.Done()
    }(i)
}

wg.Wait()
fmt.Println("completed =", completed, "(có thể < 5 nếu Wait() trả về quá sớm)")

Chạy 5 lần liên tiếp, không sửa gì:

completed = 0 (có thể < 5 nếu Wait() trả về quá sớm)
completed = 0 (có thể < 5 nếu Wait() trả về quá sớm)
completed = 0 (có thể < 5 nếu Wait() trả về quá sớm)
completed = 2 (có thể < 5 nếu Wait() trả về quá sớm)
completed = 1 (có thể < 5 nếu Wait() trả về quá sớm)

5 lần chạy, 5 kết quả khác nhau: 0, 0, 0, 2, 1. Chuyện gì xảy ra: wg.Wait() ở main goroutine chạy ngay sau vòng lặp for — tại thời điểm đó, bộ đếm nội bộ của wg vẫn đang là 0 (chưa goroutine nào kịp gọi Add(1)). Wait() thấy bộ đếm 0, coi như “không có gì để chờ”, trả về ngay lập tức — trước khi bất kỳ goroutine nào kịp chạy. Chương trình in ra completed và kết thúc, trong khi 5 goroutine kia có thể vẫn đang lơ lửng chạy dở (hoặc chưa kịp chạy) ở background.

Chạy với -race phơi bày rõ vấn đề thật sự là gì — không chỉ là “timing xui”, mà là data race trên chính biến completed:

Detector báo 3 data race riêng biệt trong 1 lần chạy — main goroutine đọc/ghi completed khi in kết quả, đúng lúc 1 hoặc nhiều goroutine con vẫn đang ghi vào biến đó, không hề có Mutex hay quan hệ happens-before nào ràng buộc thứ tự giữa chúng. wg.Wait() không tạo ra happens-before ở đây, vì bộ đếm đã về 0 (mặc định) từ trước khi có Add nào chạy — Wait() không hề chờ những Add() “tới muộn”.

Sửa đúng: Add(1) phải chạy trên goroutine gọi Wait() (thường là goroutine cha), và phải chạy trước khi go func() được gọi — như demo “WaitGroup — chờ nhiều goroutine hoàn tất” ở trên. Không có cách nào “gọi Add muộn hơn nhưng vẫn đúng” — thứ tự Add-trước-go là bắt buộc, không phải tối ưu.

Channel vs sync: khi nào chọn cái nào

Cả hai đều giải quyết được bài toán đồng bộ hoá, nhưng phù hợp với hình dạng bài toán khác nhau:

  • Dùng sync.Mutex/RWMutex khi có 1 vùng dữ liệu dùng chung (map, struct, counter) mà nhiều goroutine cần đọc/ghi — bảo vệ trạng thái, không có khái niệm “gửi dữ liệu đi đâu”.
  • Dùng sync.WaitGroup khi cần chờ N goroutine độc lập hoàn tất, không cần lấy giá trị trả về qua nó (giá trị trả về thì gom qua channel hoặc biến dùng chung có khoá).
  • Dùng sync.Once cho khởi tạo lazy đúng 1 lần — singleton, load config, mở resource dùng chung.
  • Dùng channel khi bài toán có hình dạng “luồng dữ liệu” — 1 goroutine tạo ra giá trị, goroutine khác tiêu thụ (pipeline ở bài 02), hoặc cần chọn 1 trong nhiều nguồn sự kiện (bài 03).

Quy tắc kinh nghiệm hay được trích dẫn: “share memory by communicating” (channel) cho luồng dữ liệu và quyền sở hữu, sync cho bảo vệ trạng thái tại chỗ. Cả hai xuất hiện chung trong cùng 1 chương trình thực tế là chuyện bình thường — không có bên nào “thắng tuyệt đối”.

Tự chạy lại demo

cd 04-sync-package
go run .
go vet ./...

main.go gộp 3 demo chạy an toàn (Mutex vs unsafe counter, WaitGroup đúng cách, Once). Demo bẫy wg.Add() trong goroutine không nằm trong main.go — đây là data race thật, go vet/go build -race sẽ (đúng như thiết kế) phát hiện và báo lỗi nếu để trong module chính; tách riêng thành file độc lập để tự tái hiện:

go run waitgroupbug.go        # chạy vài lần, xem completed đổi giá trị mỗi lần
go run -race waitgroupbug.go  # xem DATA RACE thật

Tổng kết & bài tiếp theo

sync.Mutex tuần tự hoá truy cập vào trạng thái dùng chung; sync.WaitGroup chờ nhiều goroutine hoàn tất — nhưng Add() bắt buộc phải chạy trước go func() trên goroutine gọi Wait(), gọi Add() bên trong goroutine con là race condition thật, không phải lỗi lý thuyết; sync.Once giải quyết khởi tạo lazy an toàn mà không cần tự viết cờ kiểm tra thủ công.
