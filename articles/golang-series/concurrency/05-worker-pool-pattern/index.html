05. Worker Pool pattern

Bài 04 dùng Mutex/WaitGroup/Once để bảo vệ và đồng bộ hoá trạng thái. Bài này ghép channel + goroutine + sync lại thành 1 pattern thực chiến dùng nhiều nhất trong code Go production: worker pool — giới hạn số goroutine chạy đồng thời cho 1 khối lượng công việc lớn, thay vì tạo goroutine không giới hạn cho mỗi job.

Vì sao cần giới hạn concurrency

go func() rẻ để viết, nhưng không miễn phí để chạy — bài 01 đã đo goroutine tốn thật ~606 byte mỗi cái. Tệ hơn cả bộ nhớ: nếu mỗi job còn gọi ra 1 service khác (database, API bên thứ 3), tạo 1 goroutine cho mỗi job trong 1 danh sách hàng nghìn phần tử nghĩa là bắn hàng nghìn kết nối đồng thời vào service đó — thứ dễ sập hơn nhiều so với chương trình Go của bạn.

Worker pool cố định số lượng “người làm việc”: N worker goroutine cùng lấy job từ 1 channel chung, worker nào rảnh thì lấy job tiếp theo, không phụ thuộc số lượng job đầu vào lớn tới đâu.

Fan-out: nhiều worker cùng đọc từ 1 channel job

for w := 0; w < numWorkers; w++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for j := range jobCh { // fan-out: nhiều worker cùng đọc 1 channel job
            resultCh <- work(j)
        }
    }()
}

numWorkers goroutine cùng chạy for j := range jobCh trên cùng 1 channel. Go runtime tự chia job cho worker đang rảnh — mỗi giá trị gửi vào jobCh chỉ được đúng 1 worker nhận (channel không broadcast), không cần logic load-balancing thủ công nào.

Fan-in: gộp kết quả từ nhiều worker về 1 nơi

go func() {
    wg.Wait()       // chờ toàn bộ worker xong
    close(resultCh) // an toàn để đóng vì chắc chắn không ai còn gửi vào resultCh
}()

var results []int
for r := range resultCh { // fan-in: gom kết quả từ mọi worker về 1 nơi
    results = append(results, r)
}

Đây là chỗ dễ viết sai nhất: ai được phép đóng resultCh? Không phải worker nào đóng cũng được — worker khác có thể vẫn đang gửi, gây panic: send on closed channel (bài 02). Giải pháp: 1 goroutine riêng chờ wg.Wait() (nghĩa là toàn bộ worker đã Done()) rồi mới close(resultCh) — đúng lúc, đúng 1 lần, không ai còn gửi dở dang.

Worker pool hoàn chỉnh

func WorkerPool(jobs []int, numWorkers int) []int {
    jobCh := make(chan int, len(jobs))
    resultCh := make(chan int, len(jobs))
    var wg sync.WaitGroup

    for w := 0; w < numWorkers; w++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := range jobCh {
                resultCh <- work(j)
            }
        }()
    }

    for _, j := range jobs {
        jobCh <- j
    }
    close(jobCh) // báo hết job, worker sẽ thoát vòng for-range khi rút cạn jobCh

    go func() {
        wg.Wait()
        close(resultCh)
    }()

    var results []int
    for r := range resultCh {
        results = append(results, r)
    }
    return results
}

3 channel/đồng bộ hoá đóng đúng 3 vai trò khác nhau: jobCh đóng để báo “hết việc” cho worker; wg đếm để biết khi nào tất cả worker thật sự xong (không chỉ hết jobCh, mà đã xử lý xong job cuối); resultCh đóng dựa trên tín hiệu từ wg, không dựa trên jobCh — 2 việc “hết job đầu vào” và “xử lý xong toàn bộ” không xảy ra cùng lúc.

Demo: throughput và số goroutine đỉnh, có/không giới hạn worker

200 job, mỗi job mô phỏng việc chậm bằng time.Sleep(50ms) (gọi API, query DB…), đo bằng runtime.NumGoroutine() lấy mẫu liên tục để bắt đúng đỉnh:

func work(n int) int {
    time.Sleep(50 * time.Millisecond)
    return n * n
}

Không giới hạn — 1 goroutine cho mỗi job:

200 job, mỗi job 50ms, không giới hạn goroutine
Thời gian: 50ms
Peak NumGoroutine: 202
Số kết quả: 200

Worker pool, 10 worker cố định:

200 job, mỗi job 50ms, worker pool 10 worker
Thời gian: 1.001s
Peak NumGoroutine: 13
Số kết quả: 200

Worker pool, 50 worker:

200 job, mỗi job 50ms, worker pool 50 worker
Thời gian: 201ms
Peak NumGoroutine: 53
Số kết quả: 200

Số liệu khớp chính xác lý thuyết: không giới hạn chạy xong trong ~50ms (tất cả 200 job chạy song song, time.Sleep chồng lên nhau) nhưng đỉnh 202 goroutine (200 job + main + goroutine đo). 10 worker mất ~1.001s — đúng bằng 200 job ÷ 10 worker × 50ms = 1000ms, vì mỗi worker phải xử lý tuần tự 20 job — nhưng đỉnh chỉ 13 goroutine (10 worker + main + goroutine đo + goroutine chờ đóng resultCh). 50 worker cân bằng giữa 2 thái cực: ~201ms (200 ÷ 50 × 50ms = 200ms), đỉnh 53 goroutine.

Đây chính là đánh đổi cốt lõi của worker pool: numWorkers càng lớn, càng gần hiệu năng “không giới hạn”, nhưng càng tốn tài nguyên đỉnh. Không có con số “đúng” duy nhất — numWorkers nên khớp với giới hạn thật của tài nguyên downstream (ví dụ: connection pool DB cho phép tối đa bao nhiêu kết nối đồng thời), không phải chọn tuỳ ý.

Tự chạy lại demo

cd 05-worker-pool-pattern
go run .
go vet ./...
go run -race . # race-free, kể cả khi chạy với detector

main.go chạy lần lượt cả 3 kịch bản (không giới hạn, 10 worker, 50 worker) trên cùng 200 job, in đúng thời gian và đỉnh goroutine như các đoạn ở trên. Tổng thời gian chạy khoảng 1.3 giây (chủ yếu do kịch bản 10 worker mất ~1 giây).

Tổng kết & bài tiếp theo

Worker pool = fan-out (N worker đọc chung 1 channel job) + fan-in (gom kết quả qua 1 channel, đóng đúng lúc nhờ WaitGroup). Đánh đổi trung tâm là numWorkers: thấp thì an toàn cho tài nguyên downstream nhưng chậm, cao thì nhanh nhưng tốn tài nguyên đỉnh gần bằng “không giới hạn” — chọn dựa trên giới hạn thật của hệ thống đang gọi tới, không phải con số tuỳ ý.
