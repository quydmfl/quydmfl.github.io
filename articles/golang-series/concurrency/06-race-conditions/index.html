06. Race conditions

Bài cuối mini-series Concurrency: tổng hợp lại các pattern gây race condition phổ biến nhất đã chạm qua rải rác từ bài 01 tới bài 05, lần này tập trung riêng vào công cụ phát hiện và cách sửa. Điểm chung của mọi pattern dưới đây: code trông có vẻ đúng khi đọc, chỉ lộ ra khi chạy với -race hoặc gặp đúng thời điểm hiếm trên production.

Race detector: -race phát hiện được gì

go run -race .
go test -race ./...
go build -race -o app .

-race chèn thêm code kiểm tra mọi truy cập bộ nhớ đồng thời (dùng thuật toán vector clock), chạy chậm hơn đáng kể — Go team ước tính thường chậm hơn 2-10 lần và tốn thêm bộ nhớ — nhưng phát hiện được chính xác race đã thực sự xảy ra trong lần chạy đó, kể cả khi output cuối cùng “trông vẫn đúng”.

Điều quan trọng cần nhớ: không phát hiện được race ≠ không có race. Detector chỉ báo race nó thấy được trong đúng lần chạy đó — 1 nhánh code hiếm khi được lịch chạy đúng lúc đụng độ có thể không lộ diện dù chạy -race hàng chục lần. Ngược lại, hễ nó đã báo, chắc chắn có race thật — không có false positive.

Pattern 1: shared counter không khoá

counter := 0
var wg sync.WaitGroup
for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        counter++ // race thật: đọc-cộng-ghi, không nguyên tử
    }()
}
wg.Wait()
fmt.Println(counter)

Chạy 3 lần liên tiếp, không sửa gì:

Không khoá: 929 (thường < 1000)
Không khoá: 955 (thường < 1000)
Không khoá: 894 (thường < 1000)

3 con số khác nhau — dấu hiệu đặc trưng nhất của race condition. Chạy -race:

==================
WARNING: DATA RACE
Read at 0x00c00000e168 by goroutine 15:
  main.main.func1()
      counter.go:16 +0x74

Previous write at 0x00c00000e168 by goroutine 10:
  main.main.func1()
      counter.go:16 +0x84

Goroutine 15 (running) created at:
  main.main()
      counter.go:14 +0x70

Goroutine 10 (finished) created at:
  main.main()
      counter.go:14 +0x70
==================
Found 2 data race(s)

Sửa bằng sync/atomic (hoặc sync.Mutex, xem bài 04):

var counter int64
atomic.AddInt64(&counter, 1)
Dùng atomic: 1000 (luôn đúng = 1000)

atomic.AddInt64 thực hiện đọc-cộng-ghi trong 1 lệnh CPU nguyên tử duy nhất (compare-and-swap ở tầng phần cứng) — không có khoảng hở giữa “đọc” và “ghi” để goroutine khác chen vào.

Pattern 2: closure capture biến loop (bẫy kinh điển — đã được vá)

Trước Go 1.22, đây là bẫy phổ biến bậc nhất: for i := 0; i < n; i++ { go func() { use(i) }() } — biến i là 1 ô nhớ duy nhất được share giữa mọi vòng lặp, không phải bản copy riêng mỗi lần. Từ Go 1.22, ngữ nghĩa vòng lặp đổi: mỗi lần lặp có bản i riêng. Kiểm chứng thật trên Go bản đang dùng cho series này:

var results []int
var mu sync.Mutex
var wg sync.WaitGroup
for i := 0; i < 5; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        mu.Lock()
        results = append(results, i) // Go 1.22+: mỗi vòng lặp có bản i riêng
        mu.Unlock()
    }()
}
wg.Wait()
sort.Ints(results)
fmt.Println(results)
go version: go1.24.1
for i := 0; i < 5 (Go 1.22+, an toàn mặc định): [0 1 2 3 4]

Chạy lại nhiều lần luôn ra đúng [0 1 2 3 4] — không lặp số, không thiếu số. Nếu series này chạy trên Go < 1.22, đoạn code y hệt có thể in ra [5 5 5 5 5] hoặc hỗn hợp tuỳ thời điểm goroutine được lịch chạy. Vẫn nên biết pattern này vì code cũ và tài liệu cũ (kể cả nhiều câu trả lời trên StackOverflow) vẫn khuyên i := i — không sai, chỉ là không còn cần thiết trên Go hiện đại.

Pattern 3: biến NGOÀI vòng lặp bị chia sẻ — Go 1.22 không cứu được kiểu này

Bẫy dễ nhầm với Pattern 2 nhưng bản chất khác hẳn: Go 1.22 chỉ sửa biến của vòng lặp for (biến khai báo trong mệnh đề for). Một biến khai báo trước vòng lặp rồi bị đọc/ghi từ cả goroutine lẫn main thì vẫn race y nguyên, bất kể phiên bản Go:

i := 0 // biến NGOÀI vòng lặp, không phải biến vòng lặp -- Go 1.22 không cứu được kiểu này
for i < 5 {
    go func() {
        fmt.Println("goroutine thấy i =", i) // đọc biến dùng chung, race với i++ ở dưới
    }()
    i++
}
time.Sleep(50 * time.Millisecond)

Chạy 2 lần liên tiếp, không sửa gì:

goroutine thấy i = 5
goroutine thấy i = 5
goroutine thấy i = 5
goroutine thấy i = 5
goroutine thấy i = 5

Cả 5 dòng đều in 5 — reproducible cả 2 lần chạy, vì goroutine bị lịch chạy trễ hơn cả vòng lặp i++ chạy xong (i đã đạt giá trị cuối 5 trước khi bất kỳ goroutine nào kịp đọc). -race xác nhận đây là race thật, không phải trùng hợp:

==================
WARNING: DATA RACE
Read at 0x00c000090038 by goroutine 7:
  main.main.func1()
      sharedvar.go:12 +0x54

Previous write at 0x00c000090038 by main goroutine:
  main.main()
      sharedvar.go:14 +0x5c

Goroutine 7 (running) created at:
  main.main()
      sharedvar.go:11 +0x44
==================
Found 1 data race(s)

Sửa bằng cách truyền i qua tham số — cách làm áp dụng được ở mọi phiên bản Go, kể cả trước 1.22:

i := 0
for i < 5 {
    wg.Add(1)
    go func(n int) { // truyền qua tham số -- mỗi goroutine có bản copy riêng
        defer wg.Done()
        mu.Lock()
        results = append(results, n)
        mu.Unlock()
    }(i)
    i++
}
Truyền qua tham số (an toàn mọi phiên bản Go): [0 1 2 3 4]

Bài học chung của Pattern 2 và 3: Go 1.22 chỉ thu hẹp phạm vi bẫy “capture biến dùng chung”, không loại bỏ hoàn toàn lớp lỗi này — bất kỳ biến nào (không riêng biến loop) bị nhiều goroutine đọc/ghi mà không đồng bộ hoá đều là race tiềm năng.

Pattern 4: concurrent map write — crash thật, không phải warning

Map trong Go không an toàn để nhiều goroutine ghi đồng thời, và runtime chủ động phát hiện việc này ở tầng thấp (không cần -race):

m := make(map[int]int)
var wg sync.WaitGroup
for r := 0; r < 20; r++ {
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func(n int) {
            defer wg.Done()
            m[n%50] = n * n // nhiều goroutine cùng ghi đè vài key -- tăng khả năng đụng độ
        }(i)
    }
}
wg.Wait()
fatal error: concurrent map writes

goroutine 26 [running]:
internal/runtime/maps.fatal({0x10496e67d?, 0x0?})
	/opt/homebrew/Cellar/go/1.24.1/libexec/src/runtime/panic.go:1058 +0x20
main.main.func1(0x9)
	mapwrite.go:13 +0x80
created by main.main in goroutine 1
	mapwrite.go:11 +0x70
...
exit status 2

Crash cả 3/3 lần chạy thử — không cần -race, không cần may rủi timing tinh vi như race đọc/ghi thông thường. Đây là fatal error, không phải panic (giống deadlock ở bài 02) — Go runtime tự vệ chủ động ngay khi phát hiện 2 goroutine cùng ghi vào map cùng lúc, dừng chương trình ngay lập tức thay vì để dữ liệu nội bộ của map bị hỏng âm thầm (map dùng cấu trúc bucket phức tạp bên trong — ghi đồng thời không khoá có thể làm hỏng con trỏ nội bộ, dẫn tới crash khó đoán hơn nhiều nếu runtime không chặn trước).

Sửa bằng sync.Mutex:

m := make(map[int]int)
var mu sync.Mutex
// ...
go func(n int) {
    defer wg.Done()
    mu.Lock()
    m[n%50] = n * n
    mu.Unlock()
}(i)
Hoàn tất, không crash. len(m) = 50

Chạy 3 lần đều ra len(m) = 50 ổn định — đúng bằng số key phân biệt (n % 50).

Pattern 5: concurrent slice write — sai âm thầm, không crash

Khác hẳn map, ghi đồng thời vào slice dùng chung không crash — chỉ âm thầm cho kết quả sai:

var s []int
var wg sync.WaitGroup
for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func(n int) {
        defer wg.Done()
        s = append(s, n) // append không khoá, nhiều goroutine cùng đọc/ghi header slice
    }(i)
}
wg.Wait()
fmt.Println("len(s) thực tế:", len(s))

Chạy 3 lần liên tiếp:

Đã append 1000 lần, len(s) thực tế: 900 (mong đợi 1000)
Đã append 1000 lần, len(s) thực tế: 914 (mong đợi 1000)
Đã append 1000 lần, len(s) thực tế: 920 (mong đợi 1000)

Mất từ 80 đến 100 phần tử mỗi lần chạy, không có lỗi, không có cảnh báo — nguy hiểm hơn hẳn map, vì bug này lặng lẽ trôi qua nếu không có test kiểm tra chặt kết quả. Nguyên nhân: append đọc len/cap/con trỏ dữ liệu hiện tại của slice (gọi là “slice header”), rồi ghi lại header mới — 2 goroutine cùng đọc header cũ, cùng ghi phần tử vào đúng cùng 1 vị trí, ghi đè lẫn nhau. -race xác nhận:

==================
WARNING: DATA RACE
Write at 0x00c0001be000 by goroutine 15:
  main.main.func1()
      slicewrite.go:15 +0xec

Previous read at 0x00c0001be000 by goroutine 10:
  main.main.func1()
      slicewrite.go:15 +0x7c
==================

Sửa bằng sync.Mutex bảo vệ toàn bộ thao tác đọc-header + append + ghi-header:

var mu sync.Mutex
go func(n int) {
    defer wg.Done()
    mu.Lock()
    s = append(s, n)
    mu.Unlock()
}(i)
Có Mutex, len(s): 1000 (luôn đúng = 1000)

Chạy 3 lần đều đúng 1000. Bài học: map crash để bảo vệ bạn, slice thì không — race trên slice/struct thường bug âm thầm hơn nhiều, càng cần -race chạy định kỳ trong CI thay vì chỉ tin vào “chạy thử không thấy lỗi gì”.

Tự chạy lại demo

cd 06-race-conditions
go run .
go vet ./...
go run -race . # sạch, không có race nào trong main.go

main.go chỉ gộp các phiên bản đã sửa (atomic counter, loop-var Go 1.22+, truyền tham số, Mutex cho map, Mutex cho slice) — chạy an toàn, xác định, pass -race. 4 kịch bản race/crash thật ở trên (counter.go không khoá, sharedvar.go, mapwrite.go, slicewrite.go) không nằm trong main.go vì cố ý gây race/crash — tách riêng thành file độc lập để tự tái hiện đúng như các đoạn output ở trên.
