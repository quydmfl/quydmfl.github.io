01. Interfaces & implicit satisfaction

Oct 17, 2026 · 6 min read

Mở đầu mini-series Fundamentals & Idioms: interface trong Go là điểm khác biệt lớn nhất so với các ngôn ngữ OOP truyền thống (Java, C#) — không có từ khoá implements, và chính sự “ngầm định” này là nguồn gốc của bug nổi tiếng nhất trong Go: nil interface trap.

Interface satisfaction ngầm định

Không cần khai báo implements — 1 type tự động thoả mãn interface nếu có đủ method đúng signature. Hệ quả trực tiếp: có thể định nghĩa interface ở phía consumer (nơi dùng), không cần biết trước ở phía implementer — khác hẳn Java/C#, nơi type phải khai báo tường minh nó implement interface nào.

type UpperWriter struct {
    Out *strings.Builder
}

func (w *UpperWriter) Write(p []byte) (int, error) {
    upper := strings.ToUpper(string(p))
    return w.Out.WriteString(upper)
}

var sb strings.Builder
uw := &UpperWriter{Out: &sb}
var _ io.Writer = uw // kiểm tra tường minh tại compile-time
fmt.Fprintf(uw, "hello from go\n")
Kết quả: HELLO FROM GO

UpperWriter chưa từng import io, chưa từng “biết” io.Writer tồn tại lúc được định nghĩa — chỉ cần có đúng method Write([]byte) (int, error) là tự động thoả mãn, dùng được với bất kỳ hàm nào nhận io.Writer (ở đây là fmt.Fprintf).

Nil interface trap — bug kinh điển nhất Go

Interface value trong Go gồm 2 phần: (type, value). Một interface chỉ == nil khi cả hai phần đều nil. Đây là nguồn gốc của bug hay gặp nhất khi mới học Go — kể cả lập trình viên có kinh nghiệm cũng dính:

type CustomError struct{ msg string }
func (e *CustomError) Error() string { return e.msg }

func mayFail(shouldFail bool) *CustomError {
    if shouldFail {
        return &CustomError{msg: "đã lỗi"}
    }
    return nil // pointer nil, kiểu *CustomError
}

// Phiên bản SAI
func doSomethingBuggy() error {
    var err *CustomError = mayFail(false)
    return err // ép kiểu ngầm định sang error
}

Chạy thật:

buggyErr := doSomethingBuggy()
fmt.Printf("err == nil? %v  (kiểu %T)\n", buggyErr == nil, buggyErr)
err == nil? false  (kiểu *main.CustomError)

false — dù mayFail(false) trả về đúng nil, và logic nghiệp vụ hoàn toàn không có lỗi gì! Chuyện gì xảy ra: err (kiểu *CustomError) mang giá trị nil, nhưng khi return err ép kiểu ngầm định sang error (interface), Go tạo ra 1 interface value với type = *CustomError (không nil, vì kiểu cụ thể vẫn tồn tại) và value = nil. Interface đó không bằng nil — dù in bằng %v sẽ hiện <nil> (dễ gây hiểu lầm thêm lần nữa, vì text hiển thị “nil” nhưng so sánh == lại false).

Đây chính xác là kịch bản thật gây bug production: hàm trả về error, người gọi if err != nil { ... } — code vào nhánh xử lý lỗi dù không hề có lỗi.

Sửa đúng: kiểm tra tường minh trước khi return

func doSomethingFixed() error {
    customErr := mayFail(false)
    if customErr != nil {
        return customErr
    }
    return nil // nil interface THẬT (type=nil, value=nil)
}
Phiên bản ĐÚNG: err == nil? true   (kiểu <nil>)

true, và kiểu hiển thị đúng là <nil> (không phải *main.CustomError) — vì lần này Go trả về literal nil, tạo ra interface value với cả 2 phần đều nil. Quy tắc thực dụng rút ra: không bao giờ return trực tiếp 1 biến pointer đã gán kiểu cụ thể vào chỗ cần interface — luôn kiểm tra nil tường minh trước, hoặc đảm bảo hàm trả pointer luôn return nil bằng literal, không qua biến trung gian đã typed.

Interface composition

Go khuyến khích interface nhỏ, ghép lại thay vì 1 interface lớn nhiều method — triết lý “interface càng nhỏ càng mạnh”:

func useReadWriter(rw io.ReadWriter) string {
    rw.Write([]byte("ghi qua interface ghép"))
    buf := make([]byte, 64)
    n, _ := rw.Read(buf)
    return string(buf[:n])
}

var buf bytes.Buffer
result := useReadWriter(&buf)
Đọc lại: ghi qua interface ghép

io.ReadWriter chỉ là io.Reader ghép với io.Writer (type ReadWriter interface { Reader; Writer }). bytes.Buffer tự động thoả mãn cả hai, nên tự động thoả mãn io.ReadWriter — không cần khai báo gì thêm. So với cách tiếp cận interface lớn (1 interface gộp chục method) ở nhiều ngôn ngữ khác: interface nhỏ dễ implement hơn (type mới chỉ cần vài method là dùng được ở nhiều nơi), dễ test hơn (mock chỉ cần đúng phần cần dùng), và dễ compose linh hoạt theo đúng nhu cầu từng hàm.

Accept interfaces, return structs

type Logger struct {
    prefix string
    out    io.Writer
}

// Trả về concrete struct (*Logger), không phải interface
func NewLogger(prefix string, out io.Writer) *Logger {
    return &Logger{prefix: prefix, out: out}
}

func (l *Logger) Log(msg string) {
    fmt.Fprintf(l.out, "[%s] %s\n", l.prefix, msg)
}

// Chỉ cần khả năng "ghi" -- nhận io.Writer, không ép kiểu cụ thể
func writeReport(w io.Writer, content string) {
    fmt.Fprintln(w, "=== BÁO CÁO ===")
    fmt.Fprintln(w, content)
}
[APP] khởi động thành công
=== BÁO CÁO ===
mọi thứ ổn

Hai quyết định thiết kế bổ trợ nhau: writeReport nhận tham số kiểu interface (io.Writer) — linh hoạt, gọi được với os.Stdout, *bytes.Buffer khi test, hay bất kỳ thứ gì biết ghi. NewLogger trả về concrete struct (*Logger, không phải 1 interface LoggerInterface nào đó) — người gọi có đủ thông tin, dùng được toàn bộ API của Logger (kể cả field/method chưa có trong 1 interface tưởng tượng nào), và không bị giới hạn bởi 1 interface được thiết kế trước khi biết hết nhu cầu thực tế. Ngoại lệ hợp lý duy nhất để trả về interface: khi cố tình muốn che giấu implementation detail (ví dụ 1 package public chỉ muốn expose hành vi, không muốn caller phụ thuộc vào struct nội bộ có thể đổi sau này).

Tổng kết & bài tiếp theo

Interface trong Go mạnh vì đơn giản — không cần khai báo, ghép được tự do — nhưng chính sự đơn giản đó (interface chỉ là cặp (type, value)) là nguồn gốc trực tiếp của nil interface trap. Nhớ đúng 1 quy tắc: không return biến pointer đã typed vào chỗ cần interface mà chưa kiểm tra nil tường minh.
