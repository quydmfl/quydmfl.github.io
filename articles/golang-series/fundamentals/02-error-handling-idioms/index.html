02. Error handling idioms

Bài 01 kết thúc với error là 1 interface (type error interface { Error() string }). Bài này đi vào idiom xử lý lỗi của Go — cố tình không có exception, và vì sao đó là quyết định thiết kế có chủ đích, không phải thiếu sót.

Sentinel error — so sánh trực tiếp

var ErrNotFound = errors.New("not found")

func find(id int) error {
    if id != 1 {
        return ErrNotFound
    }
    return nil
}
err := find(42)
fmt.Println("So sánh trực tiếp ==:", err == ErrNotFound)
fmt.Println("errors.Is:", errors.Is(err, ErrNotFound))
So sánh trực tiếp ==: true
errors.Is: true

Sentinel error là 1 giá trị error cố định, so sánh được bằng == (hoặc errors.Is, làm việc tương tự với sentinel error đơn giản). Giới hạn: không mang được thông tin ngữ cảnh — biết “not found” nhưng không biết đang tìm ID nào, resource gì.

Typed error — mang theo ngữ cảnh, kết hợp error wrapping

type NotFoundError struct {
    Resource string
    ID       int
}

func (e *NotFoundError) Error() string {
    return fmt.Sprintf("%s #%d: %v", e.Resource, e.ID, ErrNotFound)
}

func (e *NotFoundError) Unwrap() error { return ErrNotFound } // nối vào chuỗi lỗi

func queryDB(id int) error {
    return &NotFoundError{Resource: "user", ID: id}
}

func getUser(id int) error {
    if err := queryDB(id); err != nil {
        return fmt.Errorf("getUser: %w", err) // %w giữ nguyên chuỗi Unwrap
    }
    return nil
}

func handleRequest(id int) error {
    if err := getUser(id); err != nil {
        return fmt.Errorf("handleRequest: %w", err)
    }
    return nil
}

Chạy qua đúng 3 lớp gọi hàm (handleRequest → getUser → queryDB):

err := handleRequest(42)
fmt.Println("Thông báo lỗi đầy đủ:", err)
fmt.Println("errors.Is(err, ErrNotFound):", errors.Is(err, ErrNotFound))

var nfErr *NotFoundError
ok := errors.As(err, &nfErr)
fmt.Println("errors.As lấy được NotFoundError:", ok, nfErr.Resource, nfErr.ID)
Thông báo lỗi đầy đủ: handleRequest: getUser: user #42: not found
errors.Is(err, ErrNotFound): true
errors.As lấy được NotFoundError: true
  Resource: user , ID: 42

errors.Is đi xuyên qua cả 2 lớp %w để so sánh đúng sentinel error gốc, và errors.As lấy được nguyên vẹn *NotFoundError (kèm cả field Resource/ID) dù nó đã bị wrap 2 lần qua fmt.Errorf. Đây là lý do error trong Go hiện đại (từ 1.13) mạnh hơn hẳn 1 chuỗi text đơn thuần: chuỗi lỗi (err chain, nối bằng Unwrap()) cho phép vừa hiển thị thông báo đầy đủ theo ngữ cảnh, vừa kiểm tra/truy xuất được đúng lỗi gốc ở tầng sâu nhất.

Bẫy dễ mắc nhất: dùng %v thay vì %w

Đổi đúng 1 ký tự trong fmt.Errorf:

func getUserNoWrap(id int) error {
    if err := queryDB(id); err != nil {
        return fmt.Errorf("getUser: %v", err) // %v thay vì %w
    }
    return nil
}
errNoWrap := getUserNoWrap(42)
fmt.Println("Thông báo lỗi (trông giống hệt):", errNoWrap)
fmt.Println("errors.Is(errNoWrap, ErrNotFound):", errors.Is(errNoWrap, ErrNotFound))
Thông báo lỗi (trông giống hệt): getUser: user #42: not found
errors.Is(errNoWrap, ErrNotFound): false
errors.As lấy được NotFoundError: false

Thông báo lỗi hiển thị y hệt (con người đọc không phân biệt được) — nhưng errors.Is/errors.As đều trả về false. %v chỉ gọi .Error() để lấy chuỗi text rồi nhúng vào, không giữ lại liên kết Unwrap() tới lỗi gốc — về mặt lập trình, lỗi gốc coi như đã biến mất, dù log vẫn “trông đúng”. Đây là loại bug nguy hiểm nhất: không crash, không sai lệch thấy được ngay, chỉ âm thầm phá vỡ logic errors.Is/errors.As ở downstream (ví dụ code retry dựa vào errors.Is(err, ErrTimeout) sẽ không bao giờ retry đúng nếu lỗi bị wrap bằng %v ở đâu đó giữa đường).

panic/recover — hiếm khi là lựa chọn đúng

panic dành cho lỗi lập trình thật sự (index out of range, nil pointer dereference, nil map write) — không phải cách xử lý lỗi nghiệp vụ thông thường (đã có error cho việc đó). recover chỉ nên dùng ở biên — nơi 1 request/goroutine không được phép kéo sập cả tiến trình:

func recoverMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                fmt.Printf("chặn được panic: %v -- server KHÔNG sập\n", rec)
                w.WriteHeader(http.StatusInternalServerError)
                w.Write([]byte("internal error"))
            }
        }()
        next.ServeHTTP(w, r)
    })
}

func buggyHandler(w http.ResponseWriter, r *http.Request) {
    var m map[string]int // nil map
    m["x"] = 1           // panic: assignment to entry in nil map
}

Chạy thật với httptest, gửi request gây panic rồi gửi tiếp request bình thường ngay sau:

Request tới /buggy (handler panic):
  chặn được panic: assignment to entry in nil map -- server KHÔNG sập
  status code trả về: 500
Request tới /ok NGAY SAU ĐÓ (server vẫn sống):
  status code: 200 , body: ok

Middleware chặn đúng panic (trả 500 thay vì crash), và request tiếp theo vẫn được phục vụ bình thường (200) — server không hề bị kéo sập theo 1 handler lỗi. Đây chính xác là phạm vi nên dùng recover: 1 lớp bảo vệ ở biên (middleware, worker pool), không phải thay thế cho if err != nil ở logic nghiệp vụ thông thường.

Tự chạy lại demo

cd 02-error-handling-idioms
go run .
go vet ./...

main.go gộp cả 3 demo (sentinel error, error wrapping + đối chiếu %v/%w, panic/recover middleware), chạy tuần tự cho đúng output như các đoạn ở trên.

Tổng kết & bài tiếp theo

Ba idiom cốt lõi: sentinel error cho so sánh đơn giản, typed error + %w khi cần vừa ngữ cảnh vừa truy vết được lỗi gốc, và panic/recover chỉ dành cho biên hệ thống — không phải luồng xử lý lỗi chính. Nhầm %v thành %w là bug thật, âm thầm, đáng nhớ nhất trong số này.
