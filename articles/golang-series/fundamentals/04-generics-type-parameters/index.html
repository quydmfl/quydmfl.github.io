04. Generics: type parameter & constraints

Generics vào Go từ bản 1.18 (2022) — muộn hơn hẳn đa số ngôn ngữ mainstream, có chủ đích. Bài này không chỉ dạy cú pháp, mà tập trung vào ranh giới thực dụng: khi nào generics thực sự đáng dùng, khi nào interface truyền thống vẫn tốt hơn — kể cả linh hoạt hơn.

Type parameter — cú pháp cơ bản

func Map[T, U any](s []T, f func(T) U) []U {
    result := make([]U, len(s))
    for i, v := range s {
        result[i] = f(v)
    }
    return result
}
nums := []int{1, 2, 3, 4}
doubled := Map(nums, func(n int) int { return n * 2 })
strs := Map(nums, func(n int) string { return fmt.Sprintf("n=%d", n) })
doubled: [2 4 6 8]
strs: [n=1 n=2 n=3 n=4]

Map hoạt động với bất kỳ cặp kiểu T, U nào, và Go tự suy luận kiểu (T=int, U=int ở lần gọi đầu; T=int, U=string ở lần gọi sau) — không cần khai báo tường minh Map[int, int](...). So với cách làm trước 1.18 (dùng interface{} + type assertion): mất type safety, lỗi sai kiểu chỉ phát hiện được lúc chạy thay vì lúc biên dịch.

Constraints — giới hạn kiểu được chấp nhận

type Ordered interface {
    ~int | ~int64 | ~float64 | ~string
}

func Max[T Ordered](a, b T) T {
    if a > b {
        return a
    }
    return b
}
fmt.Println("Max(3, 7):", Max(3, 7))
fmt.Println("Max(3.5, 2.1):", Max(3.5, 2.1))
fmt.Println(`Max("banana", "apple"):`, Max("banana", "apple"))
Max(3, 7): 7
Max(3.5, 2.1): 3.5
Max("banana", "apple"): banana

1 hàm duy nhất chạy đúng cho cả int, float64, string — constraints giới hạn đúng tập kiểu có toán tử > hợp lệ, compiler tự kiểm tra. Thử gọi với 1 kiểu không thoả mãn:

type Point struct{ X, Y int }

p1, p2 := Point{1, 2}, Point{3, 4}
Max(p1, p2) // Point không thoả mãn Ordered

Lỗi biên dịch thật:

./constraint_fail.go:19:5: Point does not satisfy Ordered
(Point missing in ~int | ~int64 | ~float64 | ~string)

Đúng như bài 03 đã thấy với method set — Go chặn ngay tại compile-time thay vì để lỗi lọt tới runtime.

So sánh code lặp lại vs generic

Cách cũ (trước 1.18) — lặp lại logic cho từng kiểu cụ thể:

func SumInt(s []int) int {
    var total int
    for _, v := range s { total += v }
    return total
}

func SumFloat64(s []float64) float64 {
    var total float64
    for _, v := range s { total += v }
    return total
}

Rút gọn bằng generic:

type Number interface {
    ~int | ~int64 | ~float64
}

func Sum[T Number](s []T) T {
    var total T
    for _, v := range s { total += v }
    return total
}
fmt.Println("SumInt:", SumInt(ints), "  Sum generic:", Sum(ints))
fmt.Println("SumFloat64:", SumFloat64(floats), "  Sum generic:", Sum(floats))
SumInt: 6   Sum generic: 6
SumFloat64: 4   Sum generic: 4

Cùng kết quả, nhưng Sum thay thế được cho mọi kiểu số hiện tại và tương lai (int32, kiểu tự định nghĩa dựa trên int…) mà không cần viết thêm hàm nào — đúng bài toán generics giải quyết tốt nhất: loại bỏ trùng lặp code khi logic giống hệt nhau, chỉ khác kiểu dữ liệu cụ thể.

Khi nào generics KHÔNG phải lựa chọn đúng

Interface đã đủ khi chỉ cần gọi method chung, không cần biết kiểu cụ thể — và đôi khi generics còn kém linh hoạt hơn:

type Stringer interface{ String() string }

type User struct{ Name string }
func (u User) String() string { return "User:" + u.Name }

type Product struct{ Title string }
func (p Product) String() string { return "Product:" + p.Title }

// ĐÚNG: chỉ cần String() -- interface là đủ
func PrintAll(items []Stringer) {
    for _, item := range items {
        fmt.Println(item.String())
    }
}

// KHÔNG CẦN THIẾT: thêm generics nhưng không giải quyết được gì thêm
func PrintAllGeneric[T Stringer](items []T) {
    for _, item := range items {
        fmt.Println(item.String())
    }
}
mixed := []Stringer{User{Name: "An"}, Product{Title: "Sách"}}
PrintAll(mixed)

users := []User{{Name: "Bình"}}
PrintAllGeneric(users)
User:An
Product:Sách
User:Bình

Chạy đúng cả 2, nhưng nhìn kỹ input: PrintAll(mixed) nhận được 1 slice trộn lẫn User và Product — vì []Stringer chỉ quan tâm “có method String() hay không”, không quan tâm kiểu cụ thể. PrintAllGeneric thì không làm được điều đó — []T buộc mọi phần tử phải cùng 1 kiểu cụ thể T tại thời điểm gọi (users toàn User, không trộn được Product vào cùng slice). Đây là điểm hay bị bỏ qua khi mới học generics: thêm type parameter không tự động “nâng cấp” — với những bài toán chỉ cần polymorphism qua method chung, interface truyền thống vẫn là lựa chọn đúng và linh hoạt hơn, generics chỉ thật sự cần khi thao tác đòi hỏi biết kiểu cụ thể (toán tử +, >, phép tính) mà interface không biểu diễn được.

Tự chạy lại demo

cd 04-generics-type-parameters
go run .
go vet ./...

main.go gộp cả 4 demo (type parameter cơ bản, constraints, so sánh Sum, khi nào không cần generics). Lỗi biên dịch thật ở phần constraints (Point does not satisfy Ordered) không nằm trong main.go — tự tách đoạn code đó ra 1 file riêng rồi go build để tái hiện.

Tổng kết & bài tiếp theo

Generics giải quyết đúng 1 vấn đề cụ thể: loại bỏ trùng lặp code khi logic giống hệt nhau nhưng cần biết kiểu cụ thể để dùng toán tử/phép tính. Không phải công cụ thay thế mặc định cho interface — nhiều bài toán (như PrintAll ở trên) dùng interface vẫn đúng hơn, thậm chí linh hoạt hơn cả generics.

Bài 05 đi vào slice — cấu trúc dữ liệu dùng nhiều nhất Go, và những bẫy nội bộ (aliasing, append) ít người để ý cho tới khi gặp bug thật trên production.
