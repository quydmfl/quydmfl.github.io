05. Slice & Array nội bộ

Slice là cấu trúc dữ liệu dùng nhiều nhất trong Go, và cũng là nguồn bug âm thầm phổ biến nhất — vì slice không phải mảng, nó là 1 “view” (con trỏ + length + capacity) trỏ vào 1 underlying array có thể bị chia sẻ giữa nhiều slice.

Slice là gì bên dưới: pointer + len + cap

a := []int{1, 2, 3, 4, 5}
b := a[1:3] // slicing tạo view, không copy dữ liệu

fmt.Printf("a: %v, len=%d, cap=%d\n", a, len(a), cap(a))
fmt.Printf("b: %v, len=%d, cap=%d\n", b, len(b), cap(b))
fmt.Println("Địa chỉ b[0] có trùng địa chỉ a[1]?", &b[0] == &a[1])
a: [1 2 3 4 5], len=5, cap=5
b: [2 3], len=2, cap=4
Địa chỉ b[0] có trùng địa chỉ a[1]? true

true — b[0] và a[1] là cùng 1 ô nhớ. Chú ý cả cap(b) = 4, không phải 2 (bằng len(b)): slicing giữ nguyên phần capacity còn lại của underlying array tính từ điểm bắt đầu, không cắt gọn theo len.

Slicing tạo view, không copy dữ liệu

Sửa qua b, xem a có bị ảnh hưởng:

b[0] = 999
fmt.Println("a:", a)
fmt.Println("b:", b)
a: [1 999 3 4 5]  <- bị ảnh hưởng dù chỉ sửa qua b
b: [999 3]

a bị đổi dù code chỉ sửa b — đúng như dự đoán từ việc 2 slice chia sẻ chung underlying array. Đây không phải bug của demo, mà là hành vi mặc định của Go — cần biết trước để không bị bất ngờ khi 1 hàm “tưởng như chỉ đọc” slice truyền vào lại vô tình sửa luôn dữ liệu gốc.

append: khi nào an toàn, khi nào không

Đây là nơi bug aliasing thật sự xảy ra trên production — không phải lý thuyết:

func processA(data []int) []int {
    return append(data, 999)
}

original := make([]int, 3, 5) // len=3, cap=5 -- cố tình còn dư capacity
original[0], original[1], original[2] = 1, 2, 3

sub := original[:2] // sub chia sẻ underlying array, cap(sub) vẫn là 5
result := processA(sub)
Trước: [1 2 3]  cap(sub) = 5
result:   [1 2 999]
original: [1 2 999]  <- phần tử index 2 bị ghi đè âm thầm!

original[2] (giá trị 3) bị ghi đè thành 999 — dù processA chỉ nhận sub và trông như đang “thêm phần tử độc lập”. Nguyên nhân: sub có len=2 nhưng cap=5 (thừa hưởng từ original) — còn dư chỗ, nên append ghi trực tiếp vào ô tiếp theo của cùng 1 underlying array, đúng vào vị trí original[2] đang giữ.

Quy tắc dễ nhớ nhưng dễ quên: append chỉ cấp phát underlying array mới khi hết capacity. Còn dư capacity — dù chỉ 1 ô — append sẽ ghi đè tại chỗ, và hành vi này phụ thuộc capacity còn lại tại đúng thời điểm gọi, không phải thứ có thể đọc ra từ chữ ký hàm func processA(data []int) []int.

Sửa đúng: copy tường minh

func processASafe(data []int) []int {
    safe := make([]int, len(data), len(data)) // cap == len, không dư chỗ để chia sẻ
    copy(safe, data)
    return append(safe, 999)
}
result:   [1 2 999]
original: [1 2 3]  <- KHÔNG bị ảnh hưởng

make([]int, len(data), len(data)) tạo slice mới với cap đúng bằng len — không còn “chỗ trống” để append ghi đè lên bất kỳ dữ liệu chia sẻ nào. original giữ nguyên [1 2 3].

Cơ chế grow capacity

Đo thật bằng cách append từng phần tử và theo dõi cap() thay đổi:

s := make([]int, 0)
for i := 0; i < 20; i++ {
    s = append(s, i)
    // in ra mỗi khi cap() đổi
}
len= 1  cap= 1  (tăng từ 0)
len= 2  cap= 2  (tăng từ 1)
len= 3  cap= 4  (tăng từ 2)
len= 5  cap= 8  (tăng từ 4)
len= 9  cap=16  (tăng từ 8)
len=17  cap=32  (tăng từ 16)

Tăng gấp đôi ở slice nhỏ (Go 1.24, kiến trúc arm64) — đúng như tài liệu mô tả. Chạy tiếp lên tới 2.000 phần tử để thấy hệ số chậm dần khi slice đã lớn:

len= 257  cap= 512  (hệ số x2.00)
len= 513  cap= 848  (hệ số x1.66)
len= 849  cap=1280  (hệ số x1.51)
len=1281  cap=1792  (hệ số x1.40)

Từ ngưỡng ~256 phần tử, hệ số tăng giảm dần từ x2.00 xuống x1.66, x1.51… — đánh đổi thực dụng của Go runtime: slice nhỏ tăng nhanh (ít lần cấp phát lại khi mới bắt đầu), slice đã lớn tăng chậm hơn (tránh lãng phí bộ nhớ dự phòng quá nhiều khi slice đã chiếm dụng đáng kể).

Đo thật lợi ích của make với capacity biết trước

func BenchmarkAppendNoPrealloc(b *testing.B) {
    for i := 0; i < b.N; i++ {
        s := make([]int, 0)
        for j := 0; j < 100000; j++ { s = append(s, j) }
    }
}

func BenchmarkAppendWithPrealloc(b *testing.B) {
    for i := 0; i < b.N; i++ {
        s := make([]int, 0, 100000) // capacity biết trước
        for j := 0; j < 100000; j++ { s = append(s, j) }
    }
}
BenchmarkAppendNoPrealloc-10      3411   355943 ns/op   4101405 B/op   28 allocs/op
BenchmarkAppendWithPrealloc-10   13664    87237 ns/op    802825 B/op    1 allocs/op

Nhanh hơn ~4 lần (355943ns → 87237ns), tốn ít bộ nhớ hơn ~5 lần, và quan trọng nhất: 28 lần cấp phát lại → chỉ 1 lần. Mỗi lần capacity không đủ, Go phải cấp phát underlying array mới (lớn hơn) rồi copy toàn bộ dữ liệu cũ sang — biết trước kích thước cần dùng và make([]T, 0, n) ngay từ đầu loại bỏ hoàn toàn chi phí này.

Tự chạy lại demo

cd 05-slice-array-noi-bo
go run .              # 4 demo: view, aliasing bug, fix, capacity growth
go vet ./...
go test -bench=. -benchmem   # benchmark prealloc vs không prealloc

Tổng kết & bài tiếp theo

Slice mạnh vì linh hoạt (view nhẹ, chia sẻ dữ liệu hiệu quả), nhưng chính sự chia sẻ đó là nguồn bug aliasing thật — append có an toàn hay không phụ thuộc vào capacity còn lại tại thời điểm gọi, không đọc được từ chữ ký hàm. Quy tắc an toàn: nếu 1 hàm nhận slice rồi append, và không chắc chắn về capacity, luôn copy tường minh trước.
