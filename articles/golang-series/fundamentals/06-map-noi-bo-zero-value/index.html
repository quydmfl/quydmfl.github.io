06. Map nội bộ & zero value

Oct 22, 2026 · 5 min read

Bài cuối mini-series Fundamentals & Idioms: map là cấu trúc dữ liệu còn lại hay bị hiểu sai — đặc biệt điểm khác biệt quan trọng nhất so với slice (bài 05): map không an toàn khi ghi đồng thời, và Go cố tình làm nó crash ngay lập tức thay vì âm thầm cho dữ liệu sai.

Zero value của map: nil, không phải map rỗng

var m map[string]int // nil map, không phải map rỗng
fmt.Println("m == nil?", m == nil)
fmt.Println("Đọc từ nil map, key không tồn tại:", m["x"])

m["x"] = 1 // ghi vào nil map

Chạy thật:

m == nil? true
Đọc từ nil map, key không tồn tại: 0
Chuẩn bị ghi vào nil map...
panic: assignment to entry in nil map

goroutine 1 [running]:
main.main()
	.../nilmap.go:11 +0x134
exit status 2

Đọc từ nil map hoàn toàn hợp lệ (trả về zero value của kiểu value, ở đây là 0) — nhưng ghi vào nil map panic ngay lập tức. Khác biệt quan trọng với slice: nil slice vẫn append được bình thường (Go tự cấp phát underlying array mới khi cần) — map thì không có cơ chế tương tự cho việc ghi, vì map cần cấu trúc bucket nội bộ đã được khởi tạo trước (qua make hoặc literal map[K]V{}), không thể “tự phát sinh” chỉ từ 1 lần gán như slice.

Thứ tự duyệt map không đảm bảo — cố tình, không phải bug

m := map[string]int{"a": 1, "b": 2, "c": 3, "d": 4, "e": 5}
for k := range m {
    fmt.Print(k, " ")
}

Chạy đúng chương trình này 3 lần liên tiếp:

Chạy lần 1: c d e a b
Chạy lần 2: b c d e a
Chạy lần 3: e a b c d

3 kết quả khác nhau hoàn toàn — cùng 1 map, cùng dữ liệu, chạy lại vẫn đổi thứ tự. Đây là Go cố tình random hoá thứ tự range qua map ở mỗi lần chạy, để ngăn lập trình viên vô tình phụ thuộc vào 1 thứ tự cụ thể vốn không hề được ngôn ngữ đảm bảo. Cần thứ tự ổn định: lấy riêng danh sách key, sort, rồi duyệt theo thứ tự đó:

keys := make([]string, 0, len(m))
for k := range m {
    keys = append(keys, k)
}
sort.Strings(keys)
for _, k := range keys {
    fmt.Print(k, " ")
}
Thứ tự ổn định (đã sort): a b c d e

Truy cập map đồng thời: crash ngay, không phải “đôi khi sai”

20 goroutine cùng ghi vào 1 map không khoá:

m := make(map[int]int)
var wg sync.WaitGroup
for i := 0; i < 20; i++ {
    wg.Add(1)
    go func(n int) {
        defer wg.Done()
        m[n] = n // ghi đồng thời không khoá
    }(i)
}
wg.Wait()
fatal error: concurrent map writes

goroutine 38 [running]:
internal/runtime/maps.fatal(...)
	.../runtime/panic.go:1058
main.main.func1(0x13)
	.../concurrent.go:15

fatal error, không phải panic — khác biệt quan trọng: fatal error là lỗi ở tầng runtime, không thể chặn bằng defer recover() như đã học ở bài 02. Middleware recover() bảo vệ được panic do lỗi logic ứng dụng, nhưng hoàn toàn bất lực trước concurrent map writes — cả tiến trình chết ngay, không có cách nào cứu vãn từ bên trong code Go thông thường.

Chạy lại với go run -race để race detector xác nhận thêm:

WARNING: DATA RACE
Write at 0x00c0001980c0 by goroutine 6:
  runtime.mapaccess2()
Previous write at 0x00c0001980c0 by goroutine 7:
  runtime.mapaccess2()

Đây là quyết định thiết kế có chủ đích của Go: thà crash ngay và rõ ràng (dễ phát hiện ngay trong lúc dev/test) còn hơn để lỗi âm thầm lan xa thành dữ liệu sai khó truy vết sau này trên production.

Fix bằng sync.RWMutex

m := make(map[int]int)
var mu sync.RWMutex
var wg sync.WaitGroup
for i := 0; i < 20; i++ {
    wg.Add(1)
    go func(n int) {
        defer wg.Done()
        mu.Lock()
        m[n] = n
        mu.Unlock()
    }(i)
}
wg.Wait()

Chạy lại với -race:

Hoàn tất, không crash. len(m) = 20

Sạch hoàn toàn dưới -race, len(m) = 20 đúng — sync.RWMutex đảm bảo chỉ 1 goroutine ghi tại 1 thời điểm. (Với pattern đọc nhiều/ghi ít, sync.Map — kiểu map chuyên dụng cho concurrency của thư viện chuẩn — đôi khi phù hợp hơn RWMutex thường, nhưng đó là lựa chọn cần đo trên workload cụ thể, không phải mặc định thay thế.)

Tự chạy lại demo

cd 06-map-noi-bo-zero-value
go run .              # demo thứ tự duyệt + map an toàn với mutex
go run -race .         # xác nhận demo 2 sạch dưới race detector
go vet ./...

Riêng 2 demo gây crash thật (ghi vào nil map, ghi đồng thời không khoá) không nằm trong main.go — vì bản chất chúng khiến chương trình dừng đột ngột. Tách đoạn code tương ứng ra file riêng rồi go run (và go run -race cho phần concurrent) để tự tái hiện đúng lỗi thật ở trên.

Tổng kết mini-series

6 bài đi từ interface (bài 01) → error handling (bài 02) → value/pointer semantics (bài 03) → generics (bài 04) → slice (bài 05) → map (bài này). Xuyên suốt cả 6 bài là 1 sợi chỉ đỏ: Go ưu tiên phát hiện lỗi sớm và rõ ràng — compile-time error cho method set/ambiguous selector sai (bài 03, 04), runtime panic/fatal error rõ ràng thay vì dữ liệu sai âm thầm (nil interface ở bài 01 là ngoại lệ đáng nhớ, còn lại hầu hết đều “thà chết sớm còn hơn sai muộn”).

Nền tảng này là điều kiện cần trước khi bước sang mini-series Concurrency tiếp theo, nơi goroutine/channel sẽ dùng lại chính kiến thức “khi nào dữ liệu bị chia sẻ, khi nào cần đồng bộ” đã xây dựng xuyên suốt series này — đặc biệt là bài học vừa học: chia sẻ dữ liệu (map, slice) giữa nhiều goroutine luôn cần cân nhắc đồng bộ tường minh, Go sẽ không tự bảo vệ.
