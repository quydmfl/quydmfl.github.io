01. PGO (Profile-Guided Optimization)

Mở đầu mini-series cuối cùng của series Go: PGO (Profile-Guided Optimization) — tính năng chính thức từ Go 1.21 cho phép compiler dùng chính profile thật của chương trình (thu bằng pprof, đã học ở Stdlib bài 06) để đưa ra quyết định tối ưu tốt hơn, thay vì chỉ dựa trên phân tích tĩnh như escape analysis (Runtime Internals bài 03).

PGO là gì, khác gì escape analysis tĩnh

Escape analysis, inlining mặc định: compiler quyết định dựa trên cấu trúc code tĩnh, không biết hàm nào thực sự được gọi nhiều nhất lúc chạy. PGO đưa vào 1 file CPU profile thật (default.pgo) thu từ chính chương trình — compiler dùng dữ liệu đó để quyết định inline hàm nào aggressive hơn, và (từ Go 1.22+) cân nhắc “devirtualize” — biến 1 lệnh gọi qua interface (vốn không thể inline vì không biết concrete type) thành lệnh gọi trực tiếp khi profile cho thấy 1 type áp đảo.

Kịch bản demo: gọi qua interface, 1 type chiếm 95%

type Shape interface{ Area() float64 }
type Rectangle struct{ W, H float64 }
func (r Rectangle) Area() float64 { return r.W * r.H }
type Circle struct{ R float64 }
func (c Circle) Area() float64 { return 3.14159265 * c.R * c.R }

func sumAreas(shapes []Shape) float64 {
    total := 0.0
    for _, s := range shapes {
        total += s.Area() // gọi qua interface -- compiler không biết concrete type
    }
    return total
}

makeShapes tạo 10.000 shape với tỷ lệ 95% Rectangle, 5% Circle — đúng kịch bản PGO devirtualize thường được nhắc tới nhiều nhất trong tài liệu Go.

Quy trình PGO thực tế: thu profile → build → đo lại

go test -bench BenchmarkWork -benchtime=3s -cpuprofile=cpu.pprof
cp cpu.pprof default.pgo   # đặt tên default.pgo, cùng thư mục package main
go build .                 # go build (>= 1.21) TỰ ĐỘNG phát hiện và dùng default.pgo

Không cần flag gì thêm ở bước go build cuối — chỉ cần file tên đúng default.pgo nằm cùng thư mục chứa package main.

Đo chênh lệch thật bằng benchstat

So sánh benchmark 10 lần chạy, không PGO vs có PGO (liên hệ Stdlib bài 07):

go test -bench . -benchmem -count=10 > nopgo.txt     # build không default.pgo
cp cpu.pprof default.pgo
go test -bench . -benchmem -count=10 > withpgo.txt   # build CÓ default.pgo
benchstat nopgo.txt withpgo.txt
        │  nopgo.txt  │            withpgo.txt             │
        │   sec/op    │   sec/op     vs base               │
Work-10   70.04m ± 2%   67.38m ± 1%  -3.80% (p=0.000 n=10)

Cải thiện thật ~3.8%, p=0.000 — có ý nghĩa thống kê rõ ràng, không phải nhiễu đo lường (đúng tiêu chuẩn đã đặt ra ở Stdlib bài 07: chỉ tin số liệu có p đủ nhỏ). Đây là mức cải thiện thực tế, khiêm tốn cho 1 chương trình nhỏ — Go team báo cáo mức cải thiện trung bình 2-14% trên các dịch vụ nội bộ lớn của Google khi áp dụng PGO, tuỳ workload.

Bài học thật: devirtualize không phải lúc nào cũng kích hoạt

Cờ debug -d=pgodebug=2 cho xem chính xác quyết định devirtualize của compiler tại từng call site:

go build -gcflags="-d=pgodebug=2" -pgo=default.pgo .
./main.go:28:18: PGO devirtualize considering call s.Area()
./main.go:28:18: call main.sumAreas:3: no hot callee

no hot callee — dù Rectangle chiếm 95% số lần gọi trong dữ liệu thật, compiler không devirtualize lệnh s.Area() ở đây. Đọc thẳng source code compiler (cmd/compile/internal/devirtualize/pgo.go) xác nhận nguyên nhân: quyết định devirtualize dựa trên call-graph edge trong profile — nếu profile không ghi nhận được edge rõ ràng từ call site đó tới 1 callee cụ thể (ví dụ vì các hàm Area() quá nhỏ, có thể đã bị gộp/inline ngay trong lúc thu profile khiến mất thông tin “ai gọi ai” ở mức chi tiết cần thiết), compiler thà không devirtualize còn hơn đoán sai.

-d=pgodebug=1 xác nhận profile vẫn được compiler đọc và dùng thật (không phải bị bỏ qua âm thầm):

hot-callsite-thres-from-CDF=2.1367521367521367

Bài học thực dụng: đừng giả định PGO sẽ luôn devirtualize interface call chỉ vì lý thuyết “1 type áp đảo” — luôn kiểm chứng bằng -d=pgodebug=2 xem quyết định thật của compiler trên chính code của mình, và bằng benchstat xem cải thiện thật có tồn tại hay không, thay vì tin vào mô tả tính năng trên giấy.

Khi nào PGO không giúp ích

  • Profile không đại diện đúng workload production thật (benchmark khác xa traffic thật) — PGO tối ưu sai hướng, có thể còn làm chậm đi
  • Hàm không phải hot path thực sự (I/O-bound, chờ network/disk nhiều hơn tính toán) — cải thiện gần như bằng 0 vì CPU không phải nút thắt
  • Chương trình quá nhỏ/đơn giản, inlining mặc định đã gần tối ưu — như đã thấy, mức cải thiện thực tế có thể chỉ vài %, không phải phép màu

Tự chạy lại demo

cd 01-pgo
go run .
go vet ./...
go test -bench . -benchtime=3s -cpuprofile=cpu.pprof
cp cpu.pprof default.pgo
go build -gcflags="-d=pgodebug=2" -pgo=default.pgo .

main.go + bench_test.go là toàn bộ code cần thiết — default.pgo/cpu.pprof/kết quả benchmark là artifact sinh ra khi chạy lại, không commit kèm bài viết.

Tổng kết & bài tiếp theo

PGO cho phép compiler dùng profile thật thay vì chỉ phân tích tĩnh — cải thiện đo được thật (ở đây ~3.8%, p=0.000) nhưng khiêm tốn hơn nhiều so với kỳ vọng “devirtualize toàn bộ interface call nóng”. Luôn kiểm chứng bằng -d=pgodebug và benchstat, không giả định compiler sẽ làm đúng như tài liệu mô tả trong mọi trường hợp.
