05. Observability: log/slog & metrics

Nov 17, 2026 · 5 min read

Series · Go Performance & Production

  2. 02. Build & binary optimization

3 trụ cột observability cho 1 service Go production: log có cấu trúc, metrics đo được, và khả năng profiling liên tục khi cần chẩn đoán sự cố thật — không cái nào cần dependency ngoài thư viện chuẩn.

log/slog: structured logging từ thư viện chuẩn

log.Println in text tự do, khó parse/query trên hệ thống log tập trung (ELK, Loki…). log/slog (Go 1.21+) log key-value có cấu trúc — cùng 1 lời gọi, output khác nhau hoàn toàn tuỳ handler:

textLogger := slog.New(slog.NewTextHandler(os.Stdout, nil))
jsonLogger := slog.New(slog.NewJSONHandler(os.Stdout, nil))

textLogger.Info("user logged in", "user_id", 42, "ip", "10.0.0.5")
jsonLogger.Info("user logged in", "user_id", 42, "ip", "10.0.0.5")
time=2026-09-12T12:13:37.779+07:00 level=INFO msg="user logged in" user_id=42 ip=10.0.0.5
{"time":"2026-09-12T12:13:37.779962+07:00","level":"INFO","msg":"user logged in","user_id":42,"ip":"10.0.0.5"}

TextHandler dễ đọc bằng mắt khi chạy local dev; JSONHandler đúng định dạng hệ thống log tập trung mong đợi khi chạy production — cùng 1 lời gọi log.Info(...) trong code, chỉ khác handler khởi tạo 1 lần lúc main(). Đổi môi trường không cần sửa bất kỳ dòng log nào trong toàn bộ codebase.

Correlation: truy vết 1 request qua toàn bộ log — kể cả khi chạy đồng thời

Gắn request ID vào context (liên hệ Stdlib bài 01), mọi dòng log trong quá trình xử lý request đó tự động kèm cùng 1 request_id:

func loggerFromContext(ctx context.Context, base *slog.Logger) *slog.Logger {
    if reqID, ok := ctx.Value(requestIDKey).(string); ok {
        return base.With("request_id", reqID)
    }
    return base
}

3 “request” chạy thật sự đồng thời (goroutine riêng, độ trễ khác nhau), để log tự nhiên đan xen:

{"msg":"bắt đầu xử lý","request_id":"req-C"}
{"msg":"bắt đầu xử lý","request_id":"req-B"}
{"msg":"bắt đầu xử lý","request_id":"req-A"}
{"msg":"xử lý xong","request_id":"req-B"}
{"msg":"xử lý xong","request_id":"req-C"}
{"msg":"xử lý xong","request_id":"req-A"}

Log của 3 request đan xen thật (không theo thứ tự A, B, C như code khai báo — req-B xong trước vì có độ trễ ngắn nhất) — đúng bản chất log thật trên production khi hàng trăm request xử lý song song. Nhưng grep "req-A" (hoặc filter theo field request_id trên hệ thống log tập trung) luôn tái hiện lại đúng và đầy đủ hành trình của đúng 1 request, dù log gốc rối tới đâu.

Metrics cơ bản qua expvar — không cần dependency ngoài

expvar.Publish("request_count", expvar.Func(func() any {
    return atomic.LoadInt64(&requestCount)
}))

expvar (thư viện chuẩn) expose biến đếm qua /debug/vars dạng JSON. Fire 8 request thành công + 2 request lỗi (?fail=1), đọc lại:

request_count: 10
error_count: 2

Khớp chính xác 8 + 2 = 10 request, 2 lỗi. /debug/vars mặc định còn tự động kèm memstats đầy đủ (giống runtime.MemStats đã dùng suốt Runtime Internals) và cmdline — đủ dùng cho dashboard giám sát cơ bản mà không cần cài Prometheus client hay bất kỳ dependency ngoài nào.

Continuous profiling trên production: rủi ro thật nếu để hở

Stdlib bài 06 đã dùng net/http/pprof để chẩn đoán CPU/heap/goroutine — cực kỳ hữu ích, nhưng để endpoint này public không xác thực là rủi ro thật, không phải lý thuyết. Kiểm chứng bằng 2 request đơn lẻ, không cần công cụ tấn công nào:

resp, _ := http.Get("http://localhost:19093/debug/pprof/cmdline")
Nội dung /debug/pprof/cmdline (không cần xác thực):
/var/folders/c5/vj9vykd52xjf0l66w066qdkr0000gn/T/go-build3382567354/b001/exe/pprof_risk

Lộ đường dẫn binary thật chỉ với 1 request không cần đăng nhập — thông tin nội bộ (cấu trúc thư mục, tên build) mà bình thường không nên public. Nghiêm trọng hơn về mặt tài nguyên:

resp, err := http.Get("http://localhost:19094/debug/pprof/profile?seconds=5")
Request /debug/pprof/profile?seconds=5 hoàn tất sau: 5.054s

Chỉ 1 request đơn lẻ, không cần lặp lại, buộc server phải bận rộn profiling đúng 5 giây — tham số seconds hoàn toàn do phía gọi tự chọn (thử seconds=3600 sẽ giữ server “làm việc” thêm 1 giờ). Không cần kỹ thuật tấn công phức tạp nào để biến 1 endpoint chẩn đoán hữu ích thành điểm tiêu hao tài nguyên nếu để public. Cách làm đúng: mount pprof trên 1 http.ServeMux riêng, lắng nghe ở port/địa chỉ chỉ truy cập được từ nội bộ (VPN, service mesh, hoặc ít nhất 1 middleware xác thực) — không bao giờ dùng chung http.DefaultServeMux (nơi import _ "net/http/pprof" tự đăng ký) với các route public-facing của service.

Tự chạy lại demo

cd 05-observability
go run .
go vet ./...

main.go gộp 3 demo an toàn (slog handler, correlation đồng thời, expvar metrics). 2 demo minh hoạ rủi ro pprof (đọc cmdline, giữ server bận 5 giây) không nằm trong main.go vì mục đích minh hoạ khác — chỉ cần 2 dòng http.Get để tự tái hiện, không cần công cụ đặc biệt.

Tổng kết & bài tiếp theo

log/slog tách rời “log cái gì” (code logic) khỏi “log ra sao” (handler, cấu hình 1 lần) — cùng 1 lời gọi cho ra text dễ đọc lúc dev hoặc JSON có cấu trúc lúc production. Gắn request ID vào context giúp tái hiện đúng hành trình 1 request dù log thật đan xen hỗn loạn giữa hàng trăm request đồng thời. expvar đủ cho metrics cơ bản không cần dependency ngoài. Và pprof — công cụ chẩn đoán mạnh nhất đã học — chính vì mạnh nên để hở không xác thực là rủi ro thật, kiểm chứng được chỉ bằng 2 request đơn giản, không cần tới công cụ tấn công nào.
