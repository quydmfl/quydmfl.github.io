02. Goroutine stack

Bài 01 đo goroutine map lên OS thread thế nào qua GMP model. Bài này đi vào lý do chính khiến tạo 50.000 goroutine (như demo bài 01) khả thi trong khi tạo 50.000 OS thread thì gần như chắc chắn hết bộ nhớ: kích thước stack.

Stack nhỏ ban đầu, lớn động theo nhu cầu

OS thread thường cấp phát sẵn 1 vùng stack cố định khi tạo (mặc định 8MB trên Linux/macOS phổ biến) — dù thread đó chỉ dùng vài trăm byte. Goroutine ngược lại: bắt đầu với stack rất nhỏ, chỉ lớn lên khi thật sự cần, và runtime tự phát hiện nhu cầu đó qua “stack guard” — 1 phép kiểm tra chèn ở đầu mỗi lời gọi hàm, so sánh con trỏ stack hiện tại với giới hạn còn lại.

const n = 10000
ready := make(chan struct{})
done := make(chan struct{})
var wg sync.WaitGroup
for i := 0; i < n; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        <-ready
        <-done
    }()
}

Đo runtime.MemStats.StackInuse trước/sau khi tạo 10.000 goroutine (đang block, chưa làm gì phức tạp):

StackInuse trước: 2424832 bytes
StackInuse sau khi tạo 10000 goroutine: 21987328 bytes
Chênh lệch: 19562496 bytes, trung bình mỗi goroutine: 1956 bytes

~1956-2064 byte mỗi goroutine qua nhiều lần chạy (dao động nhẹ do baseline runtime) — khớp với con số vẫn được trích dẫn trong tài liệu Go: goroutine bắt đầu với stack 2KB. So với 8MB mặc định của 1 OS thread, chênh lệch hơn 4000 lần — đây là lý do cốt lõi cho phép multiplexing hàng chục nghìn goroutine đã thấy ở bài 01.

Khi cần lớn hơn: runtime tự copy sang vùng nhớ mới

Khi 1 hàm gọi sâu hơn không gian còn lại trên stack hiện tại, stack guard phát hiện, runtime cấp phát 1 vùng nhớ lớn hơn (thường gấp đôi kích thước cũ), rồi copy toàn bộ nội dung stack hiện có sang vùng mới trước khi tiếp tục chạy. Quan sát qua đệ quy có mảng cục bộ 256 byte mỗi tầng, đo StackInuse tại các mốc độ sâu:

func recurseGrowth(depth, maxDepth int) {
    var localArray [256]byte
    localArray[0] = byte(depth)
    if depth%20000 == 0 {
        reportStack(depth)
    }
    if depth >= maxDepth {
        return
    }
    recurseGrowth(depth+1, maxDepth)
}
Độ sâu      0: StackInuse =     262144 bytes
Độ sâu  20000: StackInuse =    1277952 bytes
Độ sâu  40000: StackInuse =    2326528 bytes
Độ sâu  60000: StackInuse =    2326528 bytes
Độ sâu  80000: StackInuse =    4423680 bytes
Độ sâu 100000: StackInuse =    4423680 bytes
Hoàn tất 100000 tầng đệ quy, không crash

100.000 tầng đệ quy hoàn tất, không cần khai báo trước kích thước stack — thứ bắt buộc phải làm thủ công (hoặc gây crash) với stack cố định kiểu C/C++. Số liệu cũng cho thấy đúng mô hình “lớn theo cấp số nhân rồi giữ nguyên tới lần grow tiếp theo” (60000 và 100000 giữ nguyên giá trị của mốc trước — chưa cần grow thêm ở đúng mốc đo).

Lưu ý kỹ thuật khi tự đo: hàm reportStack đọc runtime.MemStats được tách thành 1 hàm riêng, gọi từ bên trong recurseGrowth thay vì khai báo var ms runtime.MemStats ngay trong hàm đệ quy. runtime.MemStats là 1 struct khá lớn (chứa các mảng cố định như PauseNs [256]uint64) — nếu khai báo trực tiếp trong hàm đệ quy, kích thước frame của mỗi tầng sẽ phình to theo đúng kích thước struct đó dù chỉ dùng ở nhánh điều kiện, khiến chương trình chạm trần stack mặc định (1GB) chỉ sau khoảng 90.000 tầng thay vì hoàn tất 100.000 tầng như mong đợi — đây là bài học thật rút ra được trong lúc chuẩn bị demo cho chính bài viết này.

Vì sao con trỏ vào biến stack vẫn an toàn sau khi copy

Copy toàn bộ stack sang vùng nhớ mới đặt ra câu hỏi: điều gì xảy ra với con trỏ đang trỏ vào 1 biến trên vùng stack cũ? Runtime giải quyết bằng cách quét toàn bộ stack đang copy, tìm mọi con trỏ trỏ vào chính vùng stack đó, và điều chỉnh lại giá trị con trỏ theo đúng offset dịch chuyển — hoàn toàn trong suốt với code Go, lập trình viên không cần biết stack vừa “di chuyển”.

Kiểm chứng gián tiếp: đệ quy 200.000 tầng, mỗi tầng giữ 1 biến cục bộ (không escape lên heap — xác nhận bằng go build -gcflags="-m", không thấy dòng moved to heap cho biến này), cộng dồn qua giá trị trả về:

func recurseIntegrity(depth, maxDepth int) int {
    localValue := depth // biến cục bộ thật, không escape lên heap
    if depth >= maxDepth {
        return localValue
    }
    return localValue + recurseIntegrity(depth+1, maxDepth)
}
Đệ quy 200000 tầng, tổng tính được: 20000100000
Công thức đóng n(n+1)/2 = 20000100000
KHỚP -- mọi biến cục bộ trên stack vẫn đúng sau nhiều lần stack grow

200.000 tầng chắc chắn đã kích hoạt nhiều lần stack grow (so với chỉ 100.000 tầng ở demo trước đã cần tới ~4.4MB). Nếu runtime tính sai địa chỉ biến cục bộ sau bất kỳ lần copy nào, tổng cộng dồn qua return value (vốn được truyền qua thanh ghi/stack frame, không qua con trỏ tường minh) sẽ lệch khỏi công thức đóng n(n+1)/2 — kết quả khớp chính xác xác nhận toàn bộ chuỗi grow diễn ra đúng.

Giới hạn thật: stack overflow có kiểm soát

Goroutine stack không lớn vô hạn — mặc định có trần khoảng 1GB trên hệ 64-bit (runtime.maxstacksize). Để demo nhanh và có kiểm soát thay vì chờ cấp phát tới 1GB, hạ trần xuống 10MB bằng debug.SetMaxStack:

debug.SetMaxStack(10 << 20) // hạ trần xuống 10MB (mặc định ~1GB) để demo nhanh, có kiểm soát
recurse(0) // đệ quy vô hạn, không có điều kiện dừng
Trần stack đã hạ xuống 10MB, bắt đầu đệ quy vô hạn...
runtime: goroutine stack exceeds 10485760-byte limit
runtime: sp=0x14000960630 stack=[0x14000960000, 0x14001160000]
fatal error: stack overflow

fatal error, không phải panic — cùng nhóm lỗi với deadlock (Concurrency bài 02) và concurrent map write (Concurrency bài 06): runtime tự vệ chủ động khi phát hiện vi phạm bất biến nội bộ nghiêm trọng, dừng ngay lập tức thay vì để chương trình tiếp tục ở trạng thái không xác định.

Tự chạy lại demo

cd 02-goroutine-stack
go run .
go vet ./...

main.go gộp 3 demo an toàn (stack growth theo độ sâu, chi phí stack ban đầu, tính đúng đắn dữ liệu sau grow). Demo stack overflow có kiểm soát (debug.SetMaxStack + đệ quy vô hạn) không nằm trong main.go vì cố ý crash — tách thành file riêng để tự tái hiện đúng lỗi thật ở trên.

Tổng kết & bài tiếp theo

Goroutine bắt đầu với stack ~2KB (so với 8MB của OS thread), tự động grow bằng cách cấp phát vùng lớn hơn và copy toàn bộ nội dung — kể cả điều chỉnh lại mọi con trỏ trỏ vào vùng stack cũ, hoàn toàn trong suốt với code Go. Trần mặc định ~1GB vẫn tồn tại, vượt quá sẽ dừng chương trình với fatal error: stack overflow thay vì hành vi không xác định.

Bài 03 đi vào heap — nơi mọi thứ escape khỏi stack (qua con trỏ, interface, closure…) thực sự được cấp phát, và cơ chế mspan/mcache/mcentral/mheap giúp Go alloc nhanh hơn malloc truyền thống trong đa số trường hợp.
