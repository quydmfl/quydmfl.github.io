03. Memory allocator

Nov 1, 2026 · 7 min read

Bài 02 nói về stack — vùng nhớ riêng của từng goroutine, tự lớn/nhỏ động. Bài này đi vào heap — nơi mọi giá trị “thoát” khỏi stack (qua con trỏ, interface, closure…) thực sự được cấp phát, và cơ chế phân cấp giúp alloc nhỏ trong Go rẻ hơn nhiều so với gọi malloc trực tiếp.

Phân cấp cấp phát: mheap → mcentral → mcache → mspan

  • mheap: vùng heap toàn cục, quản lý bởi OS qua mmap, chia thành các trang bộ nhớ (page)
  • mcentral: theo từng size class (kích thước cố định), phân phối mspan cho các mcache
  • mcache: cache cục bộ cho từng P (liên hệ bài 01) — hầu hết alloc nhỏ lấy thẳng từ đây, không cần giành lock toàn cục
  • mspan: đơn vị vùng nhớ liên tục, chia thành các block cùng kích thước (size class)

Vì mỗi P có mcache riêng, phần lớn new/make trong code Go hoàn toàn không chạm lock nào — đây là 1 lý do khiến Go alloc nhỏ rẻ hơn hẳn so với malloc kiểu C truyền thống (vốn thường phải qua tranh chấp lock chung khi nhiều thread cùng cấp phát).

Size class: alloc bị làm tròn lên kích thước cố định gần nhất

Go định nghĩa sẵn ~70 size class cố định (8, 16, 24, 32, 48, 64…) — alloc 1 struct không khớp đúng size class nào sẽ bị làm tròn lên class gần nhất lớn hơn, đổi lấy tốc độ cấp phát/tái sử dụng nhanh hơn:

type Exact16 struct{ A, B int64 }  // đúng 16 byte
type Odd17 struct{ Data [17]byte } // 17 byte, không khớp size class nào
type Odd40 struct{ Data [40]byte } // 40 byte, không khớp size class nào

Đo bằng runtime.MemStats.HeapAlloc trước/sau khi cấp phát 1 triệu instance mỗi loại:

Exact16 (16 byte logic): trung bình 16 bytes/alloc (khớp thẳng, không lãng phí)
Odd17   (17 byte logic): trung bình 24 bytes/alloc (làm tròn lên size class 24)
Odd40   (40 byte logic): trung bình 48 bytes/alloc (làm tròn lên size class 48)

Số liệu khớp chính xác bảng size class thật của Go runtime (runtime/sizeclasses.go): Exact16 rơi đúng vào class 16 byte, không lãng phí; Odd17 (17 byte) buộc phải nhảy lên class kế tiếp là 24 byte — lãng phí 7 byte cho mỗi lần alloc (gọi là internal fragmentation); Odd40 nhảy lên class 48 byte. Chạy lại nhiều lần cho số dao động nhẹ 23-24 và 47-48 (do 1 phần nhỏ bộ nhớ nền runtime cấp phát xen kẽ trong lúc đo), nhưng luôn khớp đúng size class lý thuyết.

Lưu ý khi tự đo theo cách này: phải cấp phát mảng chứa kết quả (keep := make([]any, n)) trước khi chụp MemStats lần đầu. Nếu tạo mảng đó sau lần đo “before”, chi phí cấp phát của chính mảng chứa kết quả (8-16 byte mỗi phần tử tuỳ kiểu) sẽ cộng lẫn vào số đo trung bình mỗi struct — đây là sai lầm thật gặp phải khi chuẩn bị demo cho bài viết, ban đầu ra kết quả sai lệch gấp rưỡi so với size class thật.

Alloc lớn (>32KB): đi thẳng qua mheap, làm tròn theo trang bộ nhớ

Object lớn hơn 32KB bỏ qua toàn bộ hệ thống size class/mcache, cấp phát trực tiếp từ mheap theo đơn vị trang bộ nhớ (page, thường 8KB):

type BigObject struct {
    Data [40000]byte // 40000 byte > 32KB
}
BigObject (40000 byte logic): trung bình 40958 bytes/alloc (làm tròn theo trang bộ nhớ, không theo size class)

40958 byte đo được rất sát 40960 = 5 × 8192 — đúng 5 trang bộ nhớ 8KB, không phải làm tròn theo bảng size class như alloc nhỏ. Benchmark thật (go test -bench . -benchmem) cho thấy chênh lệch tốc độ tương ứng:

BenchmarkAllocSmall-10    120399300    9.638 ns/op      16 B/op    1 allocs/op
BenchmarkAllocLarge-10       430618   3055 ns/op    40960 B/op    1 allocs/op

Alloc lớn chậm hơn ~317 lần so với alloc nhỏ (3055 / 9.638) — không chỉ vì kích thước dữ liệu, mà vì phải đi qua đường cấp phát khác hẳn (chạm mheap trực tiếp, có thể cần tìm vùng trang liên tục đủ lớn, thay vì lấy nhanh từ mcache cục bộ của P).

Escape analysis: ai quyết định biến nằm stack hay heap

Go compiler tự quyết định 1 biến nằm stack hay heap dựa trên phân tích tĩnh “liệu địa chỉ của biến có thoát khỏi phạm vi an toàn của hàm không” — không phải lập trình viên chỉ định thủ công như C (malloc vs biến cục bộ):

// escapesToHeap: trả về con trỏ tới biến cục bộ -- biến "thoát" khỏi hàm
func escapesToHeap() *int {
    x := 42
    return &x
}

// staysOnStack: biến cục bộ chỉ dùng nội bộ, không có con trỏ nào thoát ra ngoài
func staysOnStack() int {
    y := 42
    return y
}
go build -gcflags="-m" .
./main.go:86:6: can inline escapesToHeap
./main.go:87:2: moved to heap: x
./main.go:92:6: can inline staysOnStack

x bị đánh dấu moved to heap, y thì không — đúng như tên hàm mô tả: escapesToHeap trả về &x, nếu x nằm trên stack, con trỏ đó sẽ trỏ vào vùng nhớ có thể bị ghi đè ngay khi hàm return (stack frame bị tái sử dụng cho lời gọi tiếp theo); compiler phát hiện điều này và tự động chuyển x sang heap để con trỏ vẫn hợp lệ sau khi hàm kết thúc. staysOnStack trả về giá trị y (copy), không có con trỏ nào thoát ra — y an toàn ở lại trên stack, cấp phát/thu hồi gần như miễn phí (chỉ là di chuyển con trỏ stack, không qua bất kỳ cơ chế mspan/mcache nào ở trên).

Demo: pprof allocation profile thật

runtime/pprof cho phép ghi lại toàn bộ heap profile của chương trình đang chạy — hữu ích để tìm chính xác dòng code nào chịu trách nhiệm cho phần lớn allocation:

allocateLots() // vòng lặp 500.000 lần append &Payload{} (mỗi Payload 128 byte)

f, _ := os.Create("mem.prof")
runtime.GC()
pprof.WriteHeapProfile(f)
go tool pprof -top -alloc_space -nodecount 8 mem.prof

alloc_space là cộng dồn toàn bộ byte từng cấp phát trong suốt vòng đời chương trình (không phải chỉ heap đang sống tại thời điểm chụp) — vì main.go chạy tuần tự cả 4 demo trước khi ghi profile, breakdown phản ánh đúng tỷ trọng thật của từng demo: allocateLots (Demo 4) chiếm nhiều nhất (36.38%, khớp 500.000 × 128 byte ≈ 64MB dữ liệu logic, cộng thêm overhead slice), measureAvgAlloc (Demo 1, gọi 3 lần cho 3 loại struct) cộng dồn gần một nửa (cum% = 48.50%) vì được tính gộp cả những gì các closure func1/func2/func3 cấp phát bên trong nó. Đây chính là cách chẩn đoán thật “hàm nào đang tạo áp lực GC nhiều nhất” trên 1 service Go — muốn cô lập đúng 1 đoạn code, cách làm chuẩn là gọi pprof.WriteHeapProfile ngay sau đoạn đó, tách riêng khỏi phần còn lại của chương trình.

Tự chạy lại demo

cd 03-memory-allocator
go run .
go vet ./...

go build -gcflags="-m" .                              # xem quyết định escape analysis
go tool pprof -top -alloc_space -nodecount 8 mem.prof  # xem heap profile vừa ghi ra
go test -bench . -benchmem -run '^$'                   # benchmark alloc nhỏ vs alloc lớn

main.go gộp cả 4 demo (size class, alloc lớn qua mheap, escape analysis, ghi heap profile). File mem.prof được tạo ngay khi chạy go run .. alloc_bench_test.go chứa 2 benchmark độc lập (BenchmarkAllocSmall/BenchmarkAllocLarge) dùng cho số liệu ns/op/B/op ở phần alloc lớn phía trên.

Tổng kết & bài tiếp theo

Go cấp phát heap qua 4 tầng (mheap → mcentral → mcache → mspan), dùng ~70 size class cố định để alloc nhỏ nhanh gần như miễn phí lock nhờ cache riêng cho từng P — đổi lại 1 chút lãng phí do làm tròn (internal fragmentation). Alloc lớn hơn 32KB đi con đường khác hẳn, chậm hơn hàng trăm lần. Escape analysis của compiler quyết định biến nằm stack (rẻ) hay heap (đắt hơn, cần GC dọn) hoàn toàn tự động dựa trên việc địa chỉ biến có “thoát” khỏi hàm hay không.

Bài 04 đi vào garbage collector — cơ chế dọn dẹp mọi thứ vừa được cấp phát ở bài này, tricolor mark-sweep và write barrier hoạt động thế nào trong thực tế, đo bằng runtime.ReadMemStats thật.
