Bài 03 cấp phát, bài này dọn dẹp. Go GC là concurrent mark-sweep collector — chạy phần lớn thời gian song song với chương trình chính, khác hẳn hình dung “dừng cả chương trình để dọn rác” của GC thế hệ cũ.

Tricolor mark-sweep: white/gray/black

Mọi object bắt đầu white (coi như rác). GC duyệt từ gốc (goroutine stack — bài 02, global variable…), tô gray rồi black cho object còn sống và mọi thứ nó tham chiếu tới. Sau khi duyệt xong, object còn white là rác thật, được sweep (thu hồi trả lại cho allocator ở bài 03).

Vấn đề: chương trình chính (mutator) vẫn chạy và ghi con trỏ mới trong lúc GC đang duyệt — có thể khiến GC bỏ sót 1 object còn sống nếu không cẩn thận. Write barrier — đoạn code nhỏ chèn vào mọi lệnh ghi con trỏ khi GC đang chạy — giữ bất biến “không black object nào trỏ tới white object”, đảm bảo tính đúng đắn dù mutator vẫn hoạt động song song.

GC pause thật: chỉ vài chục micro giây

Go GC chỉ dừng hẳn chương trình (stop-the-world) ở 2 giai đoạn cực ngắn: bắt đầu mark (mark setup) và kết thúc mark (mark termination). Phần lớn thời gian mark/sweep chạy song song với goroutine khác. Đo thật bằng runtime.ReadMemStats trên chương trình tạo áp lực GC (cấp phát liên tục, rời bỏ tham chiếu định kỳ):

func allocGarbage(n int) {
    var head *Node
    for i := 0; i < n; i++ {
        head = &Node{Next: head}
        if i%1000 == 0 {
            head = nil // rời bỏ tham chiếu định kỳ để tạo rác thật
        }
    }
}
Số lần GC chạy: 166
Tổng thời gian pause: 6962100 ns
Trung bình mỗi lần pause: 41940 ns

166 chu kỳ GC hoàn chỉnh, tổng cộng chỉ ~7ms pause cho toàn bộ chương trình — trung bình mỗi lần dừng hẳn chỉ ~42 micro giây (0.042 mili-giây). Đây chính là ý nghĩa thực tế của “concurrent GC”: dù chạy hàng trăm chu kỳ, tổng thời gian chương trình bị “đóng băng” hoàn toàn cộng dồn lại vẫn rất nhỏ so với tổng thời gian chạy.

GOGC: tần suất GC đánh đổi CPU lấy bộ nhớ đỉnh

GOGC (mặc định 100) quyết định: GC cycle tiếp theo chạy khi heap tăng thêm 100% so với heap sống sau lần GC trước. Tăng GOGC nghĩa là chờ heap phình to hơn mới dọn — ít GC hơn, nhưng heap đỉnh lớn hơn:

debug.SetGCPercent(percent)
allocGarbage(2_000_000)
GOGC=100 (mặc định): 165 lần GC, tổng pause 7530252 ns, thời gian chạy 138ms, HeapAlloc cuối 3622048 bytes
GOGC=400          : 37 lần GC, tổng pause 1758042 ns, thời gian chạy 117ms, HeapAlloc cuối 5923360 bytes
GOGC=off          : 0 lần GC, tổng pause 0 ns, thời gian chạy 108ms, HeapAlloc cuối 576168648 bytes

Đánh đổi rất rõ: GOGC=100 chạy 165 lần GC nhưng giữ heap chỉ ~3.6MB; GOGC=400 giảm còn 37 lần (ít hơn ~4.5 lần), đổi lấy heap phình lên ~5.9MB; GOGC=off không GC lần nào, nhanh nhất về lý thuyết (không tốn CPU cho GC) nhưng heap phình tới ~576MB — gấp ~159 lần so với GOGC=100, cho cùng 1 khối lượng công việc. Đây là lý do GOGC=off gần như không bao giờ nên dùng trên production trừ khi chương trình chạy ngắn hạn và biết chắc tổng bộ nhớ cần dùng.

GOMEMLIMIT: trần cứng, thắng cả khi GOGC đã tắt

GOMEMLIMIT (Go 1.19+) đặt trần bộ nhớ tuyệt đối — GC chạy gấp hơn khi heap tiến gần trần, bất kể GOGC đang cấu hình gì. Phù hợp môi trường container có giới hạn RAM cứng, nơi để heap phình tự do như GOGC=off ở trên có thể khiến container bị OOM-kill:

debug.SetGCPercent(-1)          // tắt hẳn GOGC-based trigger
debug.SetMemoryLimit(30 << 20) // nhưng đặt trần cứng 30MB qua GOMEMLIMIT
allocGarbage(2_000_000)
GOGC=off nhưng GOMEMLIMIT=30MB:
  Số lần GC: 60
  HeapAlloc cuối: 3336448 bytes (giữ dưới trần 30MB)

Dù GOGC đã tắt hoàn toàn (điều kiện lẽ ra khiến heap phình tới ~576MB như đo ở trên), GOMEMLIMIT=30MB vẫn buộc runtime chạy 60 lần GC, giữ heap cuối cùng chỉ ~3.3MB — nằm sâu dưới trần 30MB. GOMEMLIMIT không thay thế GOGC, mà hoạt động như 1 giới hạn bổ sung: cái nào kích hoạt GC trước thì GC chạy trước.

Demo: giảm GC pressure bằng sync.Pool

Cách giảm áp lực GC hiệu quả nhất không phải tinh chỉnh GOGC, mà là giảm allocation ngay từ đầu. So sánh cấp buffer mới mỗi lần với tái sử dụng qua sync.Pool:

// Không dùng Pool: alloc mới mỗi lần, giá trị cũ thành rác ngay
buf := make([]byte, bufSize)

// Dùng sync.Pool: lấy lại buffer đã dùng xong, tái sử dụng thay vì alloc mới
buf := bufPool.Get().([]byte)
// ... dùng buf ...
bufPool.Put(buf)
Không dùng Pool (alloc mới mỗi lần): 624 lần GC, tổng pause 17761719 ns, TotalAlloc tăng 2048024160 bytes
Dùng sync.Pool (tái sử dụng buffer): 3 lần GC, tổng pause 107542 ns, TotalAlloc tăng 12009784 bytes

Chênh lệch rất lớn cho cùng 500.000 vòng lặp: không dùng Pool tạo ra ~2GB tổng lượng cấp phát (TotalAlloc cộng dồn), kích hoạt 624 lần GC, tổng pause ~17.8ms; dùng sync.Pool giảm còn ~12MB cấp phát (giảm ~170 lần), chỉ 3 lần GC, tổng pause ~108 micro giây — nhanh hơn ~165 lần. Đây là kỹ thuật tối ưu GC phổ biến nhất trong code Go production thực tế (encoding/json, net/http và nhiều thư viện chuẩn đều dùng sync.Pool nội bộ cho đúng lý do này).

Tự chạy lại demo

cd 04-garbage-collector
go run .
go vet ./...

main.go gộp cả 4 demo (GC pause cơ bản, so sánh GOGC, GOMEMLIMIT ép GC, sync.Pool). Mỗi demo tự khôi phục cấu hình GC mặc định (debug.SetGCPercent(100), bỏ GOMEMLIMIT) trước khi demo tiếp theo chạy, tránh cấu hình của demo trước ảnh hưởng demo sau.

Tổng kết & bài tiếp theo

Go GC dùng tricolor mark-sweep chạy phần lớn song song với chương trình chính, write barrier giữ tính đúng đắn khi mutator vẫn hoạt động — pause thật chỉ vài chục micro giây mỗi chu kỳ dù chạy hàng trăm lần. GOGC đánh đổi tần suất GC lấy bộ nhớ đỉnh; GOMEMLIMIT đặt trần cứng, thắng cả khi GOGC đã tắt — nhưng cách giảm áp lực GC hiệu quả nhất vẫn là giảm allocation từ gốc, ví dụ qua sync.Pool.
