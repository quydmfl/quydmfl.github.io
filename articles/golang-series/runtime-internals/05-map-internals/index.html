05. Map internals

map là kiểu dữ liệu tưởng đơn giản nhất trong Go, nhưng bên dưới là 1 trong những phần runtime thay đổi nhiều nhất qua các bản Go gần đây. Máy chạy demo cho series này dùng Go 1.24.1 — bản đã thay thế hoàn toàn implementation map cũ, nên bài này bắt đầu bằng việc xác minh thật đang chạy thiết kế nào trước khi mô tả chi tiết.

Go 1.24: Swiss Table thay cho hmap/bmap cũ

Đọc thẳng source code Go 1.24 (internal/runtime/maps/map.go), dòng comment đầu tiên xác nhận:

// The map design is based on Abseil's "Swiss Table" map design
// (https://abseil.io/about/design/swisstables), with additional modifications
// to cover Go's additional requirements

Thuật ngữ mới hoàn toàn so với hmap/bmap quen thuộc trước Go 1.24:

  • Slot: 1 vị trí lưu 1 cặp key/value
  • Group: nhóm 8 slot + 1 “control word” (8 byte) — control word cho phép kiểm tra cả 8 slot cùng lúc bằng vài phép toán bit, thay vì dò tuần tự từng slot như hash table truyền thống
  • H1/H2: hash 64-bit tách thành H1 (57 bit cao, chọn group qua probing) và H2 (7 bit thấp, lưu ngay trong control word để so khớp nhanh không cần đọc slot)
  • Table: 1 bảng hash Swiss Table hoàn chỉnh; Directory: mảng các table — map lớn được chia thành nhiều table nhỏ (extendible hashing) để mỗi lần grow chỉ cần rehash 1 phần, không phải toàn bộ map

Dấu vết runtime thật xác nhận package này đang chạy — kích hoạt lỗi concurrent map writes (như Concurrency bài 06) và đọc thẳng stack trace:

fatal error: concurrent map writes

goroutine 44 [running]:
internal/runtime/maps.fatal({0x1002ee67d?, 0x0?})
	/opt/homebrew/Cellar/go/1.24.1/libexec/src/runtime/panic.go:1058 +0x20
main.main.func1(0xb)

internal/runtime/maps.fatal — đúng package Swiss Table vừa đọc source, không phải runtime.mapassign kiểu cũ. go env GOEXPERIMENT trên máy này trả về rỗng, xác nhận Swiss Table đã là mặc định, không còn cần cờ thử nghiệm GOEXPERIMENT=swissmap như các bản Go 1.21-1.23.

Vì sao thứ tự duyệt map luôn ngẫu nhiên

Runtime cố tình random hoá điểm bắt đầu duyệt mỗi lần range 1 map — không phải “chưa tối ưu”, mà là quyết định thiết kế ngăn code phụ thuộc nhầm vào thứ tự duyệt (vốn không được Go spec đảm bảo):

m := map[string]int{"a": 1, "b": 2, "c": 3, "d": 4, "e": 5}
for run := 0; run < 3; run++ {
    var order []string
    for k := range m {
        order = append(order, k)
    }
    fmt.Println("Lần", run+1, ":", order)
}
Lần 1 : [a b c d e]
Lần 2 : [a b c d e]
Lần 3 : [b c d e a]

3 lần range trên cùng 1 map, cùng 1 lần chạy chương trình, ra 2 thứ tự khác nhau ([a b c d e] và [b c d e a]) — không phải bug, mà đúng hành vi được thiết kế. Bài học thực dụng: không bao giờ dựa vào thứ tự duyệt map cho logic quan trọng; cần thứ tự ổn định thì lấy key ra sort.Strings()/sort.Ints() trước.

Chi phí hash: map[int]int vs map[string]int

Key kiểu string cần hash toàn bộ nội dung chuỗi mỗi lần truy cập/ghi — tốn hơn hash int (gần như tính trực tiếp từ giá trị số):

BenchmarkMapIntKey-10       187365606    6.201 ns/op    0 B/op    0 allocs/op
BenchmarkMapStringKey-10     77442252   14.810 ns/op    0 B/op    0 allocs/op

Lookup map[string]int chậm hơn ~2.4 lần map[int]int cho cùng 10.000 phần tử — hoàn toàn do chi phí hash chuỗi, không phải do cấu trúc map khác nhau (cả 2 dùng chung 1 implementation Swiss Table). Với hot path gọi map hàng triệu lần/giây, cân nhắc dùng key số (hoặc hash trước thành uint64) thay vì string khi có thể.

Resize: vì sao KHÔNG tạo ra 1 cú pause lớn

Giả thuyết tự nhiên: map tự động resize (rehash) khi đầy tới ngưỡng, và thao tác đó tốn kém, thể hiện qua độ trễ tăng đột biến tại 1 số kích thước nhất định. Đo trực tiếp độ trễ của từng lần insert đơn lẻ ngay tại các mốc map tăng gấp đôi kích thước:

m := make(map[int]int) // không preallocate, để tự grow
for i := 0; i < 10000; i++ {
    start := time.Now()
    m[i] = i
    elapsed := time.Since(start)
    // ghi lại elapsed tại các mốc 8, 16, 32... 8192
}
Sau     8 phần tử: insert thứ 8 mất 42ns
Sau    16 phần tử: insert thứ 16 mất 83ns
Sau    32 phần tử: insert thứ 32 mất 42ns
Sau    64 phần tử: insert thứ 64 mất 83ns
Sau   128 phần tử: insert thứ 128 mất 42ns
Sau   256 phần tử: insert thứ 256 mất 83ns
Sau   512 phần tử: insert thứ 512 mất 84ns
Sau  1024 phần tử: insert thứ 1024 mất 83ns
Sau  2048 phần tử: insert thứ 2048 mất 42ns
Sau  4096 phần tử: insert thứ 4096 mất 84ns
Sau  8192 phần tử: insert thứ 8192 mất 42ns

Không có cú pause lớn nào — chi phí mỗi lần insert dao động đều trong khoảng 42-84ns suốt từ 8 tới 8192 phần tử, kể cả đúng tại các mốc lẽ ra map phải “resize”. Điều này khớp chính xác với thiết kế đã đọc ở phần trên: Swiss Table trong Go dùng extendible hashing — map lớn được chia thành nhiều table nhỏ qua “directory”, mỗi lần grow chỉ rehash 1 table con (1 phần nhỏ của map), không phải toàn bộ map cùng lúc. Đây là lý do growth không tạo ra 1 cú pause đồng bộ lớn như hình dung “rehash toàn bộ map” thường thấy trong tài liệu cũ.

Nhưng chi phí grow vẫn có thật — đo qua tổng thời gian, không phải từng insert

Growth “rẻ” trên từng thao tác không có nghĩa là miễn phí toàn phần. So sánh tổng thời gian tạo map 10.000 phần tử, có preallocate capacity hay không:

// Không preallocate -- map tự grow nhiều lần trong lúc insert
m := make(map[int]int)

// Preallocate -- báo trước capacity, tránh phải grow lại nhiều lần
m := make(map[int]int, 10000)
BenchmarkMapNoPrealloc-10    3937    318329 ns/op    591485 B/op    79 allocs/op
BenchmarkMapPrealloc-10     12982     92106 ns/op    295554 B/op    33 allocs/op

Preallocate nhanh hơn ~3.5 lần (318329 / 92106), tốn ít hơn ~2 lần bộ nhớ (591485 → 295554 byte) và ít hơn ~2.4 lần số lần cấp phát (79 → 33 allocs/op). Chi phí grow tuy không tạo pause lớn ở từng thao tác đơn lẻ, nhưng cộng dồn qua nhiều lần grow (mỗi lần tăng gấp đôi kích thước bảng, kéo theo cấp phát + di chuyển dữ liệu) vẫn là chi phí thật — báo trước capacity qua tham số thứ 2 của make() khi biết trước quy mô luôn là tối ưu đáng làm.

Tự chạy lại demo

cd 05-map-internals
go run .
go vet ./...
go test -bench . -benchmem -run '^$'

main.go gộp 2 demo an toàn (random order, chi phí insert theo growth). hashcost_test.go và prealloc_test.go chứa các benchmark dùng cho 2 bảng số liệu ở trên. Demo crash concurrent map writes không nằm trong main.go vì cố ý gây crash — xem lại Concurrency bài 06 để tái hiện đầy đủ.

Tổng kết & bài tiếp theo

Go 1.24 thay hoàn toàn hmap/bmap cũ bằng thiết kế Swiss Table (group 8 slot + control word cho phép so khớp song song, extendible hashing chia map thành nhiều table nhỏ). Thứ tự duyệt map bị random hoá cố ý — không bao giờ nên phụ thuộc vào nó. Key string tốn hơn key số ~2.4 lần do chi phí hash. Nhờ extendible hashing, resize không tạo pause lớn ở từng thao tác, nhưng chi phí grow cộng dồn vẫn có thật — preallocate capacity khi biết trước quy mô giúp nhanh hơn ~3.5 lần.
