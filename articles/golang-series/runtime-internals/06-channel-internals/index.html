Concurrency bài 02 và bài 03 dùng channel và select như công cụ đồng bộ hoá. Bài này mở source code Go thật (runtime/chan.go, runtime/select.go) đứng sau make(chan T) để hiểu vì sao unbuffered channel đồng bộ hoá “đúng khoảnh khắc”, và select chọn case sẵn sàng như thế nào.

hchan: struct đứng sau mọi channel

Đọc thẳng runtime/chan.go:

type hchan struct {
    qcount   uint           // total data in the queue
    dataqsiz uint           // size of the circular queue
    buf      unsafe.Pointer // points to an array of dataqsiz elements
    elemsize uint16
    closed   uint32
    elemtype *_type // element type
    sendx    uint   // send index
    recvx    uint   // receive index
    recvq    waitq  // list of recv waiters
    sendq    waitq  // list of send waiters
    lock     mutex
}
  • buf/dataqsiz/sendx/recvx: ring buffer tuần hoàn — chỉ thật sự chứa dữ liệu nếu channel có buffer (make(chan T, n))
  • recvq/sendq: 2 hàng đợi kiểu waitq (danh sách liên kết sudog) — goroutine đang block chờ nhận/block chờ gửi
  • lock: 1 Mutex bảo vệ toàn bộ struct — mọi thao tác gửi/nhận/đóng đều phải giành lock này trước

sudog: goroutine “xếp hàng” trên channel

runtime/runtime2.go định nghĩa sudog — đại diện cho 1 goroutine đang chờ trên 1 channel (hoặc trong select):

type sudog struct {
    g    *g
    next *sudog
    prev *sudog
    elem unsafe.Pointer // data element (may point to stack)
    isSelect bool        // g đang tham gia select
    success  bool        // giao tiếp có thành công không
    // ...
}

Khi 1 goroutine gọi ch <- v mà chưa ai nhận (hoặc buffer đầy), nó tạo 1 sudog gắn elem trỏ tới giá trị cần gửi (đang nằm trên chính stack của nó — liên hệ bài 02), đẩy vào sendq, rồi tự block.

sendDirect/recvDirect: handoff trực tiếp, không qua buffer

Khi có goroutine gọi <-ch và sendq đã có sudog đang chờ, runtime copy giá trị trực tiếp từ stack goroutine gửi sang stack/heap của goroutine nhận — bỏ qua buffer hoàn toàn. Đọc thẳng runtime/chan.go:

func sendDirect(t *_type, sg *sudog, src unsafe.Pointer) {
    // src is on our stack, dst is a slot on another stack.
    dst := sg.elem
    typeBitsBulkBarrier(t, uintptr(dst), uintptr(src), t.Size_)
    memmove(dst, src, t.Size_)
}

Comment src is on our stack, dst is a slot on another stack xác nhận chính xác cơ chế: đây là lý do đã quan sát ở Concurrency bài 02 — 2 dòng log gửi/nhận trên unbuffered channel có cùng timestamp, không phải trùng hợp, mà vì memmove copy trực tiếp giữa 2 stack, đánh thức goroutine gửi ngay sau đó. Việc đọc sg.elem phải xảy ra trước khi có bất kỳ điểm preemption nào — comment gốc còn cảnh báo rõ: nếu stack đích bị co lại (shrink, bài 02) đúng lúc đó, sg.elem sẽ không được cập nhật kịp — 1 chi tiết đồng bộ hoá tinh vi giữa 2 cơ chế runtime tưởng như không liên quan.

select: pollorder ngẫu nhiên hoá — bằng chứng thật

runtime/select.go xáo trộn thứ tự kiểm tra các case trước khi vào vòng lặp chính:

j := cheaprandn(uint32(norder + 1))
pollorder[norder] = pollorder[j]
pollorder[j] = uint16(i)

Đây là 1 phép hoán vị Fisher-Yates dùng random nguồn rẻ (cheaprandn) — đảm bảo khi nhiều case cùng sẵn sàng, không case nào luôn được ưu tiên. Kiểm chứng thật: tạo 3 channel buffer đều có sẵn giá trị (luôn sẵn sàng cùng lúc), chạy select 100.000 lần:

select {
case <-ch1:
    counts["ch1"]++
case <-ch2:
    counts["ch2"]++
case <-ch3:
    counts["ch3"]++
}
Cả 3 channel LUÔN sẵn sàng cùng lúc, chạy 100000 lần select:
  ch1 được chọn: 33356 lần
  ch2 được chọn: 33312 lần
  ch3 được chọn: 33332 lần

Gần như chia đều tuyệt đối 3 case (33356/33312/33332, mỗi case ~33.33%) — nếu select luôn ưu tiên case khai báo đầu tiên (1 lỗi thiết kế dễ mắc phải khi tự viết multiplexer thủ công), ch1 sẽ luôn thắng 100% thay vì ~33%. Số liệu này là bằng chứng trực tiếp cho đoạn code cheaprandn vừa đọc ở trên.

Buffered vs unbuffered: chênh lệch latency thật

Buffered còn chỗ trống thì ghi thẳng vào ring buffer, không cần tạo sudog, không cần đánh thức ai — nhanh hơn hẳn so với unbuffered (luôn cần handoff qua sudog):

BenchmarkUnbufferedChan-10    7470364    142.1 ns/op    0 B/op    0 allocs/op
BenchmarkBufferedChan-10     27875994     42.29 ns/op    0 B/op    0 allocs/op

Buffered nhanh hơn ~3.4 lần (142.1 / 42.29) cho cùng thao tác gửi trong benchmark có 1 goroutine tiêu thụ liên tục ở nền — đúng như dự đoán từ cấu trúc hchan: unbuffered luôn cần tạo sudog + sendDirect/recvDirect + đánh thức goroutine kia; buffered (còn chỗ trống) chỉ cần ghi vào mảng buf và tăng sendx, không chạm tới cơ chế sudog nào.

Tự chạy lại demo

cd 06-channel-internals
go run .
go vet ./...
go test -bench . -benchmem -run '^$'

main.go chạy demo phân phối case của select. latency_test.go chứa 2 benchmark dùng cho số liệu buffered/unbuffered ở trên.

Tổng kết & bài tiếp theo

hchan gồm ring buffer (cho buffered channel) + 2 hàng đợi sudog (sendq/recvq) + 1 lock bảo vệ toàn bộ. Unbuffered channel luôn cần handoff trực tiếp qua sendDirect/recvDirect (copy thẳng giữa 2 stack goroutine); buffered dùng ring buffer khi còn chỗ, nhanh hơn hẳn vì bỏ qua toàn bộ cơ chế sudog. select xáo trộn thứ tự kiểm tra case bằng Fisher-Yates (cheaprandn) mỗi lần chạy — đảm bảo công bằng khi nhiều case cùng sẵn sàng, đã kiểm chứng qua 100.000 lần chạy thật.
