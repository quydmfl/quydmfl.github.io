Bài 01 học context như 1 khái niệm độc lập. Bài này xem nó xuất hiện tự nhiên thế nào trong net/http — gói I/O được dùng nhiều nhất trong code Go thực tế, và cũng là nơi vài mặc định nguy hiểm dễ bị bỏ qua.

http.Client mặc định: KHÔNG có timeout

srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    time.Sleep(1 * time.Second) // giả lập server chậm
    w.Write([]byte("OK"))
}))

resp, err := http.Get(srv.URL) // dùng http.DefaultClient
DefaultClient thành công sau: 1.003s (chờ đúng bằng server, không tự bỏ cuộc)
Client{Timeout: 300ms} kết thúc sau: 302ms | lỗi: Get "...": context deadline exceeded (Client.Timeout exceeded while awaiting headers)

http.Get/http.DefaultClient không đặt Timeout — request chờ đúng bằng thời gian server xử lý, dù là 1 giây hay treo vô thời hạn. Đây không phải bug, mà là thiết kế mặc định của net/http: an toàn cho script 1 lần chạy, nhưng nguy hiểm cho service production — 1 dependency downstream chậm hoặc treo có thể khiến toàn bộ goroutine xử lý request bị giữ lại vô thời hạn, dẫn tới cạn kiệt tài nguyên. Đặt Timeout tường minh trên http.Client trả về lỗi rõ ràng đúng thời điểm mong muốn — và thông báo lỗi thật (context deadline exceeded) lộ ra rằng Client.Timeout được cài đặt bằng chính context đã học ở bài 01, không phải cơ chế riêng biệt.

Mỗi *http.Request mang context riêng, huỷ khi client ngắt kết nối

srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    select {
    case <-r.Context().Done():
        fmt.Println("Server: phát hiện client đã ngắt kết nối, dừng xử lý sớm. Err:", r.Context().Err())
    case <-time.After(5 * time.Second):
        w.Write([]byte("OK"))
    }
}))

client := &http.Client{Timeout: 200 * time.Millisecond}
_, err := client.Get(srv.URL)
Server: phát hiện client đã ngắt kết nối, dừng xử lý sớm. Err: context canceled
Client: request kết thúc sau 202ms | lỗi: Get "...": context deadline exceeded (Client.Timeout exceeded while awaiting headers)

r.Context() trong http.Handler tự động Done() khi client ngắt kết nối giữa chừng — ở đây do client hết Timeout (200ms), server nhận ra qua r.Context().Err() == context.Canceled gần như ngay lập tức, thay vì tiếp tục xử lý (ở đây là time.After(5s)) cho 1 client không còn ở đó để nhận kết quả. Đây chính là kỹ thuật chuẩn để hàm xử lý dài hơi trong handler dừng sớm đúng lúc: select giữa công việc thật và r.Context().Done(), thay vì chạy mù tới khi xong bất kể client còn chờ hay không.

Transport và connection pooling

http.Transport (dùng ngầm bên trong http.Client) tự động tái sử dụng TCP connection đã thiết lập (HTTP keep-alive) cho các request tới cùng host — tránh lặp lại TCP handshake (và TLS handshake nếu HTTPS) cho mỗi request:

client := &http.Client{} // keep-alive mặc định BẬT

client := &http.Client{
    Transport: &http.Transport{DisableKeepAlives: true},
}
BenchmarkWithKeepAlive-10        28834     40658 ns/op     5031 B/op     62 allocs/op
BenchmarkWithoutKeepAlive-10     10000    121309 ns/op    16937 B/op    117 allocs/op

Tắt keep-alive khiến mỗi request chậm hơn ~3 lần (121309 / 40658), tốn nhiều hơn ~3.4 lần bộ nhớ và gần gấp đôi số lần cấp phát — hoàn toàn do chi phí thiết lập lại TCP connection mới cho từng request thay vì tái sử dụng connection đã mở. Trên production, gọi API tới cùng 1 service nhiều lần nên dùng chung 1 http.Client (không tạo mới mỗi lần gọi) để tận dụng đúng cơ chế pooling này.

Timeout phía server: ReadTimeout ngắt client gửi quá chậm

srv := &http.Server{
    ReadTimeout: 300 * time.Millisecond,
    Handler: http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        body, err := io.ReadAll(r.Body)
        fmt.Println("Handler: đọc được", len(body), "byte trước khi lỗi:", err)
    }),
}

Client cố tình gửi request rất chậm (1 byte mỗi 5ms qua raw TCP, giả lập client mạng yếu hoặc độc hại kiểu slowloris):

Handler: đọc được 54 byte trước khi lỗi: read tcp ...: i/o timeout
Client: ghi lỗi sau 310ms -- server đã đóng do ReadTimeout: write tcp ...: write: broken pipe

Đúng khoảng 300ms (khớp ReadTimeout đã đặt), server chủ động đóng kết nối — handler nhận lỗi i/o timeout khi đang đọc body dở dang (mới nhận 54/5006 byte), phía client thấy broken pipe khi cố ghi tiếp vào connection đã bị đóng. Không đặt ReadTimeout (mặc định là 0, tức vô hạn), 1 client gửi chậm hoặc cố tình treo kết nối có thể giữ 1 goroutine xử lý của server mở vô thời hạn — cùng dạng rủi ro với http.Client không có Timeout, nhưng ở phía ngược lại.

Tổng kết & bài tiếp theo

net/http không tự bảo vệ khỏi kết nối chậm/treo ở cả 2 phía — http.Client.Timeout và http.Server.ReadTimeout/WriteTimeout đều mặc định là vô hạn, cần đặt tường minh. Bên dưới, Client.Timeout chính là 1 lớp context bọc quanh request; mỗi *http.Request nhận r.Context() riêng tự huỷ khi client ngắt kết nối, cho phép handler dừng sớm việc không còn ai chờ kết quả. http.Transport tái sử dụng TCP connection qua keep-alive — dùng chung 1 http.Client cho các lần gọi lặp lại nhanh hơn ~3 lần so với tạo client mới (hoặc tắt keep-alive) mỗi lần.

Tự chạy lại demo

cd 02-net-http-internals
go run .
go vet ./...
go test -bench . -benchmem -run '^$'

main.go gộp 3 demo (client timeout, request context, server ReadTimeout). keepalive_test.go chứa 2 benchmark dùng cho số liệu connection pooling ở trên.
