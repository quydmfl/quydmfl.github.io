Series đã dùng go test, go vet, benchmark xuyên suốt từ Fundamentals tới Standard Library — bài này quay lại đào sâu chính công cụ đó: table-driven test, subtests, và đặc biệt là fuzzing, kỹ thuật tìm bug tự động mạnh nhất trong toolchain Go chuẩn.

Table-driven test: pattern chuẩn của Go

func TestAdd(t *testing.T) {
    cases := []struct {
        name string
        a, b int
        want int
    }{
        {"hai số dương", 2, 3, 5},
        {"số âm", -1, -1, -2},
        {"cộng 0", 5, 0, 5},
    }
    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            got := Add(tc.a, tc.b)
            if got != tc.want {
                t.Errorf("Add(%d, %d) = %d, muốn %d", tc.a, tc.b, got, tc.want)
            }
        })
    }
}

Thêm 1 case cố tình sai ({"cố tình sai để xem output", 2, 2, 5}) để xem go test báo lỗi ra sao:

=== RUN   TestAdd/số_âm

    table_test.go:25: Add(2, 2) = 4, muốn 5

Mỗi case chạy như 1 subtest độc lập qua t.Run — case sai (cố_tình_sai_để_xem_output) fail rõ ràng, 3 case còn lại vẫn PASS bình thường, không bị kéo theo. Muốn debug đúng 1 case, chạy riêng qua tên đầy đủ:

go test -run 'TestAdd/số_âm' -v
=== RUN   TestAdd
=== RUN   TestAdd/số_âm
--- PASS: TestAdd (0.00s)
    --- PASS: TestAdd/số_âm (0.00s)

go test -fuzz: tìm bug thật mà test thủ công không nghĩ tới

Viết 1 hàm Reverse đảo ngược chuỗi — phiên bản đầu tiên xử lý theo byte, không phải rune (ký tự):

// PHIÊN BẢN CÓ BUG -- xử lý theo byte
func Reverse(s string) string {
    b := []byte(s)
    for i, j := 0, len(b)-1; i < j; i, j = i+1, j-1 {
        b[i], b[j] = b[j], b[i]
    }
    return string(b)
}

Viết fuzz test kiểm tra bất biến hợp lý: đảo ngược 1 chuỗi UTF-8 hợp lệ phải cho ra chuỗi UTF-8 hợp lệ:

func FuzzReverse(f *testing.F) {
    f.Add("hello")
    f.Add("")
    f.Fuzz(func(t *testing.T, s string) {
        if !utf8.ValidString(s) {
            return
        }
        rev := Reverse(s)
        if !utf8.ValidString(rev) {
            t.Errorf("Reverse(%q) = %q -- không còn là UTF-8 hợp lệ", s, rev)
        }
    })
}

Chưa đầy 1 giây, fuzzer tự sinh input (ký tự Hebrew U+05F5, 2 byte trong UTF-8) làm lộ đúng bug: đảo ngược ở tầng byte tách rời 2 byte của 1 ký tự multi-byte, đảo ngược thứ tự của chúng, tạo ra chuỗi byte không còn hợp lệ UTF-8. Input gây lỗi được tự động lưu lại vào testdata/fuzz/FuzzReverse/ — trở thành 1 test case cố định (corpus), chạy lại mọi lần go test sau này như 1 unit test bình thường, không cần fuzz lại từ đầu:

go test -run=FuzzReverse/0e292dfe19cd3731 -v
=== RUN   FuzzReverse
=== RUN   FuzzReverse/0e292dfe19cd3731
    reverse_test.go:17: Reverse(U+05F5) = "\xb5\xd7" -- không còn là UTF-8 hợp lệ
--- FAIL: FuzzReverse (0.00s)

Sửa bằng cách đảo theo rune thay vì byte — đúng phiên bản đang nằm trong main.go của bài viết:

func Reverse(s string) string {
    r := []rune(s)
    for i, j := 0, len(r)-1; i < j; i, j = i+1, j-1 {
        r[i], r[j] = r[j], r[i]
    }
    return string(r)
}
go test -run=FuzzReverse/0e292dfe19cd3731 -v   # case cũ giờ pass
go test -fuzz FuzzReverse -fuzztime 30s        # fuzz lại, không tìm thấy lỗi nào nữa
--- PASS: FuzzReverse (0.00s)
    --- PASS: FuzzReverse/0e292dfe19cd3731 (0.00s)
fuzz: elapsed: 30s, execs: 11890000+ (390000+/sec), new interesting: 37 (total: 37)
PASS

Hơn 11 triệu lần thực thi, không còn input nào làm lộ bug — mức độ kiểm chứng mà viết test case thủ công gần như không thể đạt tới trong cùng khoảng thời gian.

t.Parallel(): chạy song song, và race thật giữa các subtest

t.Parallel() trong subtest không chạy ngay — nó báo cho framework “tạm dừng tôi, chạy tôi cùng lúc với các subtest Parallel khác sau khi hàm test cha return”:

var sharedCounter int // package-level, dùng CHUNG giữa các subtest -- KHÔNG khoá

func TestParallelRace(t *testing.T) {
    for _, name := range []string{"a", "b", "c", "d", "e"} {
        t.Run(name, func(t *testing.T) {
            t.Parallel()
            sharedCounter++ // race thật: nhiều subtest cùng ghi 1 biến chung
        })
    }
}
go test -race -v
=== RUN   TestParallelRace/a
=== PAUSE TestParallelRace/a
=== RUN   TestParallelRace/b
=== PAUSE TestParallelRace/b
...
=== CONT  TestParallelRace/a
=== CONT  TestParallelRace/c
=== CONT  TestParallelRace/b
=== CONT  TestParallelRace/e
=== CONT  TestParallelRace/d
==================
WARNING: DATA RACE
Read at 0x000104b60380 by goroutine 9:
  command-line-arguments.TestParallelRace.func1()
...
--- FAIL: TestParallelRace (0.00s)

Log PAUSE rồi CONT xác nhận đúng cơ chế: cả 5 subtest bị hoãn lại, rồi chạy đồng thời (CONT liên tiếp) — đúng lúc đó sharedCounter++ từ nhiều goroutine race với nhau, -race bắt được ngay. Sửa bằng sync/atomic (xem Runtime Internals bài 06 cho các lựa chọn đồng bộ hoá khác):

var sharedCounter int64
atomic.AddInt64(&sharedCounter, 1)

Chạy lại -race: sạch hoàn toàn, cả 5 subtest PASS. Bài học: t.Parallel() tăng tốc test suite lớn, nhưng biến package-level dùng chung giữa các subtest phải được đồng bộ hoá y hệt code production — -race trong CI cho test suite cũng quan trọng không kém -race cho code chính.

testing.B nội bộ: b.ResetTimer() quan trọng thế nào

func expensiveSetup() {
    time.Sleep(50 * time.Millisecond) // giả lập setup tốn kém, chỉ nên chạy 1 lần
}

func BenchmarkWithoutResetTimer(b *testing.B) {
    expensiveSetup() // tính luôn vào thời gian đo -- SAI
    for i := 0; i < b.N; i++ {
        _ = i * i
    }
}

func BenchmarkWithResetTimer(b *testing.B) {
    expensiveSetup()
    b.ResetTimer() // loại bỏ thời gian setup khỏi kết quả đo
    for i := 0; i < b.N; i++ {
        _ = i * i
    }
}
BenchmarkWithoutResetTimer-10    3    17016611 ns/op
BenchmarkWithResetTimer-10       3         250.0 ns/op

Chênh lệch ~68.000 lần — không phải vì code khác nhau (cả 2 chạy đúng 1 phép nhân trong loop), mà vì expensiveSetup() (50ms sleep) bị tính lẫn vào kết quả đo ở phiên bản đầu. b.N không cố định — framework Go tự chạy hàm benchmark nhiều lần với b.N tăng dần (1, rồi tăng theo cấp số nhân) tới khi tổng thời gian đo đủ lớn để có kết quả ổn định; với b.N nhỏ (ở đây là 3, do giới hạn -benchtime=3x trong demo), chi phí setup 1 lần chiếm áp đảo toàn bộ phép chia trung bình. b.ResetTimer() đặt lại đồng hồ đo về 0 ngay tại điểm gọi — chỉ nên đặt sau mọi bước chuẩn bị (tạo dữ liệu mẫu, mở file, warm-up cache) và trước vòng lặp thực sự muốn đo.

Tự chạy lại demo

cd 05-testing-package
go run .
go vet ./...
go test -race -v -run 'TestAdd|TestParallelFixed'
go test -fuzz FuzzReverse -fuzztime 30s
go test -bench . -benchtime=3x -run '^$'

main.go chứa Add/Reverse (bản đã sửa, dùng rune) làm đối tượng test. table_test.go/fuzz_test.go/parallel_test.go/bn_test.go chứa các demo tương ứng — tất cả đều pass sạch bao gồm cả -race, vì đây là phiên bản đã sửa của mọi bug đã trình bày ở trên. Case sai cố ý (TestAdd), bug đảo chuỗi theo byte (Reverse gốc), và race giữa parallel subtest (sharedCounter không khoá) chỉ xuất hiện trong đoạn code minh hoạ ở bài viết, không nằm trong code đã ship.

Tổng kết & bài tiếp theo

Table-driven test + t.Run là pattern chuẩn cho phép chạy/debug từng case độc lập. go test -fuzz tìm ra bug UTF-8 thật chỉ trong chưa đầy 1 giây — thứ viết test case thủ công khó nghĩ tới, và tự động lưu lại thành regression test cố định. t.Parallel() tăng tốc test suite nhưng đòi hỏi đồng bộ hoá đúng như code production — -race áp dụng được cho cả test. b.ResetTimer() không phải chi tiết vặt: bỏ qua nó có thể làm sai lệch kết quả benchmark tới hàng chục nghìn lần.
