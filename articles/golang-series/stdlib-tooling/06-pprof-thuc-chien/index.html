Runtime Internals bài 03 đã dùng pprof để xem heap profile. Bài này đi sâu thành quy trình chẩn đoán đầy đủ: gắn pprof vào 1 HTTP server thật, cố tình cài 3 vấn đề hiệu năng khác nhau, rồi dùng pprof tìm ra chính xác từng vấn đề.

net/http/pprof: 1 dòng import, có ngay endpoint profiling

import _ "net/http/pprof" // side-effect import: tự đăng ký /debug/pprof/* vào DefaultServeMux

Chỉ cần import với tên _ (chỉ chạy side-effect, không dùng trực tiếp symbol nào) — package này tự đăng ký các endpoint /debug/pprof/* vào http.DefaultServeMux thông qua init(). Không cần viết thêm route nào, miễn là server dùng http.ListenAndServe(addr, nil) (dùng DefaultServeMux).

CPU profile: tìm hot path thật — 70% thời gian nằm ở 1 dòng code

Cài 1 hàm kiểm tra số nguyên tố cố tình chậm (thuật toán ngây thơ, chạy hết tới n thay vì dừng ở sqrt(n)):

func isPrimeSlow(n int) bool {
    if n < 2 {
        return false
    }
    for i := 2; i < n; i++ { // chậm: lẽ ra chỉ cần chạy tới sqrt(n)
        if n%i == 0 {
            return false
        }
    }
    return true
}

Fire load liên tục vào handler này trong 3 giây, đồng thời chụp CPU profile:

go tool pprof -top -nodecount 6 "http://127.0.0.1:16060/debug/pprof/profile?seconds=3"
Duration: 3.11s, Total samples = 2.73s (87.92%)
Showing nodes accounting for 2.72s, 99.63% of 2.73s total
      flat  flat%   sum%        cum   cum%
     1.92s 70.33% 70.33%      1.92s 70.33%  main.isPrimeSlow
     0.70s 25.64% 95.97%      0.70s 25.64%  syscall.syscall
     0.04s  1.47% 97.44%      0.04s  1.47%  runtime.pthread_cond_signal

isPrimeSlow chiếm 70.33% tổng CPU time — đúng hàm cố tình cài chậm. go tool pprof -list zoom sâu hơn, chỉ ra chính xác dòng code nào tốn nhất:

go tool pprof -list=isPrimeSlow <profile.gz>
ROUTINE ======================== main.isPrimeSlow in main.go
     1.92s      1.92s (flat, cum) 70.33% of Total
         .          .     18:	if n < 2 {
     160ms      160ms     21:	for i := 2; i < n; i++ { // chậm: lẽ ra chỉ cần chạy tới sqrt(n)
     1.76s      1.76s     22:		if n%i == 0 {

Dòng if n%i == 0 một mình chiếm 1.76s trong tổng 1.92s của hàm — phép chia lấy dư chạy lặp lại hàng triệu lần do vòng lặp không dừng sớm ở sqrt(n). Đây chính xác là cách chẩn đoán “dòng code nào tốn CPU nhất” trên 1 service Go thật, không cần đoán mò hay đọc code bằng mắt.

Heap profile: tìm hàm cấp phát nhiều nhất

Cài 1 handler cấp phát thừa mỗi lần gọi (không tái sử dụng, liên hệ Runtime Internals bài 04 về sync.Pool):

type Payload struct{ Data [1024]byte }

func allocHandler(w http.ResponseWriter, r *http.Request) {
    var items []*Payload
    for i := 0; i < 5000; i++ {
        items = append(items, &Payload{})
    }
    fmt.Fprintf(w, "Đã cấp phát %d item\n", len(items))
}
go tool pprof -top -alloc_space -nodecount 5 "http://127.0.0.1:16060/debug/pprof/heap"
Showing nodes accounting for 528.98MB, 97.05% of 545.05MB total
      flat  flat%   sum%        cum   cum%
  516.94MB 94.84% 94.84%   518.44MB 95.12%  main.allocHandler
    5.02MB  0.92% 95.76%     5.02MB  0.92%  bufio.NewWriterSize (inline)

main.allocHandler chiếm 94.84% tổng lượng cấp phát của cả chương trình sau khi fire 100 request — không có gì bất ngờ ở đây (đây là handler duy nhất cấp phát nhiều), nhưng trên 1 service thật với hàng chục handler, đây chính xác là cách tìm ra đúng handler nào đang gây áp lực GC mà không cần đoán.

Goroutine profile: phát hiện leak thật — và cách nó lách qua go vet

Liên hệ bài 01: quên gọi cancel() là goroutine leak thật. Nhưng có 1 cách code “qua mặt” go vet mà vẫn leak:

func leakHandler(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithCancel(context.Background())
    _ = cancel // "che" cảnh báo lostcancel của go vet nhưng vẫn leak thật
    go func() { <-ctx.Done() }()
    fmt.Fprintf(w, "leaked\n")
}

go vet ./... chạy trên đoạn code này hoàn toàn im lặng — check lostcancel chỉ xác minh biến cancel có được tham chiếu ở đâu đó trong hàm hay không, không xác minh nó có thực sự được gọi. _ = cancel đủ để “thoả mãn” vet trong khi hàm cancel chưa từng chạy — 1 giới hạn thật của phân tích tĩnh, không phải lỗi của công cụ (phát hiện “hàm này có được gọi trong mọi nhánh thực thi hay không” khó hơn hẳn “biến này có được nhắc tới hay không”).

Đây là lý do giám sát runtime (qua pprof) vẫn cần thiết dù đã có go vet — vet chỉ bắt được lỗi ở tầng cú pháp/kiểu dữ liệu, không bắt được logic sai tinh vi kiểu này:

go tool pprof http://127.0.0.1:16060/debug/pprof/goroutine?debug=1
goroutine profile: total 36
30 @ 0x102661d88 0x1025fc55c 0x1025fc0f4 0x10284bb00 0x102669ca4
#	0x10284baff	main.leakHandler.func1+0x2f	main.go:62

Fire đúng 30 request vào /leak, endpoint goroutine báo cáo đúng 30 goroutine đang kẹt tại main.leakHandler.func1 (dòng <-ctx.Done()) — không tăng thêm khi không có request mới, và tăng đúng bằng số request khi fire thêm. Trên production, endpoint này (thường bảo vệ sau xác thực, không public ra internet) là công cụ đầu tiên nên kiểm tra khi nghi ngờ leak: số lượng goroutine cùng 1 stack trace tăng dần theo thời gian, không giảm, là dấu hiệu gần như chắc chắn.

go tool pprof interactive: đọc đúng flat vs cum

2 cột dễ nhầm nhất trong mọi bảng top ở trên: flat là thời gian/bộ nhớ tiêu tốn trong chính hàm đó (không tính hàm nó gọi); cum (cumulative) là tổng cộng dồn cả những hàm nó gọi tới. Ở bảng CPU profile trên, main.slowHandler không xuất hiện trong top 6 vì flat của nó gần như 0 (bản thân handler chỉ gọi isPrimeSlow trong loop, không làm gì tốn CPU trực tiếp) — nhưng cum của nó bằng gần như toàn bộ 70%+ vì đó là tổng thời gian của mọi hàm nó gọi tới. Nhầm giữa 2 cột dễ dẫn tới kết luận sai “handler này không tốn gì” trong khi thực tế toàn bộ chi phí nằm ở hàm nó gọi.

Tự chạy lại demo

cd 06-pprof-thuc-chien
go run .
go vet ./...

main.go tự động hoá toàn bộ quy trình trong 1 lần go run .: khởi động HTTP server với pprof, fire load vào từng handler, rồi tự gọi go tool pprof (qua os/exec) để in kết quả — không cần mở 2 terminal riêng để vừa chạy server vừa chạy client như khi thao tác thủ công.

Tổng kết & bài tiếp theo

net/http/pprof chỉ cần 1 dòng import để có ngay 3 loại profile quan trọng nhất: CPU (tìm hot path, chính xác tới từng dòng qua -list), heap (tìm hàm cấp phát nhiều nhất), và goroutine (phát hiện leak qua số lượng cùng 1 stack trace tăng dần). go vet bắt được nhiều lỗi tĩnh nhưng có giới hạn thật — _ = cancel đủ để qua mặt check lostcancel trong khi bug vẫn còn nguyên, khẳng định giám sát runtime qua pprof là lớp phòng thủ không thể thay thế.
