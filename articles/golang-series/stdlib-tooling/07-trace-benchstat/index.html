go tool trace: thấy trực tiếp scheduler hoạt động

runtime/trace ghi lại toàn bộ sự kiện scheduler (goroutine start/stop/block, GC, syscall) vào 1 file nhị phân, mở bằng giao diện trực quan trên trình duyệt:

f, _ := os.Create("trace.out")
trace.Start(f)
defer trace.Stop()

var wg sync.WaitGroup
for i := 0; i < 20; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        cpuBurn(50 * time.Millisecond) // đốt CPU 50ms mỗi goroutine
    }()
}
wg.Wait()
go tool trace trace.out   # mở UI trực quan trên trình duyệt

Đây chính là kịch bản GOMAXPROCS đã dùng ở Runtime Internals bài 01 (đo bằng GODEBUG=schedtrace lúc đó) — lần này quan sát qua giao diện timeline theo từng P, thấy trực tiếp goroutine nào chạy trên P nào, khi nào 1 P rảnh “cướp” goroutine từ P khác (work stealing).

Trích xuất dữ liệu dạng văn bản: -pprof=sync

Ngoài giao diện trình duyệt, go tool trace -pprof=<type> xuất 1 profile dạng pprof thuần văn bản — hữu ích để phân tích không cần mở UI, hoặc nhúng vào script CI:

go tool trace -pprof=sync trace.out > sync.pprof
go tool pprof -top -nodecount 8 sync.pprof
Type: delay
Showing nodes accounting for 98.74ms, 100% of 98.74ms total
      flat  flat%   sum%        cum   cum%
   98.74ms   100%   100%    98.74ms   100%  sync.(*WaitGroup).Wait
         0     0%   100%    98.74ms   100%  main.demoTrace

sync.(*WaitGroup).Wait chiếm 98.74ms — main goroutine block đúng bằng khoảng đó chờ tất cả 20 goroutine hoàn tất. Con số này khớp gần đúng lý thuyết: máy demo có GOMAXPROCS=10 (bài 01), 20 goroutine burn CPU 50ms mỗi cái cần 2 đợt (10 goroutine chạy song song đợt 1, 10 goroutine còn lại đợt 2) → tổng thời gian lý thuyết ≈ 2 × 50ms = 100ms — số đo thật 98.74ms khớp sát, xác nhận đúng hành vi GMP đã mô tả lý thuyết ở bài 01, lần này nhìn qua góc độ “thời gian block” thay vì “số P/G/M”.

benchstat: so sánh benchmark có ý nghĩa thống kê

go test -bench . -count=10 chạy lặp lại benchmark 10 lần (giảm nhiễu đo lường của 1 lần chạy đơn lẻ). benchstat old.txt new.txt so sánh 2 tập kết quả, báo cáo % chênh lệch kèm p-value — xác nhận cải thiện có ý nghĩa thống kê, không phải ăn may 1 lần đo:

go install golang.org/x/perf/cmd/benchstat@latest

Lấy lại đúng kịch bản sync.Pool từ Runtime Internals bài 04: 1 benchmark cùng tên BenchmarkBufferReuse, 2 phiên bản (build tag old/mặc định) để benchstat so sánh đúng theo tên:

go test -tags old -bench . -benchmem -count=10 > old.txt   # bản không tái sử dụng buffer
go test -bench . -benchmem -count=10 > new.txt             # bản dùng sync.Pool
benchstat old.txt new.txt
               │   old.txt    │               new.txt               │
               │    sec/op    │   sec/op     vs base                │
BufferReuse-10   2177.8µ ± 3%   107.0µ ± 8%  -95.09% (p=0.000 n=10)

               │    old.txt     │               new.txt                │
               │      B/op      │     B/op      vs base                │
BufferReuse-10   20000.2Ki ± 0%   117.2Ki ± 0%  -99.41% (p=0.000 n=10)

               │   old.txt   │              new.txt               │
               │  allocs/op  │  allocs/op   vs base               │
BufferReuse-10   5.002k ± 0%   5.000k ± 0%  -0.04% (p=0.000 n=10)

-95.09% thời gian, -99.41% bộ nhớ — cả 2 đều có p=0.000, nghĩa là khả năng chênh lệch này chỉ do ngẫu nhiên gần như bằng 0. ± 3%/± 8% là độ biến thiên giữa 10 lần chạy — benchstat tự tính median và mức dao động, không chỉ đơn giản lấy trung bình 1 lần chạy như đọc trực tiếp output go test -bench.

Khi nào 1 kết quả benchmark là nhiễu, không phải cải thiện thật

So sánh 2 lần chạy cùng 1 phiên bản code (không có thay đổi thật nào) để xem benchstat phản ứng ra sao:

go test -bench . -benchmem -count=10 > new2.txt
benchstat new.txt new2.txt
               │   new.txt   │           new2.txt            │
               │   sec/op    │   sec/op     vs base          │
BufferReuse-10   107.0µ ± 8%   105.5µ ± 4%  ~ (p=0.579 n=10)

Dấu ~ thay vì phần trăm, cùng p=0.579 (rất cao, gần 0.5 — tương đương “tung đồng xu”) — benchstat tự nhận ra chênh lệch 107.0µ vs 105.5µ không đủ ý nghĩa thống kê để kết luận có cải thiện thật, dù con số tuyệt đối trông có vẻ khác nhau. Đây chính là bẫy phổ biến khi đọc benchmark bằng mắt: nhìn 2 con số chạy 1 lần rồi kết luận “nhanh hơn” hoặc “chậm hơn” là không đủ căn cứ — dao động tự nhiên giữa các lần chạy (do tải máy nền, thermal throttling, lịch trình OS…) hoàn toàn có thể tạo ra chênh lệch trông giống thật. Quy tắc thực dụng: bất kỳ khẳng định “tối ưu X nhanh hơn Y%” nào cũng nên đi kèm benchstat với p đủ nhỏ (thường < 0.05), không phải 1 lần go test -bench chạy suông.

Tự chạy lại demo

cd 07-trace-benchstat
go run .                                          # ghi trace.out
go vet ./...
go tool trace -pprof=sync trace.out | go tool pprof -top -nodecount 8 -

go install golang.org/x/perf/cmd/benchstat@latest
go test -tags old -bench . -benchmem -count=10 > old.txt
go test -bench . -benchmem -count=10 > new.txt
benchstat old.txt new.txt

main.go tạo trace.out từ kịch bản 20 goroutine CPU-bound. pool_old_test.go (build tag old) và pool_new_test.go (mặc định) chứa 2 phiên bản cùng tên BenchmarkBufferReuse để benchstat so sánh đúng cặp.

Tổng kết mini-series & bài tiếp theo

go tool trace cho thấy trực tiếp scheduler hoạt động qua timeline (hoặc trích xuất dạng văn bản qua -pprof) — nối lại lý thuyết GMP đã học ở Runtime Internals bằng dữ liệu thời gian thực. benchstat biến benchmark từ “nhìn 2 con số đoán” thành kết luận có căn cứ thống kê — phân biệt rõ cải thiện thật (p=0.000) với nhiễu đo lường (p=0.579, ký hiệu ~).
