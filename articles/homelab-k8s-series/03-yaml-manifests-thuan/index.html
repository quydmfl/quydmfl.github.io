Trước khi dùng Helm (bài 04) hay Terraform (bài 05), viết tay 1 lần đầy đủ 3 manifest nền tảng nhất — để hiểu chính xác những gì công cụ trừu tượng hoá sẽ làm thay sau này.

Deployment: pod template, replica, và ReplicaSet phía sau

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
  namespace: demo-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
        - name: web-app
          image: nginxdemos/hello:plain-text
          ports:
            - containerPort: 80
          resources:
            requests: {cpu: "50m", memory: "32Mi"}
            limits: {cpu: "100m", memory: "64Mi"}
kubectl create namespace demo-app
kubectl apply -f deployment.yaml
kubectl get deployment,pods -n demo-app
NAME                      READY   UP-TO-DATE   AVAILABLE
deployment.apps/web-app   3/3     3            3

NAME                           READY   STATUS    NODE
pod/web-app-5d54bb4d86-ghnxh   1/1     Running   homelab-worker2
pod/web-app-5d54bb4d86-jbfbw   1/1     Running   homelab-worker
pod/web-app-5d54bb4d86-pgnvn   1/1     Running   homelab-worker2

Deployment không trực tiếp quản lý Pod — nó tạo và quản lý 1 ReplicaSet, ReplicaSet mới thực sự tạo/xoá Pod theo replicas khai báo. Scheduler tự rải Pod qua các worker node (homelab-worker/homelab-worker2), không cần chỉ định tay.

Scale: thay đổi replicas, quan sát Pod tạo/xoá theo thời gian thật

kubectl scale deployment web-app -n demo-app --replicas=5
kubectl get pods -n demo-app
NAME                       READY   STATUS    AGE
web-app-5d54bb4d86-2jv5x   1/1     Running   5s
web-app-5d54bb4d86-ghnxh   1/1     Running   30s
web-app-5d54bb4d86-jbfbw   1/1     Running   30s
web-app-5d54bb4d86-lh672   1/1     Running   5s
web-app-5d54bb4d86-pgnvn   1/1     Running   30s

Đúng 2 Pod mới (AGE: 5s) được tạo thêm, 3 Pod cũ (AGE: 30s) giữ nguyên — ReplicaSet chỉ tạo/xoá phần chênh lệch, không tạo lại từ đầu. Scale xuống lại giữ đúng những Pod cũ nhất.

Rolling update thật: đổi image, quan sát chuyển đổi từng bước

kubectl set image deployment/web-app web-app=nginxdemos/hello:latest -n demo-app
kubectl rollout status deployment/web-app -n demo-app
Waiting for deployment "web-app" rollout to finish: 1 out of 3 new replicas have been updated...
Waiting for deployment "web-app" rollout to finish: 2 out of 3 new replicas have been updated...
Waiting for deployment "web-app" rollout to finish: 1 old replicas are pending termination...
deployment "web-app" successfully rolled out

kubectl rollout status in ra đúng tiến trình thật — không phải log giả lập: cập nhật lần lượt 1, rồi 2 trong 3 Pod, sau đó chờ Pod cũ cuối cùng bị dọn. Đây là chiến lược RollingUpdate mặc định — không bao giờ có lúc tất cả Pod đều Terminating cùng lúc, luôn giữ ít nhất vài Pod phục vụ request trong lúc chuyển đổi.

kubectl rollout undo quay lại đúng version trước:

kubectl rollout undo deployment/web-app -n demo-app
Warning: resource deployments/web-app was previously managed with 'kubectl apply'. Rolling back will not update the kubectl.kubernetes.io/last-applied-configuration annotation, which may cause unexpected behavior on future 'kubectl apply' operations. Consider using 'kubectl apply' with your previous configuration file instead.
deployment.apps/web-app rolled back
...
deployment "web-app" successfully rolled out

Cảnh báo thật đáng nhớ: rollout undo và apply theo dõi lịch sử theo 2 cơ chế khác nhau (ReplicaSet revision vs annotation last-applied-configuration) — dùng undo xong quay lại apply file YAML cũ có thể tạo lệch trạng thái. Xác nhận rollback đúng bằng cách nhìn lại 2 ReplicaSet cùng tồn tại (Deployment giữ lại ReplicaSet cũ, chỉ set replicas: 0, để rollout undo khôi phục nhanh):

kubectl get replicasets -n demo-app
NAME                      DESIRED   CURRENT   READY
web-app-59bdc8d7dc        0         0         0
web-app-5d54bb4d86        3         3         3

web-app-59bdc8d7dc (image latest) còn DESIRED: 0 — vẫn tồn tại làm lịch sử, web-app-5d54bb4d86 (image plain-text, đã rollback về) đang chạy đủ 3.

Service: ClusterIP — DNS nội bộ và load balancing thật

apiVersion: v1
kind: Service
metadata:
  name: web-app-svc
  namespace: demo-app
spec:
  type: ClusterIP
  selector:
    app: web-app
  ports:
    - port: 80
      targetPort: 80
kubectl apply -f service-clusterip.yaml
kubectl get endpoints web-app-svc -n demo-app
NAME          ENDPOINTS
web-app-svc   10.244.1.12:80,10.244.2.6:80,10.244.2.7:80

Service không “chứa” Pod — nó chỉ là 1 tập Endpoints (IP:port của mọi Pod khớp selector), Kubernetes tự động cập nhật danh sách này mỗi khi Pod đổi. Từ 1 Pod debug bên trong cluster, phân giải DNS nội bộ:

kubectl exec debug -- nslookup web-app-svc.demo-app.svc.cluster.local
Name:	web-app-svc.demo-app.svc.cluster.local
Address: 10.96.197.169

Gọi qua Service 5 lần liên tiếp, mỗi lần in ra tên Pod thực sự xử lý request (image nginxdemos/hello trả về Server name = hostname của Pod):

for i in 1 2 3 4 5; do
  kubectl exec debug -- wget -qO- http://web-app-svc/ | grep "Server name"
done
Server name: web-app-5d54bb4d86-dzx2x
Server name: web-app-5d54bb4d86-dzx2x
Server name: web-app-5d54bb4d86-jqs5j
Server name: web-app-5d54bb4d86-dzx2x
Server name: web-app-5d54bb4d86-8f8bk

Cả 3 Pod đều được gọi tới trong 5 lần — load balancing thật giữa các replica, hoàn toàn tự động, không cần code nào trong app biết về việc này.

Service: NodePort — mở port cố định, và giới hạn thật trên kind

apiVersion: v1
kind: Service
metadata:
  name: web-app-nodeport
  namespace: demo-app
spec:
  type: NodePort
  selector:
    app: web-app
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080

NodePort mở port 30080 trên mọi node, không chỉ node đang chạy Pod thật — xác nhận bằng cách gọi trực tiếp từ bên trong 2 node container khác nhau:

docker exec homelab-worker curl -s http://localhost:30080/ | grep "Server name"
docker exec homelab-worker2 curl -s http://localhost:30080/ | grep "Server name"
Server name: web-app-5d54bb4d86-8f8bk
Server name: web-app-5d54bb4d86-8f8bk

Cả 2 node đều trả lời được, dù Pod 8f8bk chỉ chạy trên 1 trong 2. Nhưng gọi thẳng từ máy host thì thất bại:

curl --max-time 3 http://localhost:30080/
curl: (7) Failed to connect to localhost port 30080

Đây là giới hạn thật của kind đã nhắc ở bài 01: port 30080 chỉ mở trong network namespace của các container node, kind không tự động map nó ra máy host trừ khi khai báo extraPortMappings ngay lúc tạo cluster. Cách nhanh nhất để test ngay không cần tạo lại cluster: kubectl port-forward:

kubectl port-forward -n demo-app svc/web-app-nodeport 18099:80 &
curl -s http://localhost:18099/ | grep "Server name"
Server name: web-app-5d54bb4d86-dzx2x

port-forward mở 1 đường hầm tạm thời qua chính kết nối kubectl tới API server — hoạt động bất kể kind có port mapping gì, tiện cho việc test nhanh, nhưng chỉ tồn tại trong lúc lệnh còn chạy, không dùng để “expose” service thật (khác hoàn toàn Ingress ở bài 07/Cloudflare Tunnel ở bài 08).

Ingress: khai báo được, nhưng chưa ai thực thi

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-app-ingress
  namespace: demo-app
spec:
  rules:
    - host: web-app.homelab.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-app-svc
                port:
                  number: 80
kubectl apply -f ingress.yaml
kubectl get ingress -n demo-app
NAME              CLASS    HOSTS                   ADDRESS   PORTS   AGE
web-app-ingress   <none>   web-app.homelab.local             80      0s

Chú ý 2 cột: CLASS: <none> và ADDRESS (rỗng). Kubernetes API chấp nhận manifest này (đúng cú pháp, describe thậm chí resolve đúng backend tới 3 IP Pod thật), nhưng không có gì xảy ra — không route nào hoạt động thật, vì chưa có Ingress Controller nào đăng ký lắng nghe resource Ingress. Ingress chỉ là khai báo ý định (declaration of intent) — cần 1 controller riêng đọc và biến nó thành cấu hình reverse proxy thật, sẽ cài ở bài 07.

Tự chạy lại demo

kubectl create namespace demo-app
kubectl apply -f deployment.yaml
kubectl apply -f service-clusterip.yaml
kubectl apply -f service-nodeport.yaml
kubectl apply -f ingress.yaml

4 file YAML đi kèm bài viết — áp dụng đúng thứ tự trên cùng cluster homelab đã tạo ở bài 01.

Tổng kết & bài tiếp theo

Deployment quản lý ReplicaSet, ReplicaSet quản lý Pod — rolling update/rollback hoạt động bằng cách chuyển dần giữa 2 ReplicaSet, không cắt đứt phục vụ. Service (ClusterIP) cấp DNS nội bộ + load balancing tự động qua Endpoints; NodePort mở port trên mọi node nhưng cần cấu hình thêm mới truy cập được từ máy host trên kind. Ingress chỉ là khai báo — vô dụng nếu thiếu controller.

Bài 04 đóng gói đúng 4 manifest này thành 1 Helm chart tái sử dụng được, tham số hoá qua values.yaml — không cần viết tay lại từ đầu mỗi lần deploy.
