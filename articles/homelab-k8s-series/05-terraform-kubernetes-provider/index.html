Từ bài này, chuyển dần từ kubectl apply/helm install thủ công sang quản lý bằng Terraform — mọi thay đổi cluster đi qua code, có lịch sử, có plan trước khi apply.

provider “kubernetes”: kết nối tới cluster kind

terraform {
  required_providers {
    kubernetes = {
      source  = "hashicorp/kubernetes"
      version = "~> 2.31"
    }
  }
}

provider "kubernetes" {
  config_path    = "~/.kube/config"
  config_context = "kind-homelab"
}
terraform init
Terraform has created a lock file .terraform.lock.hcl to record the provider
selections it made above...
Terraform has been successfully initialized!

config_context = "kind-homelab" — chính context kind đã tự ghi vào kubeconfig ở bài 01, không cần cấu hình credential riêng gì thêm cho cluster local.

Quản lý namespace bằng code

resource "kubernetes_namespace" "app" {
  metadata {
    name = "tf-demo"
    labels = {
      managed-by = "terraform"
    }
  }
}
terraform plan
Terraform will perform the following actions:
  # kubernetes_namespace.app will be created
  + resource "kubernetes_namespace" "app" {
      + metadata {
          + labels = { + "managed-by" = "terraform" }
          + name   = "tf-demo"
        }
    }
Plan: 1 to add, 0 to change, 0 to destroy.

terraform plan in ra chính xác những gì sắp thay đổi trước khi chạm cluster — khác kubectl apply chạy thẳng không hỏi ý kiến.

terraform apply -auto-approve
kubectl get namespace tf-demo --show-labels
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.

NAME      STATUS   AGE   LABELS
tf-demo   Active   0s    kubernetes.io/metadata.name=tf-demo,managed-by=terraform

Khi resource đã tồn tại sẵn: lỗi thật, và cách import

Tạo tay 1 namespace trước, rồi khai báo nó trong Terraform như chưa từng tồn tại:

kubectl create namespace tf-imported
resource "kubernetes_namespace" "imported" {
  metadata {
    name = "tf-imported"
  }
}
terraform apply -auto-approve
kubernetes_namespace.imported: Creating...
╷
│ Error: namespaces "tf-imported" already exists
│
│   with kubernetes_namespace.imported,
│   on namespace-imported.tf line 1
╵

Lỗi thật, không phải Terraform tự phát hiện và “nhận nuôi” — terraform plan chỉ nhìn vào state của chính nó (rỗng đối với resource này), không biết gì về những gì đã tồn tại thật trên cluster, nên vẫn cố Create và bị Kubernetes API từ chối. Muốn Terraform quản lý resource có sẵn, phải chủ động import:

terraform import kubernetes_namespace.imported tf-imported
kubernetes_namespace.imported: Importing from ID "tf-imported"...
Import successful!

The resources that were imported are shown above. These resources are now in
your Terraform state and will henceforth be managed by Terraform.
terraform plan
No changes. Your infrastructure matches the configuration.

Sau import, plan không còn đòi tạo mới — Terraform đã “biết” resource này tồn tại và khớp đúng cấu hình khai báo.

ConfigMap và Secret qua Terraform

resource "kubernetes_config_map" "app_config" {
  metadata {
    name      = "app-config"
    namespace = kubernetes_namespace.app.metadata[0].name
  }
  data = {
    APP_ENV   = "homelab"
    LOG_LEVEL = "debug"
  }
}

resource "kubernetes_secret" "app_secret" {
  metadata {
    name      = "app-secret"
    namespace = kubernetes_namespace.app.metadata[0].name
  }
  data = {
    DB_PASSWORD = "sup3rS3cret!"
  }
}

namespace = kubernetes_namespace.app.metadata[0].name — tham chiếu trực tiếp tới resource namespace khai báo ở trên, Terraform tự suy ra thứ tự tạo đúng (namespace trước, rồi mới ConfigMap/Secret vào đúng namespace đó) mà không cần khai depends_on tường minh cho trường hợp này.

terraform apply -auto-approve
kubectl get secret app-secret -n tf-demo -o jsonpath='{.data.DB_PASSWORD}' | base64 -d
sup3rS3cret!

Cảnh báo thật: Secret lưu plaintext trong tfstate

grep -A2 "DB_PASSWORD" terraform.tfstate
"DB_PASSWORD": "sup3rS3cret!",

Giá trị Secret nằm thẳng dạng plaintext trong file terraform.tfstate — không mã hoá, không che giấu gì, dù trên kubectl get secret giá trị được base64-encode (chỉ encode, không phải mã hoá thật). Hệ quả thực dụng: không bao giờ commit .tfstate vào Git; với homelab cá nhân rủi ro thấp hơn, nhưng thói quen đúng cần tập từ đầu — dùng remote state có mã hoá (S3 + KMS, Terraform Cloud…) hoặc ít nhất .gitignore chặn *.tfstate ngay từ commit đầu tiên.

terraform destroy: dọn dẹp có kiểm soát

terraform destroy -auto-approve
Plan: 0 to add, 0 to change, 4 to destroy.
kubernetes_config_map.app_config: Destroying...
kubernetes_secret.app_secret: Destroying...
kubernetes_config_map.app_config: Destruction complete after 0s
kubernetes_secret.app_secret: Destruction complete after 0s
kubernetes_namespace.imported: Destroying...
kubernetes_namespace.app: Destroying...
kubernetes_namespace.app: Destruction complete after 6s

Destroy complete! Resources: 4 destroyed.

Terraform tự xoá đúng thứ tự ngược với lúc tạo — ConfigMap/Secret trước, namespace chứa chúng sau (namespace không xoá được khi còn resource con). terraform plan chạy lại sau đó báo 4 to add — xác nhận state hoàn toàn sạch, không sót resource nào.

Tự chạy lại demo

cd terraform
terraform init
terraform plan
terraform apply -auto-approve
terraform destroy -auto-approve

4 file .tf (main.tf, namespace.tf, namespace-imported.tf, config-secret.tf) đi kèm bài viết trong thư mục terraform/.

Tổng kết & bài tiếp theo

Terraform giữ state riêng biệt với cluster thật — plan cho biết trước chính xác điều gì sẽ đổi, nhưng cũng có nghĩa resource tạo tay ngoài Terraform cần import thủ công mới được nhận quản lý. destroy xoá đúng theo thứ tự phụ thuộc ngược. Và ghi nhớ thật quan trọng: Secret trong Terraform state là plaintext, không tự mã hoá.
