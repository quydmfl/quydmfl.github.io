Bài 03 đã viết Ingress manifest nhưng chưa có gì thực thi nó (CLASS: <none>, ADDRESS rỗng). Bài này cài ingress-nginx — Ingress Controller phổ biến nhất — để route nhiều service khác nhau qua đúng 1 entrypoint, chuẩn bị cho việc chỉ cần mở đúng 1 kết nối ra internet ở bài 08.

kind cần cấu hình đặc biệt cho Ingress Controller

Cluster đã tạo ở bài 01 sẵn có port mapping 8080->80/8443->443 trên node control-plane. Ingress Controller cần chạy đúng trên node đó để tận dụng port mapping này — cần thêm 2 việc: gắn label cho node, và bỏ taint mặc định của control-plane (Kubernetes mặc định không lịch Pod thường lên control-plane).

kubectl label node homelab-control-plane ingress-ready=true
kubectl describe node homelab-control-plane | grep Taints
Taints:  node-role.kubernetes.io/control-plane:NoSchedule

Node vẫn còn taint — Pod thường sẽ không được lịch vào đây trừ khi khai báo tolerations khớp đúng taint này.

Cài ingress-nginx bằng Helm (nối lại bài 04/06)

# values.yaml
controller:
  hostPort:
    enabled: true
  service:
    type: NodePort
  nodeSelector:
    ingress-ready: "true"
  tolerations:
    - key: node-role.kubernetes.io/control-plane
      operator: Equal
      effect: NoSchedule
  publishService:
    enabled: false
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm install ingress-nginx ingress-nginx/ingress-nginx \
  -n ingress-nginx --create-namespace \
  -f values.yaml
kubectl get pods -n ingress-nginx -o wide
NAME                                        READY   STATUS    NODE
ingress-nginx-controller-6c8646dc54-cxdkp   1/1     Running   homelab-control-plane

Đúng như cấu hình nodeSelector/tolerations — Pod được lịch chính xác vào homelab-control-plane, node duy nhất có port mapping ra host. controller.hostPort.enabled: true khiến Pod này bind trực tiếp vào port 80/443 của chính node đó (không qua NodePort/iptables trung gian) — kết hợp với Docker port mapping từ bài 01, tạo thành đường đi liền mạch: host:8080 → node container:80 → Pod ingress-nginx:80.

Host-based routing: nhiều service, 1 entrypoint

Deploy 2 service hoàn toàn khác nhau để phân biệt rõ response:

kubectl create namespace routing-demo
kubectl create deployment app-a --image=nginxdemos/hello:plain-text -n routing-demo
kubectl expose deployment app-a -n routing-demo --port=80
# app-b.yaml -- http-echo, trả về đúng text cấu hình
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-b
  namespace: routing-demo
spec:
  template:
    spec:
      containers:
        - name: http-echo
          image: hashicorp/http-echo
          args: ["-text=Xin chao tu app-b"]
          ports: [{containerPort: 5678}]
kubectl apply -f app-b.yaml
kubectl expose deployment app-b -n routing-demo --port=5678

Ingress route theo host khác nhau về đúng service tương ứng:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: routing-demo
  namespace: routing-demo
spec:
  ingressClassName: nginx
  rules:
    - host: app-a.homelab.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: {service: {name: app-a, port: {number: 80}}}
    - host: app-b.homelab.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: {service: {name: app-b, port: {number: 5678}}}
kubectl apply -f ingress.yaml
kubectl get ingress -n routing-demo
NAME           CLASS   HOSTS                                     PORTS
routing-demo   nginx   app-a.homelab.local,app-b.homelab.local   80

So với bài 03: CLASS giờ là nginx (không còn <none>) — controller đã nhận diện và bắt đầu thực thi resource này thật.

Kiểm chứng thật: cùng URL, chỉ đổi Host header, 2 response khác nhau

curl -H "Host: app-a.homelab.local" http://localhost:8080/
Server name: app-a-6fdf55dc-bnxcm
curl -H "Host: app-b.homelab.local" http://localhost:8080/
Xin chao tu app-b

Cùng http://localhost:8080/, cùng port, chỉ khác header Host — trả về 2 response hoàn toàn khác nhau, đúng service tương ứng. Đây chính là “phép màu” host-based routing: 1 IP:port công khai duy nhất có thể đứng trước hàng chục domain/service khác nhau phía sau, phân biệt hoàn toàn dựa vào header Host của request tới — nguyên lý này sẽ dùng lại nguyên vẹn khi expose ra internet thật qua Cloudflare Tunnel ở bài 08.

Gọi không có Host khớp rule nào — rơi vào default backend:

curl -o /dev/null -w "HTTP status: %{http_code}\n" http://localhost:8080/
HTTP status: 404

/etc/hosts: test bằng trình duyệt thay vì chỉ curl -H

Cách curl -H "Host: ..." ở trên set header thủ công — cách này chính xác tương đương với việc để hệ điều hành tự phân giải domain giả về 127.0.0.1 rồi trình duyệt tự gửi đúng header đó. Thêm vào /etc/hosts (cần quyền sudo, không thực hiện thay đổi hệ thống trong phạm vi bài viết này):

127.0.0.1  app-a.homelab.local app-b.homelab.local

Sau đó mở http://app-a.homelab.local:8080/ trên trình duyệt — kết quả giống hệt curl -H ở trên, nhưng trực quan hơn để demo/test bằng UI thật (hữu ích khi service có giao diện web thay vì chỉ trả text).

Tự chạy lại demo

kubectl label node homelab-control-plane ingress-ready=true
helm install ingress-nginx ingress-nginx/ingress-nginx -n ingress-nginx --create-namespace -f values.yaml
kubectl apply -f app-b.yaml
kubectl apply -f ingress.yaml
curl -H "Host: app-a.homelab.local" http://localhost:8080/
curl -H "Host: app-b.homelab.local" http://localhost:8080/

values.yaml, app-b.yaml, ingress.yaml đi kèm bài viết. Ingress Controller cài ở bài này giữ nguyên chạy — dùng trực tiếp ở bài 08.

Tổng kết & bài tiếp theo

Ingress Controller là phần thực thi — không có nó, Ingress chỉ là khai báo chết (bài 03). Trên kind, controller cần chạy đúng node có port mapping (qua nodeSelector + tolerations vượt taint control-plane) và bind trực tiếp hostPort để tận dụng đường host↔node đã thiết lập từ bài 01. Host-based routing cho phép 1 entrypoint duy nhất phục vụ nhiều domain/service khác nhau — kiểm chứng thật bằng 2 response khác nhau từ đúng 1 port.

Bài 08 đưa chính entrypoint này ra internet thật bằng cloudflared — không cần mở port trên router, không cần IP tĩnh.
