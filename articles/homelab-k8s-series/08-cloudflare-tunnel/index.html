Bài 07 route được nhiều service qua 1 entrypoint nội bộ (localhost:8080). Bài này đưa entrypoint đó ra internet thật — bằng cloudflared, không cần bất kỳ thay đổi nào trên router/firewall nhà, không cần IP tĩnh.

Vì sao không port-forward truyền thống

Port-forward cần IP public tĩnh (hoặc DDNS) + mở port trên router — rủi ro bảo mật thật (expose thẳng service ra toàn internet, ai cũng quét được), và nhiều ISP dùng CGNAT (Carrier-Grade NAT) khiến port-forward không hoạt động được dù có cấu hình đúng, vì bản thân router nhà không có IP public thật. Cloudflare Tunnel giải quyết cả 2 vấn đề: cloudflared chạy trong homelab, tự mở kết nối outbound (ra ngoài) tới Cloudflare — không port nào cần mở inbound (vào trong) trên router.

Quick Tunnel: thử nhanh không cần tài khoản

cloudflared tunnel --url http://localhost:8080
2026-09-12T06:42:35Z INF Requesting new quick Tunnel on trycloudflare.com...
+--------------------------------------------------------------------------------------------+
|  Your quick Tunnel has been created! Visit it at (it may take some time to be reachable):  |
|  https://endorsed-informal-min-soon.trycloudflare.com                                      |
+--------------------------------------------------------------------------------------------+
...
+-------------------------------------------------------------------------------------+
|                               CONNECTIVITY PRE-CHECKS                               |
+-------------------------------------------------------------------------------------+
|  COMPONENT         TARGET                     STATUS  DETAILS                       |
|  DNS Resolution    region1.v2.argotunnel.com  PASS    DNS Resolved successfully     |
|  UDP Connectivity  region1.v2.argotunnel.com  PASS    QUIC connection successful    |
|  TCP Connectivity  region1.v2.argotunnel.com  PASS    HTTP/2 connection successful  |
|  Cloudflare API    api.cloudflare.com:443     PASS    API is reachable              |
|  SUMMARY: Environment is healthy. cloudflared will use 'quic' as primary protocol.  |

1 URL trycloudflare.com công khai thật, không cần đăng nhập, không cần domain riêng. cloudflared tự đăng ký tunnel, mở kết nối QUIC tới edge gần nhất (ở đây log cho thấy Cloudflare route qua khu vực hkg — Hong Kong, edge gần Việt Nam nhất). Đúng như cảnh báo trong log: DNS cho subdomain ngẫu nhiên này cần vài chục giây để lan truyền toàn cầu trước khi truy cập được — trải nghiệm thật khi test: request đầu tiên ngay sau khi tunnel khởi tạo bị curl: (6) Could not resolve host, thử lại sau ~30 giây thì thành công.

Kiểm chứng thật: request công khai xuyên internet vào đúng Pod trong kind

Port-forward 1 service cụ thể (app-a từ bài 07) ra localhost, rồi tạo tunnel trỏ đúng port đó:

kubectl port-forward -n routing-demo svc/app-a 18089:80 &
cloudflared tunnel --url http://localhost:18089
https://discharge-eng-agrees-viruses.trycloudflare.com

Gọi từ request HTTP thật, không phải mô phỏng, tới đúng URL public đó:

curl https://discharge-eng-agrees-viruses.trycloudflare.com/
Server address: 127.0.0.1:80
Server name: app-a-6fdf55dc-bnxcm
Date: 12/Sep/2026:06:44:17 +0000
URI: /
Request ID: 0b084a72262f69425349141d0d67ecd7

Server name: app-a-6fdf55dc-bnxcm — chính xác tên Pod thật đang chạy trong cluster kind trên máy local. Chuỗi hành trình đầy đủ của request này: internet công khai → Cloudflare edge → QUIC tunnel → máy local → kubectl port-forward → Service → Pod — không mở bất kỳ port nào trên router, máy đang ở sau NAT thông thường (hoặc cả CGNAT) vẫn hoạt động bình thường vì kết nối luôn được chính cloudflared chủ động mở ra ngoài, không phải ai đó từ ngoài kết nối vào.

Phát hiện thật: Cloudflare chặn giả mạo Host header

Thử áp dụng kỹ thuật host-based routing đã học ở bài 07 — trỏ tunnel vào localhost:8080 (Ingress Controller) rồi tự set Host header để chọn app:

curl -H "Host: app-a.homelab.local" https://endorsed-informal-min-soon.trycloudflare.com/
<html>
<head><title>403 Forbidden</title></head>
<body>
<center><h1>403 Forbidden</h1></center>
<hr><center>cloudflare</center>
</body>
</html>

403 từ chính Cloudflare, không phải từ nginx — khác hẳn kết quả mong đợi. Cloudflare edge kiểm tra header Host của request phải khớp đúng hostname tunnel đã đăng ký (endorsed-informal-min-soon.trycloudflare.com), từ chối thẳng nếu bị đổi thành giá trị khác — 1 lớp bảo vệ chống giả mạo request mà kỹ thuật curl -H "Host: ..." (hoạt động tốt khi gọi trực tiếp localhost:8080 ở bài 07) không thể vượt qua khi đi qua Cloudflare. Đây là khác biệt quan trọng cần biết: routing nhiều host qua Ingress Controller nội bộ và routing nhiều host qua Cloudflare Tunnel là 2 cơ chế khác nhau, không thể trộn lẫn theo cách vừa thử.

Named Tunnel: gắn với domain riêng

Muốn nhiều hostname khác nhau cùng trỏ về homelab qua 1 tunnel bền vững (không phải URL ngẫu nhiên đổi mỗi lần chạy như Quick Tunnel), cần Named Tunnel — yêu cầu tài khoản Cloudflare thật và 1 domain đã trỏ nameserver về Cloudflare:

cloudflared tunnel login                              # mở browser xác thực, lưu cert
cloudflared tunnel create homelab                      # tạo tunnel có tên "homelab"
cloudflared tunnel route dns homelab app.example.com    # trỏ DNS record về tunnel
cloudflared tunnel run homelab

cloudflared tunnel route dns tự tạo CNAME record trong zone Cloudflare của domain — không cần vào dashboard thao tác tay. 1 tunnel định danh (homelab) có thể phục vụ nhiều hostname khác nhau nếu khai báo thêm trong file config.yml:

tunnel: <tunnel-id>
credentials-file: /root/.cloudflared/<tunnel-id>.json

ingress:
  - hostname: app-a.example.com
    service: http://app-a.routing-demo.svc.cluster.local
  - hostname: app-b.example.com
    service: http://app-b.routing-demo.svc.cluster.local:5678
  - service: http_status:404   # rule cuối cùng luôn cần, xử lý hostname không khớp

Khác biệt cốt lõi so với “giả Host header” đã thất bại ở trên: ở đây cloudflared tự đọc đúng hostname request tới (không phải header tự khai báo) rồi map sang service tương ứng trước khi gửi đi đâu cả — an toàn và đúng thiết kế, không cố lách qua bất kỳ lớp kiểm tra nào.

Phần Named Tunnel cần tài khoản Cloudflare + domain thật, ngoài phạm vi test trực tiếp được trong bài viết này — cú pháp lệnh ở trên xác nhận đúng theo cloudflared tunnel --help. Bài 09 đưa toàn bộ phần này vào Terraform.

Tự chạy lại demo

kubectl port-forward -n routing-demo svc/app-a 18089:80 &
cloudflared tunnel --url http://localhost:18089
# đợi ~30s cho DNS lan truyền, rồi:
curl https://<tên-ngẫu-nhiên>.trycloudflare.com/

Không cần file cấu hình nào cho phần Quick Tunnel — mọi thứ chạy bằng đúng 1 lệnh.

Tổng kết & bài tiếp theo

cloudflared expose service ra internet thật qua kết nối outbound, không cần mở port, không bị chặn bởi CGNAT — kiểm chứng bằng request công khai thật, xuyên Cloudflare edge, vào đúng Pod đang chạy trong kind. Quick Tunnel dùng ngay không cần tài khoản nhưng URL ngẫu nhiên, đổi mỗi lần chạy; Named Tunnel gắn domain riêng, bền vững, và route nhiều hostname đúng cách qua config.yml — không phải bằng cách giả Host header (Cloudflare chặn thẳng, trả 403).
