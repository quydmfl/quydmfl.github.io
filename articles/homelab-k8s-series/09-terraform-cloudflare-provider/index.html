Lưu ý về phạm vi bài viết: bài này cần tài khoản Cloudflare thật + domain đã trỏ nameserver về Cloudflare để terraform apply chạy thành công thật — vượt ngoài phạm vi test được trong lúc viết bài. Toàn bộ cú pháp .tf dưới đây đã được kiểm chứng bằng terraform init/validate/plan thật (đúng schema provider cloudflare/cloudflare v4.52.9), và phần cuối bài có 1 lần terraform apply thật với credential giả để cho thấy chính xác lỗi API thật sẽ gặp nếu thiếu tài khoản đúng — không phải đoán hay bịa output.

Bài cuối cùng khép lại series: đưa chính cấu hình Cloudflare Tunnel + DNS đã làm thủ công ở bài 08 vào Terraform — toàn bộ homelab, từ cluster (kind, bài 01) tới namespace/Helm release (bài 05/06) tới DNS public, đều nằm trong 1 (hoặc vài) state Terraform.

provider “cloudflare”: cần API Token

terraform {
  required_providers {
    cloudflare = {
      source  = "cloudflare/cloudflare"
      version = "~> 4.0"
    }
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
  }
}

provider "cloudflare" {
  api_token = var.cloudflare_api_token
}

variable "cloudflare_api_token" {
  type      = string
  sensitive = true
}
terraform init
Terraform has been successfully initialized!

terraform init chạy thành công không cần token thật — bước này chỉ tải provider binary, chưa gọi API Cloudflare nào. Tạo API Token đúng cách trên dashboard Cloudflare (My Profile → API Tokens → Create Token) với quyền tối thiểu cần thiết — Zone.DNS:Edit cho zone cụ thể, Account.Cloudflare Tunnel:Edit — thay vì dùng Global API Key (quyền toàn tài khoản). Nguyên tắc least privilege áp dụng cả cho homelab cá nhân: token bị lộ chỉ ảnh hưởng đúng phạm vi đã cấp, không phải toàn bộ tài khoản.

Quản lý Tunnel bằng resource cloudflare_zero_trust_tunnel_cloudflared

resource "random_id" "tunnel_secret" {
  byte_length = 35
}

resource "cloudflare_zero_trust_tunnel_cloudflared" "homelab" {
  account_id = var.cloudflare_account_id
  name       = "homelab"
  secret     = random_id.tunnel_secret.b64_std
}

secret là giá trị bí mật tunnel dùng để xác thực cloudflared với Cloudflare — sinh ngẫu nhiên bằng random_id thay vì gõ tay, tương đương giá trị cloudflared tunnel create tự sinh ra khi chạy tay ở bài 08.

Route nhiều hostname qua đúng 1 tunnel — thay thế file config.yml viết tay bằng resource ..._config:

resource "cloudflare_zero_trust_tunnel_cloudflared_config" "homelab" {
  account_id = var.cloudflare_account_id
  tunnel_id  = cloudflare_zero_trust_tunnel_cloudflared.homelab.id

  config {
    ingress_rule {
      hostname = "app-a.${var.domain}"
      service  = "http://app-a.routing-demo.svc.cluster.local"
    }
    ingress_rule {
      hostname = "app-b.${var.domain}"
      service  = "http://app-b.routing-demo.svc.cluster.local:5678"
    }
    ingress_rule {
      service = "http_status:404"   # rule cuối cùng bắt buộc: xử lý hostname không khớp
    }
  }
}

ingress_rule cuối cùng không có hostname — bắt buộc phải có, đóng vai trò “catch-all” cho request không khớp rule nào ở trên (tương đương dòng service: http_status:404 trong config.yml viết tay). Thiếu rule này, terraform validate báo lỗi ngay: cloudflare_zero_trust_tunnel_cloudflared_config yêu cầu rule cuối không có hostname.

Quản lý DNS record bằng resource cloudflare_record

resource "cloudflare_record" "app_a" {
  zone_id = var.cloudflare_zone_id
  name    = "app-a"
  content = "${cloudflare_zero_trust_tunnel_cloudflared.homelab.id}.cfargotunnel.com"
  type    = "CNAME"
  proxied = true
  ttl     = 1
}

Lưu ý tên resource theo version provider: tài liệu/blog cũ có thể ghi cloudflare_dns_record — kiểm tra bằng terraform providers schema -json trên máy đang dùng cho thấy version 4.52.9 (cài lúc viết bài) dùng tên cloudflare_record. Tên resource đổi giữa các major version của provider này — luôn kiểm tra đúng tên theo version đang khai báo trong required_providers, không copy mù từ bài viết/tài liệu khác phiên bản.

content tham chiếu trực tiếp cloudflare_zero_trust_tunnel_cloudflared.homelab.id — domain app-a.<domain> trỏ đúng về tunnel vừa tạo qua <tunnel-id>.cfargotunnel.com, không cần copy tay UUID nào. Terraform tự suy ra thứ tự: tunnel phải tồn tại trước thì DNS record mới có ID để tham chiếu (giống cơ chế dependency đã học ở bài 06).

terraform validate
Success! The configuration is valid.

Không có tài khoản thật: lỗi API thật, không phải suy đoán

Chạy terraform apply với credential giả (đúng format, sai giá trị thật) để xem chính xác điều gì xảy ra:

terraform apply -auto-approve
random_id.tunnel_secret: Creating...
random_id.tunnel_secret: Creation complete after 0s [id=2Q6EoU22cApqg4jkZm7P8nVVjdcl47uHVj39mDpVQSukEas]
cloudflare_zero_trust_tunnel_cloudflared.homelab: Creating...

Error: failed to create Argo Tunnel: Could not route to /client/v4/accounts/dummy-account-id/cfd_tunnel, perhaps your object identifier is invalid? (7003)

random_id tạo thành công (resource cục bộ, không cần gọi API) — nhưng ngay khi Terraform gọi thật tới API Cloudflare để tạo tunnel, nhận về lỗi thật từ chính Cloudflare (mã lỗi 7003, định dạng response chuẩn của Cloudflare API), không phải lỗi cục bộ của Terraform. Điều này xác nhận: terraform plan không gọi API để kiểm tra token/account hợp lệ cho resource mới hoàn toàn (chưa có gì trong state để đối chiếu) — chỉ tới apply, lúc Terraform thật sự gửi request tạo resource, mới lộ ra thiếu sót về credential/quyền hạn.

Với credential thật (API Token đúng quyền + account_id/zone_id đúng của tài khoản bạn), apply sẽ tạo thành công tunnel + config + 2 DNS record, tương đương chính xác những gì đã làm tay bằng cloudflared tunnel create/route dns ở bài 08 — chỉ khác là toàn bộ nằm trong state Terraform, plan lại lần sau sẽ thấy No changes nếu không có gì đổi.

Toàn cảnh: 1 lệnh apply cho cả homelab

Tổng hợp mọi provider đã dùng xuyên suốt series trong 1 cấu trúc rõ ràng:

homelab/
├── cluster/       # (ngoài phạm vi Terraform -- kind tạo bằng CLI, bài 01)
├── apps/          # provider kubernetes + helm (bài 05, 06)
│   ├── namespace.tf
│   └── helm-release.tf
└── dns/           # provider cloudflare (bài này)
    ├── main.tf
    ├── tunnel.tf
    └── dns.tf

Tách theo layer (thay vì 1 state khổng lồ) giúp plan/apply từng phần độc lập — đổi cấu hình DNS không cần Terraform “nhìn lại” toàn bộ Kubernetes resource mỗi lần. Với credential thật, terraform apply trong từng thư mục theo đúng thứ tự (apps/ trước để service tồn tại, dns/ sau để tunnel có gì để trỏ tới) tái lập được toàn bộ homelab từ đầu — đúng giá trị thật của Infrastructure as Code: không phụ thuộc trí nhớ “đã làm gì” của người vận hành, chỉ cần đọc lại code.

Tự chạy lại (cần tài khoản Cloudflare thật)

cd terraform
terraform init
terraform validate      # chạy được ngay, không cần token thật
terraform plan \
  -var="cloudflare_api_token=<token thật>" \
  -var="cloudflare_account_id=<account id thật>" \
  -var="cloudflare_zone_id=<zone id thật>" \
  -var="domain=<domain thật của bạn>"

Toàn bộ .tf đi kèm bài viết đã qua terraform validate thành công — chỉ cần thay 4 giá trị credential/domain thật để plan/apply chạy được trên tài khoản Cloudflare của bạn.
