Ở bài trước, schema đã được thiết kế đúng hình dạng bảng/quan hệ. Bài này đi vào việc chọn kiểu dữ liệu và constraint đúng để PostgreSQL tự bảo vệ tính đúng đắn của dữ liệu — thay vì phó mặc hoàn toàn cho application code, nơi một if thiếu sót là dữ liệu bẩn lọt vào production.

JSONB — dùng khi nào, tránh khi nào

Bài toán kinh điển: một bảng products bán nhiều loại hàng khác nhau — áo có size/color, laptop có ram/cpu, sách có author/isbn. Nếu mỗi thuộc tính là một cột riêng, bảng sẽ có hàng trăm cột mà phần lớn luôn NULL với từng loại sản phẩm cụ thể. Đây là trường hợp JSONB được sinh ra để giải quyết — thuộc tính động, không biết trước tập hợp đầy đủ, và không cần join/filter hiệu quả trên từng thuộc tính riêng lẻ.

CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    attributes JSONB NOT NULL DEFAULT '{}'
);

CREATE INDEX products_attributes_idx ON products USING GIN (attributes);

Query theo một field bên trong JSONB, dùng toán tử containment @>:

SELECT id, name, attributes FROM products WHERE attributes @> '{"size": "L"}';
 id |     name      |           attributes
----+---------------+----------------------------------
  1 | Áo thun basic | {"size": "L", "color": "black"}

Với bảng chỉ 3 dòng, planner chọn Seq Scan — hoàn toàn hợp lý, quét toàn bảng 3 dòng còn rẻ hơn mở index. Ép dùng index để xác nhận GIN hoạt động đúng (SET enable_seqscan = off):

 Bitmap Heap Scan on products
   Recheck Cond: (attributes @> '{"size": "L"}'::jsonb)
   ->  Bitmap Index Scan on products_attributes_idx
         Index Cond: (attributes @> '{"size": "L"}'::jsonb)

Khi nào tránh JSONB: ngay khi một thuộc tính cần xuất hiện trong WHERE/JOIN/ORDER BY thường xuyên, hoặc cần ràng buộc kiểu dữ liệu chặt (ví dụ price phải là số dương) — tách thành cột riêng luôn tốt hơn. JSONB không có type checking ở tầng cột, không có foreign key tới giá trị bên trong, và mỗi lần đổi cấu trúc “schema ngầm” bên trong JSON không được Postgres kiểm soát — toàn bộ gánh nặng đó rơi lại vào application.

ARRAY, ENUM, DOMAIN

ARRAY cho danh sách giá trị đơn giản

Khi danh sách giá trị nhỏ, không cần metadata riêng (không cần “tag nào được tạo lúc nào, bởi ai”), ARRAY là lựa chọn nhẹ hơn một bảng many-to-many:

CREATE TABLE articles (
    id SERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    tags TEXT[] NOT NULL DEFAULT '{}'
);
SELECT title, tags FROM articles WHERE 'postgresql' = ANY(tags);
       title        |               tags
--------------------+----------------------------------
 Chuẩn hoá schema   | {postgresql,data-modeling}
 EXCLUDE constraint | {postgresql,constraints,booking}

Ranh giới rõ ràng: ngay khi tag cần thêm thuộc tính riêng (màu hiển thị, slug, người tạo) hoặc cần đếm/thống kê tag phổ biến hiệu quả ở quy mô lớn — chuyển sang bảng tags + bảng nối article_tags (many-to-many chuẩn hoá, đúng tinh thần bài 01).

ENUM — tập giá trị cố định, có thứ tự

CREATE TYPE order_status AS ENUM ('pending', 'paid', 'shipped', 'cancelled');

Điểm hay bị bỏ sót: ORDER BY trên cột ENUM sắp xếp theo thứ tự khai báo type, không phải alphabet:

INSERT INTO orders_v2 (status) VALUES ('cancelled'), ('pending'), ('shipped'); -- + 1 dòng 'paid' có sẵn
SELECT * FROM orders_v2 ORDER BY status;
 id |  status
----+-----------
  3 | pending
  1 | paid
  4 | shipped
  2 | cancelled

Đúng thứ tự vòng đời đơn hàng (pending → paid → shipped → cancelled), không phải thứ tự chữ cái (cancelled, paid, pending, shipped) — rất tiện cho việc hiển thị timeline mà không cần CASE WHEN thủ công.

Nhược điểm lớn nhất của ENUM: thêm một giá trị mới (ALTER TYPE ... ADD VALUE) trước PostgreSQL 12 không thể chạy trong cùng transaction với các lệnh khác — và ngay cả từ PG 12 trở đi, giá trị mới thêm vẫn không thể dùng ngay trong cùng transaction đã thêm nó. Nếu tập giá trị dự kiến sẽ thay đổi thường xuyên (ví dụ trạng thái do người dùng tự định nghĩa), một bảng statuses tra cứu qua foreign key linh hoạt hơn nhiều so với ENUM.

DOMAIN — tái sử dụng một ràng buộc kiểu dữ liệu

CREATE DOMAIN email AS TEXT
    CHECK (VALUE ~ '^[^@\s]+@[^@\s]+\.[^@\s]+$');

CREATE TABLE customers_v2 (
    id SERIAL PRIMARY KEY,
    contact_email email NOT NULL
);

DOMAIN gắn một ràng buộc vào một kiểu dữ liệu, dùng lại được ở bất kỳ bảng nào cần email mà không phải lặp lại CHECK (email ~ '...') ở từng bảng — sửa một chỗ, áp dụng toàn hệ thống. Insert giá trị sai định dạng bị chặn ngay ở tầng DB, không cần code application validate trước:

INSERT INTO customers_v2 (contact_email) VALUES ('khong-phai-email');
ERROR:  value for domain email violates check constraint "email_check"

CHECK constraint nâng cao

CHECK không chỉ so sánh một cột với hằng số — có thể tham chiếu biểu thức và nhiều cột cùng lúc trong cùng một dòng:

ALTER TABLE line_items ADD CONSTRAINT valid_discount
    CHECK (discount_amount <= quantity * unit_price);

Giới hạn quan trọng cần nhớ: CHECK không thể tham chiếu dữ liệu ở bảng khác hoặc dòng khác trong cùng bảng. Bài toán “chặn 2 booking trùng phòng trùng giờ” cần so sánh dòng đang insert với các dòng đã có trong bảng — vượt quá khả năng của CHECK, và đây chính là lúc cần EXCLUDE.

EXCLUDE constraint — chặn overlap ở tầng DB

Bài toán: hệ thống đặt phòng họp, tuyệt đối không cho phép 2 booking cùng phòng có khung giờ chồng lấn. Cách làm sai phổ biến: SELECT kiểm tra overlap ở application trước, rồi mới INSERT — luôn có khe hở race condition giữa hai request chạy song song (sẽ mổ xẻ kỹ loại race condition này ở bài 03). EXCLUDE giải quyết tận gốc: đẩy việc kiểm tra overlap xuống chính constraint của bảng.

CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE bookings (
    id SERIAL PRIMARY KEY,
    room_id INTEGER NOT NULL,
    during TSTZRANGE NOT NULL,
    EXCLUDE USING gist (room_id WITH =, during WITH &&)
);

btree_gist cần thiết vì EXCLUDE mặc định chỉ hỗ trợ toán tử qua index GiST, còn room_id là kiểu số nguyên thường (B-tree) — extension này bổ sung operator class GiST cho các kiểu dữ liệu thường, cho phép kết hợp room_id WITH = (so khớp chính xác) và during WITH && (kiểm tra chồng lấn khoảng thời gian) trong cùng một constraint.

Insert booking đầu (09:00-10:00, phòng 1), sau đó thử insert một booking chồng lấn (09:30-10:30, cùng phòng):

INSERT INTO bookings (room_id, during)
VALUES (1, '[2026-10-01 09:30+07, 2026-10-01 10:30+07)');
ERROR:  conflicting key value violates exclusion constraint "bookings_room_id_during_excl"
DETAIL:  Key (room_id, during)=(1, ["2026-10-01 02:30:00+00","2026-10-01 03:30:00+00")) conflicts with
existing key (room_id, during)=(1, ["2026-10-01 02:00:00+00","2026-10-01 03:00:00+00")).

PostgreSQL tự chặn — không một dòng code application nào phải viết logic kiểm tra overlap, và đảm bảo đúng kể cả khi hai request insert đồng thời vì đây là ràng buộc ở tầng transaction/index, không phải một câu SELECT riêng biệt có thể bị chen ngang.

GENERATED ALWAYS AS — cột tính toán tại tầng DB

CREATE TABLE line_items (
    id SERIAL PRIMARY KEY,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    unit_price NUMERIC(12, 2) NOT NULL,
    total NUMERIC(14, 2) GENERATED ALWAYS AS (quantity * unit_price) STORED
);
SELECT * FROM line_items;
 id | quantity | unit_price |   total
----+----------+------------+------------
  1 |        2 |  500000.00 | 1000000.00
  2 |        3 |  150000.00 |  450000.00

Khác biệt cốt lõi so với tính total ở application code hoặc qua VIEW: generated column STORED được Postgres tự tính và ghi xuống mỗi khi quantity/unit_price thay đổi, tồn tại vật lý như một cột thật nên index được — và quan trọng nhất, không ai (kể cả một câu UPDATE tay trong psql) có thể ghi đè giá trị sai lệch với công thức:

UPDATE line_items SET total = 999999 WHERE id = 1;
ERROR:  column "total" can only be updated to DEFAULT
DETAIL:  Column "total" is a generated column.

Đây là một dạng “denormalize an toàn” nhắc tới ở cuối bài 01: dữ liệu trùng lặp (total suy ra được từ 2 cột khác) nhưng không thể lệch pha, vì Postgres — chứ không phải application — là bên duy nhất được quyền ghi giá trị đó.

Tổng kết & bài tiếp theo

Nguyên tắc chọn kiểu dữ liệu: ưu tiên cột quan hệ + constraint tường minh (CHECK, DOMAIN, EXCLUDE) trước — chúng cho Postgres cơ hội tối đa để bảo vệ tính đúng đắn của dữ liệu và tối ưu query plan. Chỉ lùi về JSONB/ARRAY khi cấu trúc dữ liệu thực sự động hoặc không cần truy vấn hiệu quả trên từng phần tử. EXCLUDE và GENERATED là hai công cụ ít được biết tới nhất trong nhóm này, nhưng giải quyết gọn hai bài toán rất hay bị đẩy sai chỗ xuống application: chặn overlap dữ liệu, và giữ một giá trị suy ra luôn nhất quán.

Bài 03 đi tiếp vào transaction và isolation level — nền tảng để hiểu tại sao EXCLUDE ở trên chặn được race condition mà một SELECT kiểm tra trước ở application thì không.
