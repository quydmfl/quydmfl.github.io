Bài khép lại series: tổng hợp lại toàn bộ kiến thức 5 bài trước qua lăng kính ngược lại — nhận diện khi một schema đang vi phạm những nguyên tắc đó, và refactor nó an toàn trên một hệ thống đang chạy production (không có chuyện DROP TABLE rồi tạo lại). Toàn bộ demo dưới đây chạy trên một schema “xấu” dựng sẵn, cố tình gộp đủ 5 anti-pattern phổ biến nhất.

CREATE TABLE users (
    id SERIAL PRIMARY KEY,               -- anti-pattern: SERIAL thay vì GENERATED ALWAYS AS IDENTITY
    email TEXT,                          -- anti-pattern: thiếu NOT NULL
    created_at TIMESTAMP                 -- anti-pattern: TIMESTAMP thay vì TIMESTAMPTZ
);

CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id) -- anti-pattern: thiếu index trên FK
);

CREATE TABLE user_attributes (           -- anti-pattern: EAV cho thứ đáng ra là cột thật
    user_id INTEGER NOT NULL REFERENCES users(id),
    key TEXT NOT NULL,
    value TEXT,
    PRIMARY KEY (user_id, key)
);

Kèm dữ liệu đã có sẵn trên “production” — bao gồm cả dữ liệu bẩn thực tế hay gặp: 2 dòng email IS NULL.

Danh sách anti-pattern thường gặp

  • EAV (Entity-Attribute-Value) lạm dụng: dùng bảng (entity_id, key, value) cho thuộc tính đáng ra là cột thật (locale, plan) — tra cứu chậm (phải tự JOIN/PIVOT để lấy N thuộc tính của 1 user), mất type safety (value luôn là TEXT), không dùng được constraint (không thể CHECK plan IN ('free','pro') ở tầng DB). EAV chỉ hợp lý khi thuộc tính thực sự động và hiếm khi cần lọc/join theo nó — như JSONB đã bàn ở bài 02.
  • Thiếu index trên foreign key: Postgres không tự tạo index cho FK (khác MySQL, nơi FK luôn kèm index ngầm). Hệ quả cụ thể: xoá 1 user sẽ khiến Postgres phải quét toàn bộ orders để kiểm tra ràng buộc FK — trên bảng lớn, đây là nguồn gốc phổ biến của lock chờ lâu bất thường mà không ai hiểu tại sao.
  • SERIAL thay vì IDENTITY: SERIAL là cú pháp riêng của Postgres, tạo ra một sequence tách rời khỏi cột (dễ gặp vấn đề quyền sở hữu/permission khi migrate giữa các user DB, và không theo chuẩn SQL). GENERATED ALWAYS AS IDENTITY (chuẩn SQL, từ PG 10) nên là lựa chọn mặc định cho schema mới.
  • TIMESTAMP thay vì TIMESTAMPTZ: bug kinh điển khi hệ thống chạy nhiều timezone hoặc server đổi timezone — TIMESTAMP lưu đúng con số đã ghi, không biết nó thuộc timezone nào, nên khi đọc lại từ một session/server có TimeZone khác, giá trị hiển thị vẫn là con số cũ nhưng ý nghĩa thời điểm thực tế đã sai.
  • Nullable lung tung: cột NOT NULL bị bỏ qua “cho tiện lúc code”, hậu quả dồn xuống tầng application phải tự kiểm tra khắp nơi thay vì để Postgres đảm bảo một lần duy nhất.

Cách nhận diện: đọc schema như một checklist

Trước khi refactor, soát nhanh schema hiện có theo đúng thứ tự 5 bài đã học:

  1. Bảng có ở 3NF chưa (bài 01)? Có cột nào lẽ ra nên tách bảng riêng, hoặc có denormalize nhưng không rõ lý do?
  2. Constraint có phản ánh đúng ràng buộc nghiệp vụ chưa (bài 02)? Cột nào đang NULL được nhưng thực ra luôn phải có giá trị? Có nơi nào cần EXCLUDE nhưng đang xử lý ở application?
  3. Thao tác “đọc rồi ghi” nào chưa được bảo vệ đúng mức (bài 03)?
  4. Query báo cáo nào đang giải bằng vòng lặp ở code thay vì window function/CTE (bài 04)?
  5. Tìm kiếm nào đang dùng LIKE '%...%' chậm chạp thay vì full-text search (bài 05)?

Case study: refactor từng bước

Bước 1 — thêm index còn thiếu trên FK, không khoá bảng

CREATE INDEX CONCURRENTLY IF NOT EXISTS orders_user_id_idx ON orders (user_id);

CONCURRENTLY xây index song song, không giữ lock chặn ghi trong suốt quá trình (đổi lại: chậm hơn CREATE INDEX thường, và không thể chạy trong transaction block). Đây gần như luôn là lựa chọn đúng khi thêm index cho bảng đang có traffic ghi thật.

Bước 2 — thêm NOT NULL không khoá bảng để quét toàn bộ

Thêm NOT NULL trực tiếp bằng ALTER TABLE ... ALTER COLUMN email SET NOT NULL trên bảng lớn giữ ACCESS EXCLUSIVE LOCK suốt thời gian quét toàn bộ bảng để xác nhận không dòng nào vi phạm — với bảng hàng triệu dòng, đây có thể là vài phút chặn hoàn toàn mọi ghi/đọc lock. Cách an toàn: tách thành CHECK ... NOT VALID (tức thời) rồi VALIDATE CONSTRAINT (quét nhưng chỉ giữ lock nhẹ, không chặn ghi) ở hai bước riêng.

ALTER TABLE users ADD CONSTRAINT users_email_not_null CHECK (email IS NOT NULL) NOT VALID;

NOT VALID áp dụng tức thời — kể cả khi bảng đang có dữ liệu vi phạm (2 dòng email IS NULL), vì nó chỉ áp dụng cho các dòng ghi sau này, chưa kiểm tra dữ liệu cũ. Thử VALIDATE ngay mà chưa backfill dữ liệu cũ:

ALTER TABLE users VALIDATE CONSTRAINT users_email_not_null;
ERROR:  check constraint "users_email_not_null" of relation "users" is violated by some row

Lỗi thật, đúng như dự kiến — 2 dòng cũ vẫn còn email IS NULL. Đây chính xác là lý do phải backfill trước:

UPDATE users SET email = 'user-' || id || '@unknown.example.com' WHERE email IS NULL;

Validate lại — lần này thành công:

ALTER TABLE users VALIDATE CONSTRAINT users_email_not_null;
ALTER TABLE

Sau khi validate xong, có thể chuyển hẳn sang NOT NULL thật (từ PG 12+, bước này gần như tức thời vì Postgres tái sử dụng chính CHECK constraint vừa validate, không quét lại):

ALTER TABLE users ALTER COLUMN email SET NOT NULL;
ALTER TABLE users DROP CONSTRAINT users_email_not_null;

Bước 3 — TIMESTAMP → TIMESTAMPTZ

ALTER TABLE users
    ALTER COLUMN created_at TYPE TIMESTAMPTZ USING created_at AT TIME ZONE 'UTC';
                                       Table "public.users"
   Column   |           Type           | Collation | Nullable |              Default
------------+--------------------------+-----------+----------+-----------------------------------
 id         | integer                  |           | not null | nextval('users_id_seq'::regclass)
 email      | text                     |           |          |
 created_at | timestamp with time zone |           |          |

Lưu ý quan trọng, khác hẳn bước 2: ALTER COLUMN ... TYPE luôn rewrite toàn bộ bảng và giữ ACCESS EXCLUSIVE LOCK suốt quá trình — không có phiên bản “NOT VALID” cho việc đổi kiểu dữ liệu. Trên bảng vài dòng như demo này, lệnh chạy tức thời; trên bảng hàng chục triệu dòng ở production, đây có thể là một khoảng downtime thật sự. Cách an toàn hơn cho bảng lớn: thêm cột TIMESTAMPTZ mới, backfill theo batch nhỏ, dual-write ở application một thời gian, rồi mới đổi tên cột — nằm ngoài phạm vi demo ở quy mô nhỏ này, nhưng bắt buộc phải cân nhắc trước khi chạy lệnh trên với bảng lớn thật.

Một điểm nữa dễ bỏ sót: AT TIME ZONE 'UTC' giả định toàn bộ dữ liệu TIMESTAMP cũ đang được ghi theo giờ UTC. Giả định này phải được xác nhận đúng với thực tế dữ liệu trước khi chạy — nếu ứng dụng cũ từng ghi giờ địa phương (Asia/Ho_Chi_Minh) mà không nhất quán, migration này sẽ âm thầm dịch sai giờ hàng loạt.

Bước 4 — EAV → cột thật

ALTER TABLE users
    ADD COLUMN locale TEXT,
    ADD COLUMN plan TEXT NOT NULL DEFAULT 'free';

UPDATE users u SET locale = a.value FROM user_attributes a
WHERE a.user_id = u.id AND a.key = 'locale';

UPDATE users u SET plan = a.value FROM user_attributes a
WHERE a.user_id = u.id AND a.key = 'plan';

Dữ liệu trước (trong user_attributes, dạng EAV):

 user_id |  key   | value
---------+--------+-------
       1 | locale | vi-VN
       1 | plan   | pro
       2 | locale | en-US
       2 | plan   | free
       4 | locale | vi-VN
       4 | plan   | free

Sau khi backfill, locale/plan là cột thật trên users, CHECK/NOT NULL/index dùng được bình thường:

 id |           email            | locale | plan
----+----------------------------+--------+------
  1 | alice@example.com          | vi-VN  | pro
  2 | bob@example.com            | en-US  | free
  3 | user-3@unknown.example.com |        | free
  4 | dave@example.com           | vi-VN  | free
  5 | user-5@unknown.example.com |        | free

User 3 và 5 (chưa từng có dòng nào trong user_attributes) tự động nhận plan = 'free' (giá trị DEFAULT) và locale = NULL — đúng ngữ nghĩa “chưa từng thiết lập”, điều mà EAV cũ thể hiện đúng bằng việc không có dòng nào, và cột thật thể hiện đúng bằng NULL. Bảng user_attributes giữ nguyên trong một thời gian (dual-write / dual-read ở application) trước khi xoá hẳn dữ liệu cũ, phòng trường hợp cần rollback.

Bước 5 — SERIAL → IDENTITY

Thử chuyển thẳng bị chặn vì cột còn default cũ:

ALTER TABLE users ALTER COLUMN id ADD GENERATED ALWAYS AS IDENTITY;
ERROR:  column "id" of relation "users" already has a default value

Thứ tự đúng: gỡ default cũ trước, rồi mới thêm IDENTITY, với START WITH lớn hơn id lớn nhất hiện có (tránh trùng id dữ liệu cũ):

ALTER TABLE users ALTER COLUMN id DROP DEFAULT;
ALTER TABLE users ALTER COLUMN id ADD GENERATED ALWAYS AS IDENTITY (START WITH 6);

Insert thử để xác nhận identity tự sinh đúng số tiếp theo:

INSERT INTO users (email, created_at) VALUES ('frank@example.com', now()) RETURNING id;
 id
----
  6

Sequence cũ (users_id_seq) không còn cột nào tham chiếu tới nữa sau bước này — dọn luôn bằng DROP SEQUENCE IF EXISTS users_id_seq; để tránh để lại object mồ côi trong schema.

Tự chạy lại toàn bộ

docker compose up -d

sql/ (tự chạy khi khởi động container) dựng schema “xấu” ban đầu (01-schema-bad.sql) và seed dữ liệu thật kèm 2 dòng email NULL (02-seed.sql). migrations/ chứa 5 bước refactor riêng biệt — chạy tay từng bước, theo đúng thứ tự, để tự thấy rõ ràng từng bước giải quyết đúng 1 vấn đề:

docker compose exec -T postgres psql -U demo -d legacy_app -f - < migrations/01-add-fk-index-concurrently.sql
docker compose exec -T postgres psql -U demo -d legacy_app -f - < migrations/02-not-null-without-long-lock.sql
docker compose exec -T postgres psql -U demo -d legacy_app -f - < migrations/03-timestamptz.sql
docker compose exec -T postgres psql -U demo -d legacy_app -f - < migrations/04-eav-to-columns.sql
docker compose exec -T postgres psql -U demo -d legacy_app -f - < migrations/05-serial-to-identity.sql
docker compose down -v
