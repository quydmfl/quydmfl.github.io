03. Table Partitioning

Oct 7, 2026 · 6 min read

Series · Postgres HA & Scaling

  1. 01. Streaming Replication
  2. 02. Failover
  3. 03. Table Partitioning
  4. 04. Connection Pooling
  5. 05. Horizontal Scaling

Rời khỏi HA, mini-series chuyển sang scaling theo chiều dữ liệu — bắt đầu từ kỹ thuật vẫn nằm trong 1 node trước khi cần tới nhiều node: partitioning. Chia 1 bảng logic thành nhiều bảng vật lý nhỏ hơn, Postgres tự định tuyến query tới đúng partition. Bảng events 600.000 dòng, partition theo tháng (RANGE trên created_at, 6 partition), cùng 1 bảng events_flat y hệt dữ liệu nhưng không partition để đối chứng trực tiếp.

Range Partitioning — theo thời gian, kịch bản phổ biến nhất

CREATE TABLE events (
    id SERIAL,
    created_at DATE NOT NULL,
    payload TEXT NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2025_03 PARTITION OF events FOR VALUES FROM ('2025-03-01') TO ('2025-04-01');
-- ... 5 partition khác, mỗi tháng 1 partition

INSERT INTO events bình thường — Postgres tự định tuyến từng dòng vào đúng partition dựa trên created_at, hoàn toàn trong suốt với application (không cần biết bảng đã partition).

Partition Pruning — lợi ích thực sự đo được

Query lọc đúng 1 tháng:

EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM events
WHERE created_at >= '2025-03-01' AND created_at < '2025-04-01';
Aggregate (cost=2453.39..2453.40 rows=1 width=8) (actual time=11.899..11.899 rows=1 loops=1)
  Buffers: shared hit=655
  ->  Seq Scan on events_2025_03 events
        Filter: ((created_at >= '2025-03-01'::date) AND (created_at < '2025-04-01'::date))
        Buffers: shared hit=655
Execution Time: 11.918 ms

Chỉ đúng 1 partition (events_2025_03) xuất hiện trong plan — 5 partition còn lại bị loại bỏ hoàn toàn ngay từ bước lập kế hoạch, không hề được nhắc tới, không tốn 1 buffer nào để kiểm tra. Đây là partition pruning: khác các kỹ thuật lọc dữ liệu khác (index, WHERE) chạy lúc thực thi, pruning loại bỏ partition ngay ở bước lập kế hoạch.

So sánh trung thực với bảng không partition

Cùng dữ liệu, cùng index trên created_at, bảng events_flat:

EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM events_flat
WHERE created_at >= '2025-03-01' AND created_at < '2025-04-01';
Aggregate (cost=2705.82..2705.83 rows=1 width=8) (actual time=10.391..10.391 rows=1 loops=1)
  Buffers: shared hit=93
  ->  Index Only Scan using events_flat_created_at_idx on events_flat
        Heap Fetches: 0
        Buffers: shared hit=93
Execution Time: 10.421 ms

Kết quả cần nói thẳng, không tô hồng: events_flat (93 buffer, 10.4ms) thực ra nhanh hơn và nhẹ hơn events đã partition (655 buffer, 11.9ms) cho đúng query này! Lý do: sau khi pruning chỉ còn đúng 1 partition (~100.000 dòng), toàn bộ dòng trong partition đó đều khớp điều kiện (~100% selectivity nội bộ) — đúng bài học selectivity từ Performance & Indexing bài 01: planner chọn Seq Scan cho partition đó thay vì dùng index, vì gần như phải đọc hết. Trong khi đó, events_flat có toàn bộ 600.000 dòng nhưng chỉ ~17% khớp điều kiện — Index Only Scan (với visibility map đã set sau VACUUM) trở nên rất hiệu quả, ít buffer hơn hẳn so với đọc nguyên 1 partition.

Bài học quan trọng nhất bài này: partitioning không tự động nhanh hơn một bảng thường có index tốt — với truy vấn range đơn giản như trên, một B-tree index hiệu quả trên bảng phẳng có thể thắng cả partition pruning. Lợi ích thật của partitioning nằm ở chỗ khác, sẽ nói ở cuối bài.

Khi KHÔNG lọc theo partition key — mất hết lợi ích pruning

EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM events WHERE payload LIKE 'payload 1%';
Finalize Aggregate (actual time=20.965..22.453 rows=1 loops=1)
  Buffers: shared hit=3825
  ->  Gather (Workers Launched: 2)
        ->  Parallel Append
              ->  Parallel Seq Scan on events_2025_03 events_3 ...
              ->  Parallel Seq Scan on events_2025_05 events_5 ...
              ->  Parallel Seq Scan on events_2025_01 events_1 ...
              ->  Parallel Seq Scan on events_2025_04 events_4 ...
              ->  Parallel Seq Scan on events_2025_06 events_6 ...
              ->  Parallel Seq Scan on events_2025_02 events_2 ...
Execution Time: 22.518 ms

Cả 6 partition đều xuất hiện (gộp qua Parallel Append) — không lọc theo created_at nghĩa là Postgres không có cơ sở nào để loại bớt partition. So với events_flat cho đúng query này:

Finalize Aggregate (actual time=21.646..23.380 rows=1 loops=1)
  Buffers: shared hit=688 read=3134
  ->  Gather (Workers Launched: 2)
        ->  Parallel Seq Scan on events_flat
Execution Time: 23.434 ms

Gần như y hệt nhau (3825 buffer/22.5ms so với 3822 buffer/23.4ms) — đúng như dự đoán: không lọc theo partition key thì partition hay không partition không tạo ra khác biệt đáng kể, có chăng partition tốn thêm chút overhead điều phối Parallel Append giữa nhiều bảng con.

Vậy lợi ích thật của partitioning nằm ở đâu?

Không phải ở tốc độ 1 query đơn lẻ như 2 thí nghiệm trên cho thấy — mà ở các thao tác vận hành mà bảng phẳng làm rất tốn kém:

  • Xoá dữ liệu cũ tức thời: DROP TABLE events_2025_01 xoá toàn bộ 1 tháng dữ liệu ngay lập tức (thao tác catalog, không quét/không ghi WAL cho từng dòng), so với DELETE FROM events_flat WHERE created_at < '2025-02-01' phải quét, đánh dấu dead tuple hàng trăm nghìn dòng, rồi chờ VACUUM dọn — đúng bài học bloat ở Internals bài 03.
  • VACUUM/ANALYZE/backup rải nhỏ theo từng partition: partition tháng cũ (không còn ghi) gần như không bao giờ cần VACUUM lại, trong khi bảng phẳng 600.000 dòng luôn phải quét toàn bộ dù 5/6 dữ liệu đã “nguội”.
  • Dữ liệu quá lớn để 1 file quản lý hiệu quả: ở quy mô hàng chục/trăm triệu dòng, chia nhỏ theo partition giúp mỗi thao tác bảo trì chỉ động vào 1 phần dữ liệu, thay vì luôn phải xử lý cả khối khổng lồ.

List & Hash Partitioning

  • PARTITION BY LIST: chia theo tập giá trị rời rạc cụ thể — ví dụ region, hoặc tenant_id cho hệ thống multi-tenant, nơi mỗi tenant lớn có thể tách hẳn 1 partition riêng.
  • PARTITION BY HASH: chia đều dữ liệu khi không có tiêu chí tự nhiên rõ ràng để phân nhóm — mục tiêu chỉ là chia nhỏ đồng đều để dễ vận hành song song (ví dụ VACUUM nhiều partition cùng lúc), không nhắm tới pruning theo giá trị cụ thể như RANGE/LIST (hash của 1 giá trị không đoán trước được nó rơi vào partition nào nếu không tính hash, nên pruning theo WHERE tenant_id = X vẫn hoạt động, nhưng pruning theo range giá trị thì không).

Tự chạy lại demo

docker compose up -d
docker compose exec postgres psql -U demo -d partition_demo

sql/01-setup.sql dựng cả events (partition) và events_flat (đối chứng), cùng dữ liệu, cùng index. Chạy lại đúng 2 cặp EXPLAIN trong bài để tự thấy sự khác biệt (hoặc không khác biệt).

docker compose down -v

Tổng kết & bài tiếp theo

Partitioning là công cụ vận hành, không phải công cụ tăng tốc query mặc định — 2 thí nghiệm ở trên cho thấy rõ nó có thể chậm hơn hoặc ngang bằng một bảng phẳng có index tốt cho truy vấn đơn giản. Giá trị thật nằm ở việc quản lý dữ liệu lớn dần theo thời gian: xoá nhanh, bảo trì rải nhỏ, và khả năng scale các thao tác vận hành độc lập theo từng phần dữ liệu.
