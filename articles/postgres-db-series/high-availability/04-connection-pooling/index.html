04. Connection Pooling

Oct 8, 2026 · 5 min read

Series · Postgres HA & Scaling

  1. 01. Streaming Replication
  2. 02. Failover
  3. 03. Table Partitioning
  4. 04. Connection Pooling
  5. 05. Horizontal Scaling

Partitioning (bài 03) scale theo chiều dữ liệu. Bài này scale theo chiều kết nối — nơi Postgres có một giới hạn vật lý ít ứng dụng để ý tới cho đến khi chạm phải trong production.

Vì sao mỗi connection Postgres đắt hơn tưởng tượng

Mỗi connection Postgres là 1 process hệ điều hành riêng (khác MySQL dùng thread nhẹ hơn nhiều) — tốn RAM cố định cho mỗi connection bất kể đang chạy query hay idle. max_connections mặc định thường ở mức vài trăm, nhưng đây là con số không co giãn tự động theo RAM — đặt quá cao mà không kiểm soát khiến tổng RAM cấp phát cho connection có thể vượt quá RAM vật lý thực tế.

Đo thật giới hạn: đặt max_connections = 20, mở 25 connection song song trực tiếp:

-- 25 session song song, mỗi session: SELECT pg_sleep(3);

6 trong số 25 connection thất bại, lỗi thật:

psql: error: connection to server ... failed: FATAL:  sorry, too many clients already

Đúng như kỳ vọng: 20 connection đầu tiên chiếm hết max_connections, phần còn lại bị từ chối thẳng — không xếp hàng, không chờ, từ chối ngay lập tức.

PgBouncer: pool connection ở giữa application và Postgres

Application kết nối vào PgBouncer thay vì thẳng vào Postgres; PgBouncer duy trì 1 pool nhỏ connection thật tới Postgres, tái sử dụng qua lại cho nhiều client. Dựng thật (DEFAULT_POOL_SIZE = 10, POOL_MODE = transaction), chạy cùng tải 25 connection song song — lần này qua PgBouncer:

docker compose exec postgres psql "postgresql://demo:demo@pgbouncer:5432/appdb" -c "SELECT pg_sleep(1);"
# lặp lại 25 lần song song

0 lỗi trong cả 25 connection. Xác nhận PgBouncer thực sự chỉ dùng đúng số connection thật đã cấu hình, kiểm tra ngay trong lúc 25 client đang chờ xử lý:

SELECT count(*) FROM pg_stat_activity WHERE datname = 'appdb' AND pid <> pg_backend_pid();
 count
-------
    10

Đúng bằng DEFAULT_POOL_SIZE = 10 — dù có 25 client đang kết nối đồng thời qua PgBouncer, Postgres chỉ thấy đúng 10 connection thật. 15 client còn lại được PgBouncer xếp hàng chờ, tái sử dụng ngay khi có connection rảnh, hoàn toàn trong suốt với client.

Transaction mode vs Session mode — khác biệt nguy hiểm nhất

Session mode: 1 client connection = 1 server connection cố định suốt phiên — an toàn tuyệt đối, nhưng không tiết kiệm được nhiều (gần như 1-1 như không có pool). Transaction mode (đang dùng ở demo trên): server connection chỉ được giữ trong đúng 1 transaction, trả lại pool ngay sau COMMIT — tiết kiệm tối đa, nhưng có thể âm thầm phá vỡ trạng thái ở tầng session.

Chứng minh bằng cách theo dõi pg_backend_pid() (PID thật của tiến trình Postgres đang phục vụ) qua nhiều câu lệnh trong cùng 1 session client, dưới tải tranh chấp (30 connection nền chiếm pool đồng thời):

Kết nối trực tiếp (không qua pool):

SELECT pg_backend_pid(); -- 1023
SELECT pg_backend_pid(); -- 1023
SELECT pg_backend_pid(); -- 1023
SELECT pg_backend_pid(); -- 1023
SELECT pg_backend_pid(); -- 1023

Qua PgBouncer (transaction mode), cùng session, dưới tranh chấp:

SELECT pg_backend_pid(); -- 411
SELECT pg_backend_pid(); -- 302
SELECT pg_backend_pid(); -- 364
SELECT pg_backend_pid(); -- 364
SELECT pg_backend_pid(); -- 364

PID đổi liên tục (411 → 302 → 364) dù toàn bộ 5 câu lệnh chạy trong cùng 1 kết nối client, cùng 1 script, không hề ngắt kết nối — mỗi câu lệnh tự động là 1 transaction riêng (autocommit), và PgBouncer tự do gán bất kỳ backend rảnh nào cho transaction tiếp theo khi có tranh chấp. Kết nối trực tiếp thì PID không đổi suốt session — đúng hành vi thông thường mọi ứng dụng đang giả định.

Hệ quả thực tế — SET biến mất không báo lỗi: chạy đúng kịch bản đó với SET:

SET search_path TO 'my_custom_schema';
SELECT pg_backend_pid();                          -- 410
SELECT current_setting('search_path');
SELECT pg_backend_pid();                          -- 302
SET
 backend_khi_set
------------------
              410

 search_path_thay_doi
------------------------
 "$user", public

 backend_luc_doc
------------------
              302

search_path vẫn là giá trị mặc định ("$user", public), không phải my_custom_schema vừa SET — vì câu SELECT current_setting bị route sang backend 302, chưa từng thấy câu SET chạy trên backend 410. Không có lỗi nào được ném ra — ứng dụng chỉ âm thầm nhận sai giá trị cấu hình, loại bug khó phát hiện nhất vì không crash, chỉ sai một cách im lặng.

Đây là lý do transaction mode không tương thích với: SET session-level không bọc trong transaction, prepared statement sống qua nhiều transaction, session-level advisory lock giữ xuyên transaction, và LISTEN/NOTIFY. Nếu ứng dụng cần bất kỳ tính năng nào trong số này, chọn session mode (đánh đổi mất phần lớn lợi ích tiết kiệm connection) hoặc tách riêng 1 pool session mode cho đúng phần code cần tính năng đó.

Tự chạy lại demo

docker compose up -d
# Kết nối trực tiếp Postgres (max_connections=20):
docker compose exec postgres psql -U demo -d appdb

# Kết nối qua PgBouncer (port 6432, transaction mode):
docker compose exec postgres psql "postgresql://demo:demo@pgbouncer:5432/appdb"

Để tái hiện đúng hiện tượng đổi PID, cần tạo tải nền tranh chấp pool trước (nhiều connection song song qua PgBouncer đang chạy pg_sleep) — không tranh chấp, PgBouncer có xu hướng tái sử dụng lại đúng backend cũ cho cùng client (tối ưu hiệu năng), nên hiện tượng không phải lúc nào cũng lộ ra ngay cả khi đang ở transaction mode.

docker compose down -v

Tổng kết & bài tiếp theo

PgBouncer giải quyết thật vấn đề max_connections — số liệu chứng minh rõ ràng (10 connection thật phục vụ 25 client). Nhưng transaction mode, chế độ tiết kiệm nhất, có đánh đổi thật và âm thầm, không phải lý thuyết suông: PID backend đổi ngay giữa các câu lệnh trong cùng 1 session, kéo theo bất kỳ trạng thái session-level nào cũng có thể biến mất không báo trước.
