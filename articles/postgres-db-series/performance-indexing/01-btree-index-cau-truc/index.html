Nền tảng vật lý (page, tuple, buffer cache) đã học ở mini-series Internals. Mini-series này chuyển sang câu hỏi thực dụng hơn: làm sao query nhanh hơn, đo được bao nhiêu, và index có thực sự được dùng hay không. Bắt đầu từ loại index phổ biến nhất — B-tree, loại mặc định khi chạy CREATE INDEX không chỉ định gì khác — và một sự thật hay bị bỏ qua: có index không có nghĩa là planner luôn dùng nó.

Cấu trúc B-tree: vì sao tra cứu luôn nhanh gần như O(log n)

Soi trực tiếp metadata của 1 index bằng pageinspect, trên bảng events 100.000 dòng với cột status:

CREATE EXTENSION IF NOT EXISTS pageinspect;
SELECT * FROM bt_metap('events_status_idx');
-[ RECORD 1 ]-------------+-------
magic                     | 340322
version                   | 4
root                      | 3
level                     | 1
fastroot                  | 3
fastlevel                 | 1

level = 1 nghĩa là cây chỉ có 2 tầng: root (tầng 1) và leaf (tầng 0) — dù index phủ 100.000 dòng. Đây chính là bản chất “nhiều nhánh” của B-tree: khác cây nhị phân (mỗi node tối đa 2 con), mỗi node B-tree chứa hàng trăm key, nên số tầng cần đi qua để tới đúng leaf tăng cực chậm so với số dòng — quan hệ gần đúng O(log_B n) với B là “độ phân nhánh” (fanout), không phải O(log_2 n).

Soi tiếp 1 leaf page cụ thể:

SELECT * FROM bt_page_stats('events_status_idx', 1);
 blkno | type | live_items | dead_items | avg_item_size | free_size
-------+------+------------+------------+----------------+-----------
     1 | l    |         10 |          0 |            729 |       812

Con số bất ngờ: chỉ 10 item trên page này, nhưng avg_item_size = 729 byte — rất lớn so với 1 entry B-tree thông thường (thường chỉ vài chục byte: giá trị key + con trỏ tới heap). Soi kỹ hơn từng item:

SELECT itemoffset, ctid, itemlen, data FROM bt_page_items('events_status_idx', 1) LIMIT 3;
 itemoffset |   ctid    | itemlen |          data
------------+-----------+---------+-------------------------
          1 | (16,4097) |      24 | 0b 64 6f 6e 65 00 00 00
          2 | (16,8324) |     808 | 0b 64 6f 6e 65 00 00 00

Cả 2 item đều mang giá trị 'done' (64 6f 6e 65 = “done” dạng hex), nhưng item thứ 2 nặng 808 byte — vì đây là posting list: thay vì lưu riêng từng cặp (giá trị, con trỏ heap) cho hàng chục nghìn dòng cùng giá trị 'done', PostgreSQL (từ bản 13, B-tree version 4 — đúng khớp version=4 ở bt_metap phía trên) nén nhiều con trỏ heap của cùng 1 giá trị vào chung 1 entry. Đây là lý do index cho cột chỉ có vài giá trị riêng biệt (status chỉ có 'done'/'failed') vẫn nhỏ gọn bất ngờ:

SELECT pg_size_pretty(pg_relation_size('events_status_idx')) AS index_size,
       pg_size_pretty(pg_relation_size('events')) AS table_size;
 index_size | table_size
------------+------------
 696 kB     | 5096 kB

Index chỉ 696KB cho bảng 5MB — nhỏ hơn nhiều so với ước tính ngây thơ “mỗi dòng 1 entry index”.

Selectivity & cardinality: hai con số quyết định planner có dùng index không

Cardinality — số giá trị riêng biệt trong cột — Postgres ước lượng qua pg_stats (cập nhật bởi ANALYZE):

SELECT attname, n_distinct, most_common_vals, most_common_freqs
FROM pg_stats WHERE tablename = 'events' AND attname = 'status';
 attname | n_distinct | most_common_vals |    most_common_freqs
---------+------------+------------------+--------------------------
 status  |          2 |  {done,failed}   | {0.98973334,0.010266666}

n_distinct = 2 — cardinality rất thấp. Nhưng con số quyết định trực tiếp việc dùng index không phải cardinality của cả cột, mà là selectivity của điều kiện cụ thể trong WHERE — tỉ lệ dòng thoả điều kiện đó. most_common_freqs cho thấy 'done' chiếm 98.97%, 'failed' chỉ 1.03% — hai điều kiện lọc trên cùng 1 cột, cùng 1 index, nhưng selectivity khác nhau hoàn toàn.

Khi nào planner CHỦ ĐỘNG bỏ qua index dù đã tạo

Cùng 1 index events_status_idx, hai điều kiện khác nhau:

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE status = 'failed';
Index Scan using events_status_idx on events (cost=0.29..121.31 rows=1027 width=17) (actual time=0.022..0.620 rows=980 loops=1)
  Index Cond: (status = 'failed'::text)
  Buffers: shared hit=494 read=3
Execution Time: 0.694 ms
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE status = 'done';
Seq Scan on events (cost=0.00..1887.00 rows=98973 width=17) (actual time=0.004..7.895 rows=99020 loops=1)
  Filter: (status = 'done'::text)
  Rows Removed by Filter: 980
  Buffers: shared hit=637
Execution Time: 10.943 ms

Cùng 1 index, 2 plan hoàn toàn khác nhau — planner tự quyết định, không phải “có index thì phải dùng”. Với 'failed' (selectivity 0.98%): Index Scan, chỉ đọc 497 buffer, 0.694ms. Với 'done' (selectivity 99%): Seq Scan, đọc 637 buffer nhưng đọc tuần tự thay vì nhảy qua lại giữa index và heap — nhanh hơn Index Scan trong trường hợp gần như phải đọc lại toàn bộ bảng.

Đừng chỉ tin vào ước lượng — ép Postgres phải dùng Index Scan cho 'done' để so sánh chi phí thật:

SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE status = 'done';
Index Scan using events_status_idx on events (cost=0.29..2789.54 rows=98973 width=17) (actual time=0.029..9.997 rows=99020 loops=1)
  Buffers: shared hit=639 read=83
Execution Time: 13.803 ms

Xác nhận bằng số liệu thật, không chỉ ước lượng: cost=2789.54 (cao hơn Seq Scan’s 1887.00) và thời gian chạy thật cũng chậm hơn — 13.803ms so với 10.943ms. Planner đã chọn đúng. Index Scan phải nhảy qua lại liên tục giữa các trang index và trang heap tương ứng (mỗi lần một random I/O riêng lẻ) để lấy gần như toàn bộ 99% số dòng — tốn kém hơn hẳn việc đọc tuần tự toàn bộ bảng một lượt.

Tự chạy lại demo

docker compose up -d
docker compose exec postgres psql -U demo -d perf_demo

sql/01-setup.sql seed 100.000 dòng events (status 'done' 99%, 'failed' 1%) và tạo sẵn index. Toàn bộ câu lệnh trong bài chạy trực tiếp được theo đúng thứ tự đã trình bày.

docker compose down -v

Tổng kết & bài tiếp theo

Ba điều cần nhớ: B-tree đạt tốc độ tra cứu nhanh nhờ phân nhánh rộng (nhiều tầng ít hơn hẳn số dòng), Postgres tự nén các giá trị trùng lặp bằng posting list nên index cho cột cardinality thấp vẫn nhỏ gọn, và planner luôn cân nhắc selectivity thực tế — index tồn tại không đảm bảo nó được dùng, và đó là hành vi đúng, không phải bug.
