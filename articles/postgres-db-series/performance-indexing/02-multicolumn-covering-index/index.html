Bài 01 dừng ở index 1 cột. Bài này đi vào index nhiều cột trên bảng orders (300.000 dòng, cột customer_id, status, total) — nơi thứ tự khai báo cột trong CREATE INDEX ảnh hưởng trực tiếp tới việc index được dùng hiệu quả tới đâu, không đơn giản chỉ là “dùng được” hay “không dùng được” như trực giác thường nghĩ.

Quy tắc “leftmost prefix”

Index (customer_id, status) sắp xếp vật lý theo customer_id trước, status chỉ có thứ tự bên trong từng nhóm customer_id — giống một cuốn danh bạ sắp theo (họ, tên): tra theo họ nhanh vì danh bạ đã sắp đúng thứ tự đó; tra theo tên một mình thì không tận dụng được thứ tự sắp xếp, phải lật gần hết cuốn danh bạ.

So sánh thật, lọc theo cột đầu (customer_id) so với cột thứ 2 (status) một mình:

EXPLAIN (ANALYZE, BUFFERS) SELECT status FROM orders WHERE customer_id = 42;
Index Only Scan using orders_customer_status_covering_idx on orders
  Index Cond: (customer_id = 42)
  Heap Fetches: 0
  Buffers: shared hit=4
Execution Time: 0.081 ms
EXPLAIN (ANALYZE, BUFFERS) SELECT status FROM orders WHERE status = 'paid';
Index Only Scan using orders_customer_status_idx on orders
  Index Cond: (status = 'paid'::text)
  Heap Fetches: 0
  Buffers: shared hit=4 read=306
Execution Time: 15.629 ms

Cả hai đều dùng index — đây là điểm hay bị hiểu nhầm: lọc theo cột không nằm ở đầu (status) không có nghĩa index “không dùng được” tuyệt đối. Vấn đề nằm ở hiệu quả: customer_id = 42 chỉ cần đọc 4 buffer, còn status = 'paid' phải đọc 310 buffer — gần như quét toàn bộ index:

SELECT relpages FROM pg_class WHERE relname = 'orders_customer_status_idx';
 relpages
----------
      311

310/311 trang — đúng là gần như toàn bộ index. Lý do vật lý: B-tree sắp theo customer_id trước, nên các dòng có status = 'paid' nằm rải rác khắp mọi nơi trong cây (mỗi nhóm customer_id đều có thể có vài dòng 'paid'), không gom lại được ở một vùng liên tục — Postgres buộc phải duyệt gần hết cây để tìm đủ. Ngược lại, mọi dòng có customer_id = 42 nằm liền kề nhau trong cây, tra thẳng tới đúng vị trí bằng vài bước so sánh.

Thứ tự cột: đặt cột selective nhất lên trước — nhưng không phải luôn luôn

Trực giác phổ biến: đặt cột lọc nhiều nhất (cardinality cao — như customer_id, hàng nghìn giá trị riêng biệt) lên trước để index “cắt” được nhiều nhất càng sớm càng tốt. Đúng, nhưng có ngoại lệ quan trọng: thứ tự chỉ thực sự ảnh hưởng khi có query lọc theo một trong các cột riêng lẻ như minh hoạ trên. Nếu mọi query trong ứng dụng luôn lọc đồng thời cả customer_id và status cùng lúc, thứ tự khai báo gần như không ảnh hưởng tới hiệu năng — B-tree tìm đúng vị trí bằng cả 2 điều kiện dù đặt cột nào trước.

Covering Index với INCLUDE

Query cần thêm cột total (không nằm trong key của index thường), so sánh trực tiếp 2 tình huống trên cùng 1 điều kiện WHERE:

Không có INCLUDE — index chỉ biết (customer_id, status), phải quay lại heap lấy total:

EXPLAIN (ANALYZE, BUFFERS) SELECT customer_id, status, total FROM orders
WHERE customer_id = 42 AND status = 'paid';
Bitmap Heap Scan on orders
  Recheck Cond: ((customer_id = 42) AND (status = 'paid'::text))
  Heap Blocks: exact=38
  Buffers: shared hit=38 read=3
  ->  Bitmap Index Scan on orders_customer_status_idx
        Buffers: shared read=3
Execution Time: 0.243 ms

Có INCLUDE (total) — cùng câu query, cùng dữ liệu:

CREATE INDEX orders_customer_status_covering_idx ON orders (customer_id, status) INCLUDE (total);
EXPLAIN (ANALYZE, BUFFERS) SELECT customer_id, status, total FROM orders
WHERE customer_id = 42 AND status = 'paid';
Index Only Scan using orders_customer_status_covering_idx on orders
  Heap Fetches: 0
  Buffers: shared hit=1 read=3
Execution Time: 0.066 ms

Nhanh gấp ~3.7 lần (0.243ms → 0.066ms), buffer giảm từ 41 xuống 4 — vì total giờ nằm sẵn trong leaf node của index, Heap Fetches: 0 xác nhận không cần chạm vào bảng chính lần nào. total chỉ được lưu kèm (INCLUDE), không tham gia sắp xếp/tra cứu — đây là khác biệt so với đưa hẳn total vào key: index vẫn nhỏ hơn so với đánh index đầy đủ 3 cột, vì phần INCLUDE không cần cấu trúc B-tree đầy đủ cho riêng nó.

Index-Only Scan: khi nào Postgres không cần chạm vào bảng chính

Heap Fetches: 0 ở trên là điều kiện lý tưởng, nhưng có một yêu cầu thực tế hay bị quên: Postgres cần visibility map (bản đồ đánh dấu trang nào “toàn bộ dòng đều visible với mọi transaction”, cập nhật bởi VACUUM) xác nhận trang heap tương ứng an toàn để bỏ qua. Nếu visibility map chưa cập nhật (bảng vừa ghi nhiều, chưa kịp VACUUM), Postgres vẫn phải ghé qua heap để tự xác minh tuple còn hiệu lực hay không — Index-Only Scan trên lý thuyết vẫn chạy nhưng Heap Fetches sẽ khác 0, mất đi phần lớn lợi ích.

Minh hoạ đúng điều này xảy ra thật trong lúc build demo cho bài này: trước khi chạy VACUUM ANALYZE, chính câu query status = 'paid' ở trên không dùng Index-Only Scan mà rơi về Seq Scan — vì visibility map chưa sẵn sàng khiến Index-Only Scan bị đánh giá đắt hơn. Chỉ sau khi VACUUM ANALYZE orders chạy xong, visibility map được cập nhật đầy đủ, plan mới chuyển hẳn sang Index Only Scan với Heap Fetches: 0 như đã thấy. Bài học thực tế: benchmark ngay sau khi seed dữ liệu lớn, chưa VACUUM, có thể cho kết quả bi quan hơn hẳn so với trạng thái ổn định lâu dài của bảng đó trên production (nơi autovacuum đã chạy).

Tự chạy lại demo

docker compose up -d
docker compose exec postgres psql -U demo -d perf_demo

sql/01-setup.sql seed 300.000 dòng orders và tạo sẵn cả 2 loại index. Thử tự DROP INDEX orders_customer_status_covering_idx rồi chạy lại câu query có total để tự thấy khác biệt trước/sau khi có INCLUDE.

docker compose down -v

Tổng kết & bài tiếp theo

Ba điều rút ra: leftmost prefix quyết định index có được dùng hiệu quả (không phải nhị phân dùng/không dùng), INCLUDE cho phép Index-Only Scan mà không cần mở rộng key index, và Index-Only Scan cần VACUUM chạy đều để thực sự phát huy tác dụng — một sợi dây nối trực tiếp về bài 03 mini-series Internals.
