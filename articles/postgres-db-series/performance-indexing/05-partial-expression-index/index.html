05. Partial Index & Expression Index

Oct 2, 2026 · 5 min read

Bài 01 học selectivity quyết định planner có dùng index không. Bài này dùng chính hiểu biết đó để chủ động thiết kế index nhỏ hơn cho đúng phần dữ liệu thực sự cần tra cứu thường xuyên, trên bảng orders 300.000 dòng với status (pending chỉ chiếm ~2%) và email.

Partial Index — chỉ index phần dữ liệu cần

CREATE INDEX orders_status_full_idx ON orders (status);
CREATE INDEX orders_status_pending_idx ON orders (status) WHERE status = 'pending';
SELECT pg_size_pretty(pg_relation_size('orders_status_full_idx')) AS full_idx_size,
       pg_size_pretty(pg_relation_size('orders_status_pending_idx')) AS partial_idx_size;
 full_idx_size | partial_idx_size
---------------+------------------
 2072 kB       | 56 kB

Nhỏ hơn ~37 lần — partial index chỉ chứa 6.054 dòng 'pending', bỏ qua hoàn toàn 294.000 dòng 'done'/'cancelled' mà ứng dụng hiếm khi cần tra theo trạng thái đó. Planner tự động chọn đúng index nhỏ hơn khi điều kiện khớp:

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE status = 'pending';
Bitmap Heap Scan on orders (cost=61.20..2502.57 rows=6270 width=33) (actual time=0.628..3.107 rows=6054 loops=1)
  Heap Blocks: exact=2207
  ->  Bitmap Index Scan on orders_status_pending_idx

So với chỉ dùng index đầy đủ (partial index tạm bị drop để so sánh công bằng):

Bitmap Heap Scan on orders (cost=73.01..2514.39 rows=6270 width=33) (actual time=0.612..3.357 rows=6054 loops=1)
  Heap Blocks: exact=2207
  ->  Bitmap Index Scan on orders_status_full_idx

Thời gian thực thi gần như không khác biệt (3.414ms vs 3.612ms) — điều này cần nói thẳng, không tô hồng: với đúng 1 query này, cả 2 heap block đều phải đọc y hệt nhau (2207 block, vì 6.054 dòng pending rải rác khắp bảng), nên phần “tiết kiệm” ở đây chủ yếu nằm ở kích thước lưu trữ và chi phí bảo trì — index nhỏ hơn nghĩa là mỗi lần INSERT/UPDATE một dòng không phải 'pending' hoàn toàn không cần đụng tới index này, và index nhỏ hơn thì dễ vừa RAM cache hơn khi hệ thống có nhiều index khác cùng cạnh tranh bộ nhớ.

Partial index chỉ dùng được đúng cho điều kiện đã khai báo — không phải “index nhỏ dùng chung cho mọi query trên cột đó”:

EXPLAIN SELECT * FROM orders WHERE status = 'done';
Bitmap Heap Scan on orders (cost=1648.29..5849.79 rows=147080 width=33)
  ->  Bitmap Index Scan on orders_status_full_idx
        Index Cond: (status = 'done'::text)

Tự động rơi về orders_status_full_idx — đúng như kỳ vọng, vì orders_status_pending_idx vật lý không hề chứa dòng nào có status = 'done'.

Expression Index — index trên kết quả tính toán, không phải cột thô

Bài toán kinh điển: so sánh email không phân biệt hoa/thường. Index trên cột thô email không giúp được gì nếu query luôn bọc qua lower():

CREATE INDEX orders_email_lower_idx ON orders (lower(email));
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE lower(email) = 'user123@example.com';
Index Scan using orders_email_lower_idx on orders (cost=0.42..8.44 rows=1 width=33) (actual time=0.033..0.034 rows=1 loops=1)
  Index Cond: (lower(email) = 'user123@example.com'::text)
  Buffers: shared hit=1 read=3
Execution Time: 0.059 ms

Nhưng đổi sang so sánh trực tiếp trên email thô (không qua lower()) — dù thực chất đang tìm đúng 1 dòng đó, chỉ khác cách viết điều kiện:

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE email = 'User123@Example.com';
Gather (cost=1000.00..5568.98 rows=1 width=33) (actual time=0.109..8.707 rows=1 loops=1)
  Workers Planned: 1
  ->  Parallel Seq Scan on orders
        Filter: (email = 'User123@Example.com'::text)
        Rows Removed by Filter: 150000
  Buffers: shared hit=2363
Execution Time: 8.740 ms

Chậm hơn ~148 lần (0.059ms → 8.740ms), phải quét gần hết bảng (2363 buffer) kể cả chạy song song 2 worker. Bài học cốt lõi, dễ mắc lỗi nhất khi dùng expression index: biểu thức trong index phải khớp CHÍNH XÁC với biểu thức trong WHERE — Postgres không tự suy luận email = 'X' tương đương lower(email) = lower('X'), dù về mặt logic ứng dụng chúng “giống nhau”. Sai lệch nhỏ (thiếu lower(), viết LOWER() khác case tham số…) khiến index bị bỏ qua hoàn toàn mà không có cảnh báo nào — chỉ phát hiện được qua EXPLAIN.

Kết hợp cả hai: partial + expression index

Pattern rất phổ biến trong thực tế — soft-delete kèm tra cứu không phân biệt hoa/thường:

CREATE INDEX users_email_active_idx ON users (lower(email)) WHERE deleted_at IS NULL;

Vừa nhỏ (chỉ index user chưa xoá), vừa khớp đúng cách ứng dụng luôn query (WHERE lower(email) = ... AND deleted_at IS NULL) — kết hợp cả hai kỹ thuật trong bài mà không cần đổi schema.

Tự chạy lại demo

docker compose up -d
docker compose exec postgres psql -U demo -d perf_demo

sql/01-setup.sql seed 300.000 dòng orders. Tự tạo lần lượt từng index theo đúng thứ tự trong bài, thử DROP/CREATE lại để so sánh trước/sau như đã trình bày.

docker compose down -v

Tổng kết & bài tiếp theo

Partial index thu nhỏ phạm vi dòng được index; expression index thu nhỏ (và mở rộng) phạm vi biểu thức index hiểu được. Cả hai đều là ứng dụng trực tiếp của bài học selectivity ở bài 01 — chỉ index đúng phần dữ liệu/đúng dạng truy vấn ứng dụng thực sự dùng, thay vì index “cho chắc” mọi cột mọi giá trị.
