Bài cuối mini-series: 5 bài trước tối ưu ở tầng schema/index — bài này tối ưu ở tầng cấu hình instance, nơi vài tham số có thể thay đổi hoàn toàn plan mà không cần sửa 1 dòng SQL nào. Tất cả tham số dưới đây đổi được theo session bằng SET, không cần restart instance — tiện để thử nghiệm trước khi quyết định đổi vĩnh viễn trong postgresql.conf.

work_mem — bộ nhớ cho mỗi thao tác sort/hash

work_mem giới hạn bộ nhớ cho mỗi node sort/hash trong 1 query — không phải tổng cho cả query, càng không phải tổng cho cả connection. Đo thật cùng 1 câu ORDER BY trên 1 triệu dòng, tắt parallel query tạm thời để cô lập đúng 1 biến số:

SET max_parallel_workers_per_gather = 0;
SET work_mem = '1MB';
EXPLAIN (ANALYZE) SELECT region, amount FROM sales ORDER BY amount;
Sort Method: external merge  Disk: 23968kB
Execution Time: 633.807 ms
SET work_mem = '256MB';
EXPLAIN (ANALYZE) SELECT region, amount FROM sales ORDER BY amount;
Sort Method: quicksort  Memory: 63639kB
Execution Time: 395.474 ms

work_mem quá thấp buộc Postgres tràn ra đĩa (external merge Disk) — chậm hơn ~1.6 lần so với sort gọn trong RAM (quicksort Memory) ở demo này, và chênh lệch còn lớn hơn nhiều với dữ liệu lớn hơn hoặc đĩa chậm hơn. Dòng Sort Method trong EXPLAIN ANALYZE là cách chẩn đoán trực tiếp nhất — thấy Disk nghĩa là work_mem đang là nút thắt cổ chai cho đúng query đó.

Lưu ý khi tăng: work_mem áp dụng cho mỗi node sort/hash, và với parallel query, mỗi worker có thể cấp riêng một phần work_mem — 1 query phức tạp (nhiều JOIN/ORDER BY/GROUP BY lồng nhau) chạy song song nhiều worker có thể dùng gấp nhiều lần con số cấu hình. Đặt work_mem quá cao trên toàn instance với nhiều connection đồng thời có thể làm cạn RAM hệ thống — nên cân nhắc đặt riêng theo session (SET work_mem trước 1 câu báo cáo nặng) thay vì đổi mặc định toàn instance nếu chỉ một số query cụ thể cần.

random_page_cost — chi phí tương đối của random I/O

Mặc định 4.0 — giả định random I/O đắt gấp 4 lần sequential I/O, đúng với đĩa cơ (HDD, phải di chuyển đầu đọc vật lý). Trên SSD/NVMe hiện đại, chênh lệch này nhỏ hơn nhiều; giá trị hợp lý hơn thường trong khoảng 1.1-2.0. Đo thật cho cùng 1 query lọc theo điều kiện selectivity vừa phải (region = 'south', ~33% dữ liệu, đã có index):

SET random_page_cost = 4.0;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM sales WHERE region = 'south';
Bitmap Heap Scan on sales (cost=3682.18..14177.59 rows=330033 width=17) (actual time=5.945..39.829 rows=334362 loops=1)
  Buffers: shared hit=6654
Execution Time: 50.711 ms
SET random_page_cost = 1.1;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM sales WHERE region = 'south';
Index Scan using sales_region_idx on sales (cost=0.42..12757.49 rows=330033 width=17) (actual time=0.016..28.293 rows=334362 loops=1)
  Buffers: shared hit=6654
Execution Time: 37.424 ms

Cùng số buffer đọc (6654), nhưng plan đổi hẳn hình dạng: random_page_cost = 4.0 khiến planner chọn Bitmap Heap Scan — chiến lược gom trước các vị trí cần đọc thành bitmap rồi sắp xếp lại để giảm số lần “nhảy” ngẫu nhiên (bù đắp cho random I/O bị coi là đắt); random_page_cost = 1.1 cho phép Index Scan thẳng, đọc index rồi nhảy trực tiếp tới heap không cần bước gom trung gian, vì random I/O giờ được coi là rẻ gần bằng sequential. Nhanh hơn ~26% (50.7ms → 37.4ms) trong demo này — với SSD thật trên production, đặt sai random_page_cost (giữ mặc định 4.0 cho hạ tầng toàn SSD) khiến planner hệ thống hoá thiên vị chiến lược tối ưu cho đĩa cơ trên toàn bộ query trong instance, không chỉ 1 câu lệnh.

Parallel query: khi nào Postgres tự chia việc

max_parallel_workers_per_gather, cùng parallel_setup_cost/parallel_tuple_cost, quyết định planner có đáng “trả giá” (chi phí khởi tạo worker) để chia song song hay không. Trên bảng rất nhỏ:

CREATE TABLE sales_small AS SELECT * FROM sales LIMIT 100;
EXPLAIN (ANALYZE) SELECT sum(amount) FROM sales_small;
Aggregate (cost=22.75..22.76 rows=1 width=32) (actual time=0.019..0.019 rows=1 loops=1)
  ->  Seq Scan on sales_small

Không một worker nào được cân nhắc — chi phí khởi tạo song song còn đắt hơn hẳn lợi ích trên 100 dòng. Cùng phép tính, trên bảng 1 triệu dòng:

EXPLAIN (ANALYZE) SELECT sum(amount) FROM sales;
Finalize Aggregate (cost=12578.56..12578.57 rows=1 width=32) (actual time=39.236..40.724 rows=1 loops=1)
  ->  Gather
        Workers Planned: 2
        Workers Launched: 2
        ->  Partial Aggregate
              ->  Parallel Seq Scan on sales (actual time=0.010..15.968 rows=333333 loops=3)

Planner tự động chia thành 2 worker + 1 process chính, mỗi worker quét và tính tổng riêng một phần (Partial Aggregate), rồi Finalize Aggregate gộp lại — hoàn toàn tự động, không cần bất kỳ chỉ dẫn nào trong câu SQL. Đây chính là cơ chế đứng sau các dòng Workers Launched đã xuất hiện âm thầm ở EXPLAIN của nhiều bài trước trong series.

Tự chạy lại demo

docker compose up -d
docker compose exec postgres psql -U demo -d perf_demo

sql/01-setup.sql seed 1 triệu dòng sales và tạo sẵn index trên region. Toàn bộ tham số trong bài đổi được bằng SET ngay trong session, không cần restart — thử với RESET <tên tham số> để quay lại giá trị mặc định của server.

docker compose down -v
