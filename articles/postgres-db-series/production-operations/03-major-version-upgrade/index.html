03. Major Version Upgrade

Oct 13, 2026 · 6 min read

Series · Postgres Production Operations

  2. 02. Monitoring
  3. 03. Major Version Upgrade
  4. 04. Troubleshooting sự cố production

Monitoring (bài 02) giúp phát hiện vấn đề trong vận hành bình thường. Bài này nói về một thao tác có kế hoạch nhưng rủi ro cao: nâng cấp phiên bản chính (major version) — demo thật nâng cấp từ PostgreSQL 16 lên 17 trong cùng 1 container (kho gói Alpine dùng cho series này không còn giữ bản 15, nhưng cơ chế pg_upgrade giữa bất kỳ 2 major version nào đều giống hệt nhau).

Vì sao major version upgrade không đơn giản như restart

Minor version (16.1 → 16.2) chỉ thay binary — format dữ liệu không đổi, restart là xong. Major version (16 → 17) có thể đổi format lưu trữ nội bộ — không thể chỉ thay binary rồi khởi động lại trên dữ liệu cũ.

pg_upgrade: nhanh hơn dump/restore, nhưng có điều kiện

pg_upgrade cần cả 2 bộ binary (bản cũ + bản mới) truy cập trực tiếp cùng 1 filesystem — không phải thao tác qua mạng như pg_dump. Cách dựng: cài thêm PostgreSQL 17 vào ngay container đang chạy PostgreSQL 16 (image Alpine hỗ trợ cài song song nhiều major version qua gói riêng biệt):

apk add --no-cache postgresql17 postgresql17-contrib

Cạm bẫy thật gặp phải ngay bước này: sau khi cài, gọi thử psql của PG17 báo lỗi:

Error relocating /usr/libexec/postgresql17/psql: PQsetChunkedRowsMode: symbol not found

Nguyên nhân: image gốc có sẵn libpq (bản 16, tại /usr/local/lib) được dynamic linker ưu tiên tìm trước libpq mới hơn Alpine vừa cài (/usr/lib) — binary PG17 bị link nhầm vào thư viện cũ, thiếu hàm nó cần. Fix bằng LD_LIBRARY_PATH=/usr/lib để ép ưu tiên đúng thư viện. Đây là ví dụ thật về loại lỗi “2 phiên bản cùng tồn tại” hay gặp khi chuẩn bị upgrade tại chỗ, không phải lỗi của riêng demo này.

pg_upgrade –check: xác nhận trước khi làm thật

pg_upgrade \
  --old-bindir=/usr/local/bin --new-bindir=/usr/libexec/postgresql17 \
  --old-datadir=/var/lib/postgresql/data --new-datadir=/var/lib/postgresql/data17 \
  --username=demo --check
Checking cluster versions                                     ok
Checking database user is the install user                    ok
Checking database connection settings                         ok
Checking for prepared transactions                            ok
Checking for contrib/isn with bigint-passing mismatch          ok
Checking data type usage                                      ok
Checking for not-null constraint inconsistencies               ok
Checking for presence of required libraries                    ok

*Clusters are compatible*

--check chạy toàn bộ kiểm tra tương thích mà không đụng vào dữ liệu thật — extension không tương thích, kiểu dữ liệu đã bị loại bỏ giữa 2 phiên bản, transaction chưa hoàn tất… tất cả được phát hiện ở đây, trước khi upgrade thật. Bỏ qua bước này nghĩa là chỉ biết được vấn đề giữa lúc đang upgrade — rủi ro hơn nhiều.

Chạy pg_upgrade thật — và đo thời gian thật

Bỏ --check, chạy trên cluster 100.000 dòng:

Performing Upgrade
------------------
...
Restoring database schemas in the new cluster                 ok
Copying user relation files                                   ok
...
Upgrade Complete
----------------
Optimizer statistics are not transferred by pg_upgrade.
Once you start the new server, consider running:
    /usr/libexec/postgresql17/vacuumdb -U demo --all --analyze-in-stages

real    0m 1.61s

1.61 giây cho 100.000 dòng — nhanh hơn hẳn pg_dump/pg_restore (đã thấy ở bài 01 đi qua tầng logic chậm hơn nhiều), vì pg_upgrade chỉ copy trực tiếp file dữ liệu, không đọc lại từng dòng qua SQL. Chú ý dòng cảnh báo tự động: “Optimizer statistics are not transferred by pg_upgrade” — chính là rủi ro quan trọng nhất của toàn bộ quy trình, kiểm chứng ngay bên dưới.

Rủi ro thật: planner “mù” ngay sau upgrade

Khởi động cluster PG17 vừa nâng cấp, thử ngay 1 query quen thuộc trước khi chạy lệnh vacuumdb được khuyến nghị ở trên:

EXPLAIN SELECT * FROM orders WHERE status = 'pending';
Seq Scan on orders (cost=0.00..1440.08 rows=323 width=52)

So với số dòng thực tế khớp điều kiện:

SELECT count(*) FROM orders WHERE status = 'pending';
 count
-------
 25131

Ước lượng 323, thực tế 25131 — sai lệch 78 lần. pg_upgrade copy dữ liệu nhưng không copy pg_statistic — planner trên cluster mới hoàn toàn “mù” về phân bố dữ liệu thật cho tới khi được ANALYZE lại, đúng bài học từ Performance bài 04 về thống kê cũ — chỉ khác ở đây thống kê không “cũ”, mà hoàn toàn không tồn tại. Chạy đúng lệnh pg_upgrade đã khuyến nghị:

vacuumdb -U demo --all --analyze-in-stages
EXPLAIN SELECT * FROM orders WHERE status = 'pending';
Seq Scan on orders (cost=0.00..1883.00 rows=25257 width=18)

25257 so với thực tế 25131 — lệch chưa tới 0.5%. Trên production, khoảng thời gian giữa lúc mở lại traffic sau upgrade và lúc ANALYZE hoàn tất là cửa sổ planner đưa ra quyết định sai — với bảng lớn, query phức tạp, đây có thể là vài phút hiệu năng tệ hẳn ngay sau 1 thao tác tưởng đã “xong”. --analyze-in-stages giảm thiểu điều này bằng cách chạy thống kê thô trước (nhanh, đủ dùng tạm), rồi thống kê đầy đủ sau — không phải chờ ANALYZE đầy đủ mới có được ước lượng tạm chấp nhận được.

Giảm downtime: logical replication để upgrade gần như 0 downtime

pg_upgrade (đo được ở trên) đã rất nhanh, nhưng vẫn cần dừng cluster cũ trong lúc upgrade — downtime tỉ lệ thuận với kích thước dữ liệu (dù nhanh hơn dump/restore nhiều). Để giảm xuống gần 0: dựng instance đích (phiên bản mới) làm logical replica của instance cũ, đợi đồng bộ xong rồi mới switchover — downtime chỉ còn đúng khoảng thời gian switchover (vài giây), không phải toàn bộ thời gian chạy pg_upgrade. Đánh đổi: phức tạp hơn hẳn, cần hạ tầng tạm thời chạy song song trong lúc chuyển đổi.

Tự chạy lại demo

docker compose up -d

Toàn bộ chuỗi lệnh ở trên nằm trong comment của sql/01-setup.sql, chạy tay theo đúng thứ tự (không có script tự động do bản chất thao tác cần dừng/khởi động lại nhiều lần). Do phải dừng cluster cũ giữa chừng, cần docker compose stop postgres rồi docker compose run --rm --entrypoint sh postgres -c "..." cho các bước cần cả 2 bindir, thay vì docker compose exec thông thường.

docker compose down -v

Tổng kết & bài tiếp theo

pg_upgrade nhanh và đáng tin cậy — --check bắt lỗi tương thích trước khi làm thật, và thời gian upgrade thực tế đo được chỉ vài giây cho dữ liệu cỡ vừa. Nhưng “upgrade xong” không có nghĩa là “sẵn sàng nhận traffic đầy đủ” — thống kê planner luôn cần được xây dựng lại, và bỏ qua bước đó là để lại một khoảng thời gian hiệu năng suy giảm ngay sau khi tưởng mọi thứ đã hoàn tất.

Bài 04 giả định điều tệ nhất đã xảy ra dù đã chuẩn bị kỹ — sự cố production thật cần chẩn đoán trực tiếp, không phải kế hoạch trước.
