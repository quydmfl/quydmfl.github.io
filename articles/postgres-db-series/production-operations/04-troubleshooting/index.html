Bài thực dụng nhất mini-series: tái hiện thật 3 sự cố production kinh điển, và quy trình chẩn đoán từng bước bằng chính công cụ đã học xuyên suốt series — không phải danh sách lý thuyết “các loại sự cố thường gặp”.

Lock contention: query bị treo không rõ lý do

Session A giữ lock (chưa commit), session B chờ để UPDATE đúng dòng đó:

-- Session A
BEGIN;
UPDATE accounts SET balance = 90 WHERE id = 1;
SELECT pg_sleep(30);  -- giữ transaction mở, mô phỏng treo bất thường
-- Session B, chạy ngay sau
UPDATE accounts SET balance = 80 WHERE id = 1;  -- treo

Chẩn đoán bằng pg_stat_activity (đúng view đã dùng làm nền cho ops_health ở bài 02):

SELECT pid, state, wait_event_type, now() - query_start AS duration, query
FROM pg_stat_activity WHERE datname = 'appdb' AND pid <> pg_backend_pid();
 pid | state  | wait_event_type |    duration     |                     query
-----+--------+------------------+------------------+------------------------------------------------
  84 | active | Timeout          | 00:00:02.048394 | SELECT pg_sleep(30);
  91 | active | Lock             | 00:00:00.997136 | UPDATE accounts SET balance = 80 WHERE id = 1;

Xác định chính xác PID 84 là thủ phạm — đang trong pg_sleep, giữ transaction mở gần 2 giây và còn tiếp tục. Giải quyết bằng pg_terminate_backend:

SELECT pg_terminate_backend(84);

Session A (bị terminate) — lỗi thật, kết nối bị đóng hẳn:

FATAL:  terminating connection due to administrator command
server closed the connection unexpectedly

Session B — được giải phóng ngay lập tức:

UPDATE 1
SELECT * FROM accounts WHERE id = 1;
 id | owner | balance
----+-------+---------
  1 | alice |   80.00

Kết quả đúng: 80.00 (thay đổi của session B) — thay đổi 90.00 của session A tự động rollback vì transaction chưa kịp commit khi bị terminate.

pg_cancel_backend — nhẹ hơn, giữ lại session

pg_terminate_backend đóng hẳn kết nối. Khi chỉ cần huỷ đúng câu query đang chạy (không phải cả session — ví dụ session đó còn transaction/state cần giữ), dùng pg_cancel_backend:

-- Session khác đang chạy: SELECT pg_sleep(30);
SELECT pg_cancel_backend(<pid>);

Session bị cancel — lỗi ở đúng câu lệnh, nhưng session sống sót, chạy tiếp câu lệnh kế tiếp bình thường:

ERROR:  canceling statement due to user request
                 status
------------------------------------------
 session vẫn còn sống sau khi bị cancel

Quy tắc chọn: pg_cancel_backend trước — ít phá huỷ hơn, đủ dùng cho phần lớn trường hợp (huỷ 1 query chạy sai/quá lâu). Chỉ dùng pg_terminate_backend khi cần chắc chắn dọn sạch toàn bộ session (transaction treo hẳn, hoặc pg_cancel_backend không có tác dụng vì session đang ở trạng thái không phản hồi cancel).

Runaway query: 1 câu query ăn hết CPU

JOIN thiếu điều kiện tạo cartesian product — 100.000 × 100.000 = 10 tỷ dòng cần tính:

SELECT count(*) FROM orders o1, orders o2;

Phát hiện qua pg_stat_activity trong lúc đang chạy — 3 process (parallel worker) cùng chiếm CPU:

SELECT pid, now() - query_start AS duration, state, query
FROM pg_stat_activity WHERE datname = 'appdb' AND state = 'active';
 pid |    duration     | state  |                   query
-----+------------------+--------+---------------------------------------------
 134 | 00:00:02.000295 | active | SELECT count(*) FROM orders o1, orders o2;
 135 | 00:00:02.000295 | active | SELECT count(*) FROM orders o1, orders o2;
 136 | 00:00:02.000295 | active | SELECT count(*) FROM orders o1, orders o2;

Phát hiện được là một chuyện — nhưng trông chờ con người kịp thấy trước khi hệ thống bị ảnh hưởng nghiêm trọng là không đủ tin cậy. statement_timeout chặn cứng tự động:

SET statement_timeout = '2s';
SELECT count(*) FROM orders o1, orders o2;
ERROR:  canceling statement due to statement timeout

Tự huỷ sau đúng 2 giây, không cần ai can thiệp. Đặt statement_timeout hợp lý ở tầng role/database (khác nhau cho role ứng dụng thông thường vs role chạy báo cáo/batch) là biện pháp phòng ngừa hiệu quả hơn hẳn việc chỉ trông chờ phát hiện kịp thời.

Disk full: sự cố nghiêm trọng nhất, dễ tái diễn nhất

Mô phỏng an toàn bằng container riêng, giới hạn dung lượng thật qua tmpfs:

docker run -d --name pg-diskfull-test \
  --tmpfs /var/lib/postgresql/data:size=150m,uid=70,gid=70 \
  -e POSTGRES_USER=demo -e POSTGRES_PASSWORD=demo -e POSTGRES_DB=appdb postgres:16-alpine

Tạo tải ghi lớn:

CREATE TABLE filler (id SERIAL PRIMARY KEY, payload TEXT);
INSERT INTO filler (payload) SELECT repeat('x', 1000) FROM generate_series(1, 200000);
ERROR:  could not extend file "base/16384/16386": No space left on device
HINT:  Check free disk space.

Lỗi thật, đúng như production — df xác nhận đĩa đã đầy 98%:

Filesystem   Size   Used  Available  Use%
tmpfs        150.0M 147.3M    2.7M    98%

Điều quan trọng cần biết: Postgres không crash khi hết dung lượng — chỉ transaction ghi đang thực hiện thất bại (và tự động rollback, count(*) vẫn trả về 0 sau đó, không có dữ liệu nửa vời). Đọc dữ liệu vẫn hoạt động bình thường:

SELECT count(*) FROM filler;
 count
-------
     0

Khôi phục an toàn — dọn bớt dữ liệu không cần thiết để lấy lại chỗ trống, không phải xoá file WAL bằng tay (sẽ phá hỏng khả năng phục hồi, đúng bài học bài 01):

DROP TABLE filler;
Filesystem   Size   Used   Available  Use%
tmpfs        150.0M 93.6M     56.4M    62%

Ghi thử lại — hoạt động bình thường:

CREATE TABLE t2 (id INT);
INSERT INTO t2 VALUES (1);
CREATE TABLE
INSERT 0 1

Nguyên nhân phổ biến nhất dẫn tới disk full trên production không phải tăng trưởng dữ liệu tự nhiên (dễ dự đoán, dễ lên kế hoạch) — mà là archive_command lỗi âm thầm khiến WAL tích luỹ vô hạn trong pg_wal/ (đúng lỗi thật đã gặp ở bài 01), hoặc bloat không được VACUUM kịp (Internals bài 03). Cả hai đều được ops_health (bài 02) phát hiện sớm — archive_failed_count và max_dead_tup_any_table — trước khi tiến triển thành disk full thật.

Tự chạy lại demo

docker compose up -d
docker compose exec postgres psql -U demo -d appdb

sql/01-setup.sql seed dữ liệu cho 2 sự cố đầu. Chi tiết đầy đủ (kể cả lệnh dựng container riêng cho phần disk full) nằm trong comment của file đó — chạy tay 2 session song song ở 2 terminal để tự cảm nhận đúng thứ tự sự kiện.

docker compose down -v
docker rm -f pg-diskfull-test  # nếu đã chạy phần disk full

Tổng kết & bài tiếp theo

Cả 3 sự cố đều có chung một mẫu số: pg_stat_activity là điểm bắt đầu chẩn đoán cho gần như mọi vấn đề runtime, và phòng ngừa tự động (statement_timeout, monitoring chủ động) luôn đáng tin cậy hơn trông chờ phát hiện kịp thời bằng mắt người.
