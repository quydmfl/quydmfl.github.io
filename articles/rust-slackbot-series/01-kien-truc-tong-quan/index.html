Mở đầu series: đi qua kiến trúc của 1 dự án Rust thật — vuonweb/slackbot, 1 Slack bot dịch tin nhắn đa ngôn ngữ. Bài toán cụ thể: ai đó react emoji cờ (flag-vn flag-us flag-jp…) vào 1 tin nhắn trong kênh Slack, bot nhận event, fetch nội dung tin nhắn gốc, dịch sang ngôn ngữ tương ứng với lá cờ, rồi reply bản dịch ngay trong thread của tin nhắn đó.

Series này giả định bạn đã biết Rust cơ bản: ownership/borrowing, struct/enum, Result/Option, và đã tự tay viết được vài chương trình nhỏ. Không dạy lại cú pháp — dạy qua ví dụ thật: mỗi bài mở 1 phần của project thật này, đọc code thật, chạy thử thật, giải thích tại sao code được tổ chức như vậy chứ không phải cách khác.

Cargo workspace: biên giới module do compiler ép buộc

Cargo.toml ở gốc project:

[workspace]
resolver = "2"
members = [
    "crates/kernel",
    "crates/translation",
    "crates/slack_gateway",
    "crates/app",
]

[workspace.package]
version = "0.1.0"
edition = "2021"

[workspace.dependencies]
tokio = { version = "1", features = ["full"] }
axum = "0.7"
serde = { version = "1", features = ["derive"] }
serde_json = "1"
reqwest = { version = "0.12", features = ["json"] }
async-trait = "0.1"
thiserror = "1"
anyhow = "1"
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }
dotenvy = "0.15"
hmac = "0.12"
sha2 = "0.10"
hex = "0.4"

[workspace] members khai 4 crate riêng biệt — không phải 4 module trong cùng 1 crate. Khác biệt này quan trọng hơn vẻ ngoài của nó: muốn crate slack_gateway gọi được code trong crate translation, slack_gateway phải khai translation = { path = "../translation" } (hoặc qua workspace.dependencies) tường minh trong Cargo.toml của chính nó. Không khai — không compile được, chấm hết.

So với module cùng 1 crate (mod a; mod b;) — nơi chỉ cần đúng từ khoá pub là b gọi được vào a, không cần khai báo gì thêm ở cấp “package” — ranh giới giữa module dễ bị xói mòn dần theo thời gian: thêm 1 use crate::a::internal_helper là xong, compiler không phàn nàn gì. Ranh giới giữa crate thì khác: nó nằm ở Cargo.toml, compiler ép buộc — không có cách nào lách qua bằng cách chỉnh sửa 1 file .rs. [workspace.dependencies] ở trên là nơi khai version dùng chung (tokio, axum, serde…) để 4 crate không lệch version với nhau; từng crate con vẫn phải tự [dependencies] tham chiếu vào workspace nếu cần dùng thư viện đó.

Modular monolith, không phải microservices

4 crate — kernel, translation, slack_gateway, app — build chung thành 1 binary duy nhất (crates/app), deploy 1 process duy nhất. Không có network call giữa translation và slack_gateway, không có serialization qua lại giữa 2 “service” — gọi hàm trực tiếp trong cùng 1 process, nhanh như gọi hàm bình thường vì đúng là gọi hàm bình thường.

Nhưng ranh giới code giữa translation và slack_gateway rõ ràng gần như 2 service tách biệt thật sự — nhờ đúng cơ chế Cargo workspace ở trên: mỗi crate có Cargo.toml riêng, dependency riêng, và (sẽ thấy ở phần sau) chỉ được import đúng 1 “cửa” công khai của crate kia.

Đây là điểm mấu chốt của lối kiến trúc modular monolith: giữ kỷ luật ranh giới module chặt như thể sắp tách microservices, nhưng chưa trả giá cho sự phức tạp phân tán (network timeout, retry, serialization, service discovery…) khi hệ thống chưa thật sự cần scale từng phần độc lập. Nếu sau này translation cần tách thành 1 service riêng (ví dụ để scale số lượng request dịch độc lập với số lượng Slack event), việc tách ra dễ hơn nhiều so với tách 1 codebase module lẫn lộn — vì ranh giới interface đã tồn tại sẵn từ đầu, chỉ cần thay lời gọi hàm bằng lời gọi HTTP/gRPC.

Clean Architecture rút gọn: domain → application → infrastructure

Bên trong translation và slack_gateway, mỗi crate tự chia làm 3 module con. crates/translation/src/lib.rs:

//! `translation` module — bounded context responsible for turning text in one
//! language into text in another. Consumers outside this module should only
//! ever touch `application` (the public port + use case); `infrastructure`
//! holds swappable adapters (LibreTranslate today) and is wired in only by
//! the composition root in `crates/app`.

pub mod application;
pub mod domain;
pub mod infrastructure;

crates/slack_gateway/src/lib.rs:

//! `slack_gateway` module — bounded context for everything Slack: receiving
//! Events API callbacks, talking to the Slack Web API, and the one use case
//! that ties a reaction to a translation. Depends on `translation`'s public
//! `application` port only — never on `translation::infrastructure`.

pub mod application;
pub mod domain;
pub mod infrastructure;

3 module này không phải cách đặt tên tuỳ ý — đó là bản rút gọn của Clean Architecture, với 1 quy tắc phụ thuộc 1 chiều duy nhất:

  • domain: kiểu dữ liệu và logic nghiệp vụ thuần tuý. Không phụ thuộc bất kỳ thư viện nào thuộc về hạ tầng — không async-trait (không có gì bất đồng bộ ở tầng này), không reqwest (không gọi mạng), không axum/serde (không biết gì về HTTP hay serialization). Vẫn có 2 phụ thuộc được cho phép, và cả 2 đều xuất hiện thật trong code: translation::domain::error dùng thiserror để định nghĩa enum lỗi của chính nó (#[derive(Debug, thiserror::Error)] pub enum TranslationError); còn translation::domain::translation và slack_gateway::domain::emoji_lang đều use kernel::LanguageCode — kiểu giá trị dùng chung nằm ở kernel (bài sau sẽ nói kỹ). Ranh giới thật của tầng domain không phải “zero dependency”, mà là “không phụ thuộc bất cứ thứ gì thuộc về công nghệ hạ tầng cụ thể” — thiserror chỉ là tiện ích khai báo lỗi, kernel là kiểu dữ liệu dùng chung giữa các bounded context chứ không phải 1 adapter hạ tầng, nên cả 2 đều không vi phạm quy tắc phụ thuộc 1 chiều. Đây là phần “sự thật nghiệp vụ” không đổi dù mai sau đổi framework HTTP hay đổi nhà cung cấp dịch thuật.
  • application: định nghĩa port — 1 trait mô tả “cần làm được việc gì” (ví dụ: “dịch được 1 đoạn text”) — và use case dùng domain + gọi qua port đó. application biết cần gì, không biết ai làm việc đó.
  • infrastructure: implement port của application bằng công nghệ cụ thể — gọi LibreTranslate qua reqwest, hoặc expose HTTP endpoint bằng axum. Đây là nơi duy nhất được phép “bẩn” với thư viện ngoài.

Phụ thuộc chỉ đi 1 chiều: infrastructure phụ thuộc application phụ thuộc domain — không bao giờ ngược lại. domain không hề biết infrastructure tồn tại.

Quy tắc quan trọng nhất của toàn bộ project, và cũng là lý do 2 dòng docstring trên tồn tại: slack_gateway chỉ được import translation::application, không bao giờ đụng vào translation::infrastructure. slack_gateway cần dịch text — nó gọi qua port mà translation::application expose, không quan tâm phía sau port đó là LibreTranslate, Google Translate hay bất kỳ thứ gì khác. Đổi nhà cung cấp dịch thuật (thay translation::infrastructure::libretranslate bằng 1 adapter khác) không đụng 1 dòng nào trong slack_gateway — đó chính là lợi ích thực dụng của dependency inversion, không phải lý thuyết suông.

Build thử — xác nhận project chạy được

rustc --version && cargo --version
rustc 1.94.1 (e408947bf 2026-03-25)
cargo 1.94.1 (29ea6fb6a 2026-03-24)
cd /path/to/slackbot && cargo build --workspace
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.22s

Không thấy dòng Compiling nào — vì lần build này chạy trên artifact đã cache sẵn từ những lần trước, và Cargo nhận ra chưa có gì thay đổi trong cả 4 crate nên không biên dịch lại dòng nào. Một build thực sự “sạch” — ví dụ ngay sau khi git clone project này về, trước khi có bất kỳ cache nào — sẽ trông khác hẳn: hàng trăm dòng Compiling <tên crate>, vì Cargo phải biên dịch toàn bộ dependency graph trước — tokio, axum, hyper, reqwest, serde, và hàng chục crate transitive khác. 4 dòng Compiling kernel, Compiling translation, Compiling slack_gateway, Compiling app vẫn xuất hiện, nhưng nằm ở CUỐI danh sách đó chứ không phải toàn bộ nội dung console — đúng vì Cargo build theo thứ tự dependency graph từ dưới lên, và 4 crate của workspace này nằm ở đỉnh graph, phụ thuộc vào gần như mọi crate bên dưới. Điều đáng chú ý hơn cả thời gian build: 1 dependency vòng (circular dependency) giữa các crate trong workspace không phải thứ Cargo chỉ cảnh báo — đó là lỗi build cứng (error: cyclic package dependency), khiến cargo build thất bại hoàn toàn chứ không chạy tiếp được. Build cache sẵn ở trên chỉ chứng minh đúng 1 điều: dependency graph HIỆN TẠI của project không có vòng lặp nào — nó không nói gì về console sẽ hiện ra sao trong 1 lần build từ-đầu, đó là 1 khẳng định khác hẳn. Ranh giới phụ thuộc 1 chiều đã trình bày ở trên mới là lý do graph này không có vòng lặp, không phải nhờ Cargo “cảnh báo” gì cả.

Tổng kết & bài tiếp theo

3 điều cốt lõi của bài này, mọi bài sau đều mặc định bạn đã nắm: Cargo workspace tách 4 crate với ranh giới do compiler ép buộc qua Cargo.toml, không phải quy ước bằng lời; đây là 1 modular monolith — build/deploy như 1 khối nhưng giữ kỷ luật ranh giới như nhiều service tách biệt; và mỗi crate nghiệp vụ (translation, slack_gateway) tổ chức theo Clean Architecture rút gọn domain → application → infrastructure, với quy tắc bất di bất dịch: không crate nào được đụng vào infrastructure của crate khác.
