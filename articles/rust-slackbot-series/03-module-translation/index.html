Bài 02 mổ xẻ kernel — cực nhỏ, chỉ 3 thành phần dùng chung, trong đó có LanguageCode: value object tự validate, đại diện cho 1 mã ngôn ngữ ISO 639-1 hợp lệ. Bài này xây module đầu tiên thật sự dùng nó: translation — bounded context chịu trách nhiệm dịch văn bản, đủ cả 3 lớp domain/application/infrastructure như đã hứa ở bài 01.

Domain: Translation + TranslationError

crates/translation/src/domain/translation.rs:

use kernel::LanguageCode;

/// The core entity of this module: the outcome of translating some text.
#[derive(Debug, Clone)]
pub struct Translation {
    pub original_text: String,
    pub translated_text: String,
    pub source_lang: Option<LanguageCode>,
    pub target_lang: LanguageCode,
}

crates/translation/src/domain/error.rs:

#[derive(Debug, thiserror::Error)]
pub enum TranslationError {
    #[error("translation provider request failed: {0}")]
    ProviderRequestFailed(String),
    #[error("translation provider returned an unexpected response: {0}")]
    UnexpectedResponse(String),
    #[error("text to translate is empty")]
    EmptyText,
}

crates/translation/src/domain/mod.rs:

mod error;
mod translation;

pub use error::TranslationError;
pub use translation::Translation;

Nhìn kỹ phần use ở đầu 2 file: translation.rs chỉ import kernel::LanguageCode, error.rs không import gì ngoài thiserror. Không async-trait, không reqwest, không serde. Domain của module này là struct và enum thuần Rust cộng đúng 2 ngoại lệ đã thống nhất từ bài 01 — kernel (vì Translation cần khái niệm ngôn ngữ) và thiserror (công thức chuẩn cho lỗi trong ranh giới module, không phải infra thật). Domain không biết HTTP là gì, không biết LibreTranslate tồn tại, không biết async runtime nào đang chạy. Translation là entity — kết quả của 1 lượt dịch: văn bản gốc, văn bản đã dịch, ngôn ngữ nguồn (có thể không biết trước, nên Option<LanguageCode>), ngôn ngữ đích (luôn phải có, không Option). TranslationError liệt kê đúng 3 cách việc dịch có thể thất bại: gọi provider lỗi, provider trả về thứ không hiểu được, hoặc văn bản đầu vào rỗng.

Application: 2 loại port

crates/translation/src/application/ports.rs:

use async_trait::async_trait;
use kernel::LanguageCode;

use crate::domain::{Translation, TranslationError};

/// Outbound port: whatever external engine actually performs translation.
/// Implement this trait to add a new provider (DeepL, Claude, Google...);
/// nothing else in this module — or in consumers of `TranslateText` — needs
/// to change.
#[async_trait]
pub trait TranslationProviderPort: Send + Sync {
    async fn translate(
        &self,
        text: &str,
        target_lang: &LanguageCode,
        source_lang: Option<&LanguageCode>,
    ) -> Result<Translation, TranslationError>;
}

/// Inbound port: this module's public API. Other modules (e.g. `slack_gateway`)
/// and any future entry point depend on this trait, never on a concrete
/// provider or on `translation::infrastructure` directly.
#[async_trait]
pub trait TranslateText: Send + Sync {
    async fn execute(&self, cmd: TranslateTextCommand) -> Result<Translation, TranslationError>;
}

#[derive(Debug, Clone)]
pub struct TranslateTextCommand {
    pub text: String,
    pub target_lang: LanguageCode,
    pub source_lang: Option<LanguageCode>,
}

File này định nghĩa 2 trait, và chúng đứng ở 2 hướng ngược nhau — dễ nhầm nếu chỉ đọc lướt.

TranslationProviderPort là outbound port: hướng từ translation đi ra ngoài, tới 1 engine dịch thuật cụ thể nào đó. Ai implement trait này là 1 provider — LibreTranslate hôm nay, DeepL hay Google Translate nếu đổi sau này. Module translation gọi qua trait này, không quan tâm bên dưới là ai.

TranslateText là inbound port: hướng từ ngoài đi vào translation. Ai gọi qua trait này là 1 consumer — ví dụ slack_gateway ở bài 04. Đây là API công khai duy nhất của module: consumer gọi TranslateText::execute, không bao giờ gọi thẳng vào use case cụ thể hay đụng vào translation::infrastructure. TranslateTextCommand là tham số đầu vào của lệnh gọi đó — gói gọn văn bản cần dịch, ngôn ngữ đích, ngôn ngữ nguồn tuỳ chọn.

Cả 2 trait đều cần #[async_trait]. Lý do: tại thời điểm project này viết, Rust ở kênh stable chưa hỗ trợ đầy đủ async fn bên trong trait khi trait đó cần dùng như dyn Trait (trait object) — trường hợp bắt buộc phải có ở đây, vì TranslateTextUseCase sẽ giữ 1 Arc<dyn TranslationProviderPort> chứ không phải kiểu cụ thể. Macro async_trait giải quyết việc này bằng cách biến đổi async fn thành 1 hàm trả về Pin<Box<dyn Future>> ở tầng expand-macro, cho phép trait chứa hàm async vẫn dùng được như trait object.

TranslateTextUseCase: dependency inversion bằng Arc<dyn Trait>

crates/translation/src/application/translate_text.rs:

use async_trait::async_trait;
use std::sync::Arc;

use crate::application::ports::{TranslateText, TranslateTextCommand, TranslationProviderPort};
use crate::domain::{Translation, TranslationError};

/// The one use case this module exposes today. Depends only on the outbound
/// port — the concrete provider (LibreTranslate, DeepL, ...) is injected at
/// the composition root (`crates/app`), never referenced here.
pub struct TranslateTextUseCase {
    provider: Arc<dyn TranslationProviderPort>,
}

impl TranslateTextUseCase {
    pub fn new(provider: Arc<dyn TranslationProviderPort>) -> Self {
        Self { provider }
    }
}

#[async_trait]
impl TranslateText for TranslateTextUseCase {
    async fn execute(&self, cmd: TranslateTextCommand) -> Result<Translation, TranslationError> {
        if cmd.text.trim().is_empty() {
            return Err(TranslationError::EmptyText);
        }

        self.provider
            .translate(&cmd.text, &cmd.target_lang, cmd.source_lang.as_ref())
            .await
    }
}

crates/translation/src/application/mod.rs:

pub mod ports;
mod translate_text;

pub use ports::{TranslateText, TranslateTextCommand, TranslationProviderPort};
pub use translate_text::TranslateTextUseCase;

TranslateTextUseCase là use case duy nhất module này có tính tới thời điểm này, và toàn bộ state của nó gói trong đúng 1 field: provider: Arc<dyn TranslationProviderPort>. Không phải LibreTranslateAdapter, không phải kiểu cụ thể nào — dyn TranslationProviderPort, kiểu trừu tượng. Đây là dependency inversion đúng nghĩa: theo hướng phụ thuộc thông thường, code gọi (use case) phải biết code bị gọi (provider cụ thể) là gì. Ở đây quan hệ bị đảo ngược — use case chỉ biết 1 trait, còn provider cụ thể nào implement trait đó là chi tiết bị giấu kín, quyết định ở nơi khác (composition root, crates/app, sẽ gặp ở các bài sau) rồi tiêm vào qua new().

Arc (Atomically Reference Counted) cần thiết vì 1 provider có thể được nhiều use case hoặc nhiều request đồng thời cùng giữ tham chiếu tới, và bản thân use case cũng cần Send + Sync để chạy an toàn trên executor đa luồng của Tokio — 2 bound đã khai báo sẵn ngay trên trait TranslationProviderPort: Send + Sync.

Logic nghiệp vụ trong execute cực ngắn: kiểm tra văn bản rỗng (cmd.text.trim().is_empty()) trước khi gọi ra ngoài — trả TranslationError::EmptyText ngay tại use case, không tốn 1 lượt gọi HTTP vô ích tới provider chỉ để nhận lại lỗi tương tự. Qua được kiểm tra này, phần còn lại chỉ là ủy quyền thẳng cho self.provider.translate(...) và trả nguyên kết quả về. Use case không biết (và không cần biết) đây là LibreTranslate hay DeepL — nó chỉ biết “có 1 thứ gì đó implement TranslationProviderPort”.

Infrastructure: LibreTranslateAdapter

crates/translation/src/infrastructure/libretranslate.rs:

use async_trait::async_trait;
use kernel::LanguageCode;
use serde::{Deserialize, Serialize};

use crate::application::ports::TranslationProviderPort;
use crate::domain::{Translation, TranslationError};

/// Adapter for a LibreTranslate instance (https://github.com/LibreTranslate/LibreTranslate),
/// self-hosted or public. This is the *only* file in the codebase that knows
/// LibreTranslate's HTTP shape. To switch providers, add a sibling adapter
/// implementing `TranslationProviderPort` and rewire `crates/app` — this file
/// and everything depending on `TranslationProviderPort` stays untouched.
pub struct LibreTranslateAdapter {
    http: reqwest::Client,
    base_url: String,
    api_key: Option<String>,
}

impl LibreTranslateAdapter {
    pub fn new(base_url: impl Into<String>, api_key: Option<String>) -> Self {
        Self {
            http: reqwest::Client::new(),
            base_url: base_url.into(),
            api_key,
        }
    }
}

#[derive(Serialize)]
struct LibreTranslateRequest<'a> {
    q: &'a str,
    source: &'a str,
    target: &'a str,
    format: &'static str,
    #[serde(skip_serializing_if = "Option::is_none")]
    api_key: Option<&'a str>,
}

#[derive(Deserialize)]
struct LibreTranslateResponse {
    #[serde(rename = "translatedText")]
    translated_text: String,
    #[serde(rename = "detectedLanguage")]
    detected_language: Option<DetectedLanguage>,
}

#[derive(Deserialize)]
struct DetectedLanguage {
    language: String,
}

#[async_trait]
impl TranslationProviderPort for LibreTranslateAdapter {
    async fn translate(
        &self,
        text: &str,
        target_lang: &LanguageCode,
        source_lang: Option<&LanguageCode>,
    ) -> Result<Translation, TranslationError> {
        let source = source_lang.map(|l| l.as_str()).unwrap_or("auto");

        let body = LibreTranslateRequest {
            q: text,
            source,
            target: target_lang.as_str(),
            format: "text",
            api_key: self.api_key.as_deref(),
        };

        let resp = self
            .http
            .post(format!("{}/translate", self.base_url))
            .json(&body)
            .send()
            .await
            .map_err(|e| TranslationError::ProviderRequestFailed(e.to_string()))?;

        if !resp.status().is_success() {
            let status = resp.status();
            let body_text = resp.text().await.unwrap_or_default();
            return Err(TranslationError::ProviderRequestFailed(format!(
                "libretranslate returned {status}: {body_text}"
            )));
        }

        let parsed: LibreTranslateResponse = resp
            .json()
            .await
            .map_err(|e| TranslationError::UnexpectedResponse(e.to_string()))?;

        let detected_source = parsed
            .detected_language
            .and_then(|d| LanguageCode::new(d.language).ok());

        Ok(Translation {
            original_text: text.to_string(),
            translated_text: parsed.translated_text,
            source_lang: source_lang.cloned().or(detected_source),
            target_lang: target_lang.clone(),
        })
    }
}

crates/translation/src/infrastructure/mod.rs:

mod libretranslate;

pub use libretranslate::LibreTranslateAdapter;

Docstring trên LibreTranslateAdapter nói thẳng vai trò của file này: đây là file duy nhất trong toàn bộ codebase biết hình dạng HTTP request/response của LibreTranslate. Bằng chứng nằm ngay trong 3 struct riêng: LibreTranslateRequest (q, source, target, format, api_key — đúng field LibreTranslate API yêu cầu), LibreTranslateResponse (đọc translatedText/detectedLanguage — chú ý #[serde(rename = ...)] để map từ camelCase JSON của LibreTranslate sang snake_case Rust), và DetectedLanguage lồng bên trong. Cả 3 struct này đều không pub ra ngoài — không xuất hiện trong chữ ký hàm translate(), không lộ ra pub use ở mod.rs. Consumer của TranslationProviderPort chỉ thấy &str, &LanguageCode, Result<Translation, TranslationError> — không thấy LibreTranslateRequest tồn tại.

Thân hàm translate() làm đúng việc 1 adapter phải làm: dịch giữa 2 thế giới. Nhận input miền chung (&str, &LanguageCode) → build request theo hình dạng LibreTranslate cần (kể cả quy ước riêng của nó: không có source_lang thì gửi chuỗi "auto" để LibreTranslate tự nhận diện) → gọi HTTP qua reqwest → parse response JSON → convert ngược lại thành Translation, kiểu domain chung. Kiểm tra !resp.status().is_success() xử lý lỗi tầng HTTP (4xx/5xx) tách biệt khỏi lỗi parse JSON — 2 nhánh lỗi map vào 2 biến thể khác nhau của TranslationError (ProviderRequestFailed cho cả lỗi mạng lẫn HTTP status xấu, UnexpectedResponse cho JSON không parse được). Dòng LanguageCode::new(d.language).ok() đáng chú ý: ngôn ngữ do LibreTranslate tự nhận diện vẫn phải đi qua LanguageCode::new() — validate lại, không tin thẳng chuỗi trả về từ bên ngoài — đúng nguyên tắc “validate ở biên” đã nói ở bài 02.

Nếu 1 ngày cần đổi sang DeepL: viết 1 file mới, ví dụ deepl.rs, định nghĩa struct riêng cho request/response shape của DeepL, implement TranslationProviderPort cho nó, rồi đổi 1 dòng ở composition root từ LibreTranslateAdapter::new(...) thành DeepLAdapter::new(...). Không sửa gì ở application hay domain. Đó chính là cái giá — và cái lợi — của outbound port: chi phí trả trước là phải viết 1 trait và ép mọi thứ đi qua nó, đổi lại là thay provider mà không chạm code nghiệp vụ.

Build sạch, nhưng để ý dòng running 0 tests lặp lại 2 lần — cả unit test lẫn doc-test đều 0. Không phải thiếu sót bỏ quên, mà là thực trạng đúng của module này ở giai đoạn hiện tại: translation chưa có unit test riêng nào.

Vì sao vẫn chấp nhận được? Vì cách module này được thiết kế — toàn bộ logic nghiệp vụ thật sự đáng test (kiểm tra text rỗng, ủy quyền cho provider) nằm trong TranslateTextUseCase, và use case đó chỉ phụ thuộc vào trait TranslationProviderPort, không phụ thuộc LibreTranslateAdapter cụ thể. Điều đó có nghĩa: muốn test TranslateTextUseCase::execute, không cần LibreTranslate thật chạy, không cần mạng — chỉ cần 1 struct giả (stub) implement TranslationProviderPort, trả về giá trị cố định. Bài 04, khi slack_gateway::HandleReactionUseCase gọi TranslateText, sẽ thấy đúng kiểu test này xuất hiện: 1 stub triển khai TranslateText (hoặc TranslationProviderPort, tuỳ tầng cần test), gán vào Arc<dyn ...>, rồi assert hành vi của use case gọi nó — test gián tiếp module translation thông qua port, không đụng LibreTranslateAdapter hay mạng thật.

Nói cách khác: 0 test ở đây không phải nợ kỹ thuật bị bỏ quên — nó phản ánh đúng nguyên tắc test theo port đã bàn ở trên. Adapter (LibreTranslateAdapter) là phần khó test nhất vì đụng HTTP thật; use case là phần dễ test nhất vì chỉ phụ thuộc trait. Module translation hiện đặt cược test coverage vào việc tầng tiêu thụ nó test qua stub — cách tiếp cận hợp lý cho 1 use case đơn giản, nhưng cũng là điểm cần nhớ nếu sau này thêm logic nghiệp vụ phức tạp hơn vào TranslateTextUseCase: lúc đó nên có unit test riêng ngay trong crates/translation, không chỉ dựa vào test gián tiếp từ module khác.

Tổng kết & bài tiếp theo

Module translation đủ 3 lớp: domain (Translation, TranslationError — thuần Rust, không infra), application (2 port ngược hướng nhau — TranslationProviderPort outbound, TranslateText inbound — và TranslateTextUseCase nối chúng lại bằng Arc<dyn Trait>), infrastructure (LibreTranslateAdapter — nơi duy nhất biết HTTP shape của LibreTranslate). #[async_trait] là mảnh ghép kỹ thuật bắt buộc để cả 2 trait dùng được như trait object. Toàn bộ kiến trúc tồn tại để trả lời đúng 1 câu hỏi: đổi provider dịch có phải sửa use case không? Không — chỉ cần 1 file adapter mới.

Bài 04 chuyển sang slack_gateway — domain và application của module thứ 2, module sẽ gọi translation::application::TranslateText từ HandleReactionUseCase, và lần đầu tiên dùng stub để test dependency inversion vừa xây ở đây.
