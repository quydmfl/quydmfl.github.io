Bài 03 khép lại module translation với đúng 1 API công khai: translation::application::TranslateText. Consumer nào cần dịch chỉ cần gọi execute() qua trait đó, không cần biết bên dưới là LibreTranslate hay provider nào khác. Bài này xây module thứ 2, module thật sự gọi TranslateText: slack_gateway — nơi phản ứng emoji trên Slack (reaction) biến thành 1 bản dịch trả lời trong thread. Cũng như translation, module này đủ 3 lớp domain/application/infrastructure; bài hôm nay dừng ở 2 lớp đầu, để lại infrastructure (HTTP nhận request thật từ Slack, bảo mật request signature) cho bài 05/06.

Domain: decouple khỏi wire format của Slack

crates/slack_gateway/src/domain/event.rs:

/// Domain representation of a `reaction_added` Slack event — decoupled from
/// Slack's actual wire format (see `infrastructure::dto` for that mapping).
#[derive(Debug, Clone)]
pub struct ReactionAddedEvent {

Docstring trên ReactionAddedEvent nói thẳng điều quan trọng nhất của file này: đây là kiểu dữ liệu của riêng slack_gateway, không phải struct map thẳng JSON mà Slack Events API trả về. Việc định nghĩa các kiểu wire-format khớp đúng JSON Slack gửi (SlackEventPayload, SlackEvent, ReactionAddedDto…) là việc của infrastructure::dto, sẽ viết ở bài 06 — chưa tồn tại ở bài này. Còn việc map thật sự từ các DTO đó sang ReactionAddedEvent domain lại nằm ở infrastructure::http::handlers, viết ở bài 05 — dto.rs chỉ định nghĩa hình dạng dữ liệu, không tự làm phép map đó. Cùng lý do, SlackMessage chỉ giữ đúng 4 field module này cần để dịch (channel, ts, text, user), không phải toàn bộ shape message thật Slack Web API trả về (có timestamp, có attachment, có block kit, …).

Cái lợi của việc tách này: nếu Slack đổi format API — đổi tên field, thêm field mới, đổi cấu trúc JSON — chỉ file mapping ở infrastructure cần sửa. ReactionAddedEvent, SlackMessage, và mọi thứ dùng chúng ở application (HandleReactionUseCase) không biết và không cần biết chuyện đó xảy ra. Đây là cùng nguyên tắc domain-không-biết-infra đã thấy ở translation bài 03, áp dụng lại cho module thứ 2.

Một chi tiết dễ bỏ qua nhưng quan trọng, nằm ngay trong docstring của field emoji: giá trị đây là short name dạng "flag-vn", không phải glyph unicode 🇻🇳. Slack Events API thực sự gửi short name trong field reaction, không gửi emoji hiển thị — quyết định thiết kế này ảnh hưởng trực tiếp tới business rule ở phần tiếp theo.

Business rule: emoji_lang

crates/slack_gateway/src/domain/emoji_lang.rs:

use kernel::LanguageCode;

/// Business rule: which flag-emoji reaction triggers translation into which
/// language. Slack's `reaction_added` event carries the emoji's *short name*
/// (e.g. `"flag-vn"`), not the unicode glyph, so this table matches against
/// short names. Deliberately a small curated set rather than every ISO
/// territory flag — extend as needed.
const EMOJI_LANGUAGE_TABLE: &[(&str, &str)] = &[
    ("flag-vn", "vi"),
    ("flag-us", "en"),
    ("flag-gb", "en"),
    ("flag-england", "en"),
    ("flag-scotland", "en"),
    ("flag-jp", "ja"),
    ("flag-kr", "ko"),
    ("flag-cn", "zh"),
    ("flag-fr", "fr"),
    ("flag-de", "de"),
    ("flag-es", "es"),
    ("flag-th", "th"),
];

pub fn language_for_emoji(emoji: &str) -> Option<LanguageCode> {
    EMOJI_LANGUAGE_TABLE
        .iter()
        .find(|(short_name, _)| *short_name == emoji)
        .and_then(|(_, code)| LanguageCode::new(*code).ok())
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn maps_known_flags() {
        assert_eq!(language_for_emoji("flag-vn").unwrap().as_str(), "vi");
        assert_eq!(language_for_emoji("flag-gb").unwrap().as_str(), "en");
    }

    #[test]
    fn ignores_unknown_reactions() {
        assert!(language_for_emoji("thumbsup").is_none());
    }
}

EMOJI_LANGUAGE_TABLE là bảng tra cứu tĩnh, khớp đúng lý do đã nêu ở phần trước: khoá tra cứu là short name ("flag-vn", "flag-jp", …), không phải glyph unicode. Đây là 1 quyết định nghiệp vụ có chủ đích, không phải liệt kê đầy đủ mọi lá cờ ISO tồn tại — docstring nói rõ “deliberately a small curated set”, chỉ 12 mục, thêm quốc gia mới là thêm 1 dòng vào bảng. Đáng chú ý: 3 short name khác nhau (flag-gb, flag-england, flag-scotland) cùng map về "en" — phản ánh đúng thực tế Slack có nhiều emoji cờ khác nhau cho cùng 1 khối ngôn ngữ.

language_for_emoji tìm trong bảng bằng short name, rồi chuyển string ngôn ngữ ("vi", "en", …) qua LanguageCode::new() — validate lại bằng type từ kernel (bài 02), không trả thẳng &str. Trả về Option<LanguageCode>: None nếu emoji không có trong bảng, đây là con đường phổ biến nhất trong thực tế — hầu hết reaction trên Slack là thumbsup, eyes, heart, không phải cờ nào cả.

2 test tại chỗ xác nhận đúng 2 nhánh của hàm: maps_known_flags kiểm tra map đúng (flag-vn → vi, flag-gb → en), ignores_unknown_reactions kiểm tra emoji không có trong bảng (thumbsup) trả về None chứ không panic. Chạy thật:

Application: 2 port outbound

crates/slack_gateway/src/application/ports.rs:

use async_trait::async_trait;

use crate::domain::SlackMessage;

#[derive(Debug, thiserror::Error)]
pub enum SlackApiError {
    #[error("slack api request failed: {0}")]
    RequestFailed(String),
    #[error("slack api returned an error: {0}")]
    ApiError(String),
    #[error("message not found: channel={channel} ts={ts}")]
    MessageNotFound { channel: String, ts: String },
}

/// Outbound port: everything this module needs from the Slack Web API.
/// Implemented by `infrastructure::SlackWebApiClient`; a test double can
/// implement this trait directly for use-case-level tests without any HTTP.
#[async_trait]
pub trait SlackMessagingPort: Send + Sync {
    async fn fetch_message(&self, channel: &str, ts: &str) -> Result<SlackMessage, SlackApiError>;

    async fn post_thread_reply(
        &self,
        channel: &str,
        thread_ts: &str,
        text: &str,
    ) -> Result<(), SlackApiError>;
}

/// Outbound port: prevents translating (and replying to) the same
/// message+language combination twice — e.g. several people reacting with the
/// same flag emoji, or Slack retrying a webhook delivery it thinks timed out.
#[async_trait]
pub trait DedupCachePort: Send + Sync {
    /// Attempts to claim `key`. Returns `true` if this call is the first to
    /// claim it (caller should proceed), `false` if it's already claimed and
    /// still within its TTL (caller should skip).
    async fn try_claim(&self, key: &str) -> bool;

    /// Releases a previously claimed key — call this after a failed attempt
    /// so a transient error doesn't permanently block retries.
    async fn release(&self, key: &str);
}

2 outbound port, cả 2 đều để HandleReactionUseCase không biết chi tiết triển khai bên dưới.

SlackMessagingPort gói mọi thao tác module này cần từ Slack Web API: lấy nội dung message (fetch_message) và trả lời trong thread (post_thread_reply). Docstring nói rõ ai sẽ implement trait này thật — infrastructure::SlackWebApiClient, ở bài 06, gọi HTTP thật tới Slack — nhưng cũng nói rõ điều quan trọng hơn cho bài hôm nay: 1 test double có thể implement thẳng trait này để test use case mà không cần HTTP nào cả. SlackApiError liệt kê 3 cách việc gọi Slack có thể thất bại, kể cả trường hợp cụ thể MessageNotFound — đủ chi tiết để phân biệt lỗi mạng chung chung với lỗi “message này không còn tồn tại”.

DedupCachePort giải quyết 1 vấn đề thực tế: nhiều người có thể react cùng 1 lá cờ vào cùng 1 message, hoặc Slack tự retry gửi lại webhook nếu nghĩ lần gửi trước timeout — cả 2 trường hợp đều không nên tạo ra 2 bản dịch, 2 reply trùng nhau. try_claim trả true nếu đây là lần đầu tiên claim khoá đó (nên tiếp tục xử lý), false nếu đã bị claim và còn trong TTL (nên bỏ qua). release là nửa còn lại: nhả khoá ra khi có lỗi tạm thời, để không khoá vĩnh viễn 1 message chỉ vì 1 lần Slack API hoặc translation provider bị lỗi thoáng qua.

Cả 2 port đều chưa có implementation thật ở bài này — infrastructure::SlackWebApiClient cho SlackMessagingPort, và 1 adapter dựa trên cache (Redis hoặc in-memory với TTL) cho DedupCachePort — đều để dành cho bài 06.

HandleReactionUseCase: orchestration thật

crates/slack_gateway/src/application/handle_reaction.rs (phần logic, chưa tính test):

use std::sync::Arc;

use kernel::LanguageCode;
use tracing::{debug, info};
use translation::application::{TranslateText, TranslateTextCommand};

use crate::application::ports::{DedupCachePort, SlackApiError, SlackMessagingPort};
use crate::domain::{emoji_lang, ReactionAddedEvent};

/// Orchestrates the one thing this bot does today: a flag-emoji reaction on a
/// message triggers fetching that message, translating it via the
/// `translation` module's public port, and replying in-thread with the
/// result. This is the only place the two modules meet — and they meet only
/// through `TranslateText`, never through `translation::infrastructure`.
pub struct HandleReactionUseCase {
    slack: Arc<dyn SlackMessagingPort>,
    translator: Arc<dyn TranslateText>,
    dedup: Arc<dyn DedupCachePort>,
}

impl HandleReactionUseCase {
    pub fn new(
        slack: Arc<dyn SlackMessagingPort>,
        translator: Arc<dyn TranslateText>,
        dedup: Arc<dyn DedupCachePort>,
    ) -> Self {
        Self {
            slack,
            translator,
            dedup,
        }
    }

    pub async fn execute(&self, event: ReactionAddedEvent) -> Result<(), SlackApiError> {
        let Some(target_lang) = emoji_lang::language_for_emoji(&event.emoji) else {
            // Not a flag emoji we recognize — silently ignore. Expected for
            // the vast majority of reactions (thumbsup, eyes, ...).
            return Ok(());
        };

        // One reply per (message, target language), no matter how many
        // people react with the same flag or how many times Slack retries
        // delivering the webhook.
        let dedup_key = format!("{}:{}:{}", event.channel, event.message_ts, target_lang);
        if !self.dedup.try_claim(&dedup_key).await {
            debug!(key = %dedup_key, "duplicate reaction, skipping");
            return Ok(());
        }

        let result = self.translate_and_reply(&event, &target_lang).await;

        if result.is_err() {
            // Don't let a transient failure (Slack API hiccup, translation
            // provider down) permanently block a retry.
            self.dedup.release(&dedup_key).await;
        }

        result
    }

    async fn translate_and_reply(
        &self,
        event: &ReactionAddedEvent,
        target_lang: &LanguageCode,
    ) -> Result<(), SlackApiError> {
        let message = self
            .slack
            .fetch_message(&event.channel, &event.message_ts)
            .await?;

        let translation = self
            .translator
            .execute(TranslateTextCommand {
                text: message.text,
                target_lang: target_lang.clone(),
                source_lang: None,
            })
            .await
            .map_err(|e| SlackApiError::ApiError(e.to_string()))?;

        info!(
            channel = %event.channel,
            ts = %event.message_ts,
            target_lang = %target_lang,
            "posting translation"
        );

        self.slack
            .post_thread_reply(&event.channel, &event.message_ts, &translation.translated_text)
            .await
    }
}

HandleReactionUseCase giữ đúng 3 field, cả 3 đều là trait object đứng sau Arc: slack: Arc<dyn SlackMessagingPort>, translator: Arc<dyn TranslateText>, dedup: Arc<dyn DedupCachePort>. Cùng công thức dependency inversion đã thấy ở TranslateTextUseCase bài 03 — use case chỉ biết 3 trait, không biết implementation cụ thể nào đứng sau chúng.

Chú ý field translator có kiểu Arc<dyn TranslateText> — chính là inbound port của module translation, chứ không phải TranslationProviderPort hay bất cứ thứ gì từ translation::infrastructure. Docstring trên struct nói thẳng: “they meet only through TranslateText, never through translation::infrastructure”. Đây là ranh giới module được tôn trọng đúng như thiết kế ở bài 03 — slack_gateway không biết, và không cần biết, translation đang dùng LibreTranslate hay provider nào khác.

execute() đi qua từng bước theo đúng thứ tự:

  1. Lọc emoji hợp lệ. emoji_lang::language_for_emoji(&event.emoji) trả None thì return Ok(()) ngay, im lặng bỏ qua — không phải lỗi, chỉ là phần lớn reaction không phải cờ.
  2. Tạo dedup key. Format {channel}:{message_ts}:{target_lang} — chú ý key gồm cả target_lang, không chỉ channel:message_ts. Cùng 1 message bị react bởi 2 lá cờ khác nhau (ví dụ flag-vn và flag-jp) vẫn tạo ra 2 key khác nhau, nên dịch ra 2 ngôn ngữ khác nhau không bị coi là trùng.
  3. Claim dedup. self.dedup.try_claim(&dedup_key).await trả false thì return Ok(()) ngay, log ở mức debug. Đây là điểm chặn request trùng trước khi tốn bất cứ lệnh gọi mạng nào.
  4. Fetch message qua self.slack.fetch_message(...). Lỗi ở bước này propagate thẳng ra bằng ?.
  5. Gọi translator.execute() — đúng và chỉ đúng TranslateText, gói tham số vào TranslateTextCommand với source_lang: None (để translation tự phát hiện ngôn ngữ nguồn, như đã thấy ở LibreTranslateAdapter bài 03). Lỗi translation (TranslationError) được map sang SlackApiError::ApiError — 2 module có 2 loại lỗi riêng, việc map lỗi này là chỗ duy nhất slack_gateway “nhìn thấy” translation có thể lỗi.
  6. Reply bằng post_thread_reply.
  7. Xử lý lỗi transient bằng cách release dedup key. Nếu translate_and_reply trả lỗi ở bất cứ bước nào (fetch, translate, hay reply), execute() gọi self.dedup.release(&dedup_key).await trước khi trả lỗi ra ngoài. Không làm vậy thì 1 lần Slack API hoặc LibreTranslate hiccup tạm thời sẽ khoá vĩnh viễn message đó — không ai react lại được nữa vì key coi như “đã xử lý”.

Toàn bộ logic nghiệp vụ đáng test nằm gọn trong 1 hàm execute() khoảng 20 dòng, không phụ thuộc gì ngoài 3 trait.

            &self,
            _channel: &str,
            _thread_ts: &str,

    impl StubDedup {

        }

    #[async_trait]
    impl DedupCachePort for StubDedup {
        async fn try_claim(&self, key: &str) -> bool {
            self.claimed.lock().unwrap().insert(key.to_string())
        }

        async fn release(&self, key: &str) {
            self.claimed.lock().unwrap().remove(key);
        }
    }

    fn reaction_event() -> ReactionAddedEvent {
        ReactionAddedEvent {
            emoji: "flag-vn".to_string(),
            channel: "C1".to_string(),

    #[tokio::test]

            post_count: AtomicUsize::new(0),

            Arc::new(StubDedup::new()),

        });
        let use_case = HandleReactionUseCase::new(
            slack.clone(),

            Arc::new(StubDedup::new()),

        use_case.execute(reaction_event()).await.unwrap();

    #[tokio::test]
    async fn skips_duplicate_reactions_to_the_same_message_and_language() {
        let slack = Arc::new(StubSlack {
            post_count: AtomicUsize::new(0),
        });
        let use_case = HandleReactionUseCase::new(
            slack.clone(),
            Arc::new(StubTranslator),
            Arc::new(StubDedup::new()),

        use_case.execute(reaction_event()).await.unwrap();
        use_case.execute(reaction_event()).await.unwrap();

        assert_eq!(slack.post_count.load(Ordering::SeqCst), 1);

    #[tokio::test]
    async fn does_not_dedup_across_different_target_languages() {
        let slack = Arc::new(StubSlack {
            post_count: AtomicUsize::new(0),
        });
        let use_case = HandleReactionUseCase::new(

3 stub, mỗi stub implement thẳng 1 trong 3 trait HandleReactionUseCase phụ thuộc — không có gì khác trong test module này chạm tới HTTP hay filesystem:

  • StubSlack implement SlackMessagingPort. fetch_message luôn trả về 1 SlackMessage cố định với text "hello". post_thread_reply không thật sự gửi gì đi — chỉ tăng post_count (một AtomicUsize, an toàn gọi từ nhiều task async cùng lúc) để test sau này assert được đã reply bao nhiêu lần.
  • StubTranslator implement TranslateText — chính là inbound port của translation, không phải TranslationProviderPort. Trả về ngay 1 Translation giả, ghép chuỗi "[{target_lang}] {text}", không gọi LibreTranslate hay bất cứ provider thật nào.
  • StubDedup implement DedupCachePort bằng 1 HashSet<String> bọc trong Mutex, sống hoàn toàn trong bộ nhớ tiến trình test. Docstring trên struct nói rõ lý do đặt nó cục bộ trong module test này: để test tầng application không phải với tới infrastructure.

4 test lần lượt xác nhận đúng các nhánh logic đã liệt kê ở phần trước:

  • ignores_reactions_that_are_not_a_mapped_flag: emoji thumbsup không map được ngôn ngữ nào → post_count vẫn là 0, use case return sớm ở bước lọc emoji, không đụng tới dedup, slack, hay translator.
  • translates_and_replies_once_per_message_and_language: đường đi thành công đầy đủ, 1 reaction hợp lệ → post_count = 1.
  • skips_duplicate_reactions_to_the_same_message_and_language: gọi execute 2 lần với cùng 1 event (mô phỏng 2 người react cùng lá cờ vào cùng message, hoặc Slack gửi lại webhook) → post_count vẫn là 1, không phải 2 — dedup hoạt động đúng.
  • does_not_dedup_across_different_target_languages: cùng message nhưng 2 emoji khác nhau (flag-vn rồi flag-jp) → post_count = 2 — dedup key gồm cả target_lang nên không chặn nhầm 2 ngôn ngữ khác nhau của cùng 1 message.

Đây chính là lợi ích thật của kiến trúc port/adapter, không phải lý thuyết suông: toàn bộ luồng nghiệp vụ — lọc emoji, dedup theo key, orchestration fetch → translate → reply, xử lý lỗi transient bằng release — được test đầy đủ trong 0.00s, không cần Slack Web API thật, không cần LibreTranslate chạy, không cần mạng, không cần mock framework hay HTTP interceptor nào. 3 struct Rust bình thường, mỗi struct implement đúng 1 trait, là đủ.

Tổng kết & bài tiếp theo

slack_gateway bài này có domain thuần Rust (ReactionAddedEvent, SlackMessage, đều decouple khỏi wire format Slack thật) cộng 1 business rule nhỏ (emoji_lang, tra cứu theo short name chứ không phải glyph unicode), và application với 2 outbound port (SlackMessagingPort, DedupCachePort) cộng 1 use case (HandleReactionUseCase) nối chúng lại với translation::application::TranslateText — đúng và chỉ đúng qua trait đó, chưa bao giờ chạm translation::infrastructure. 6 test thật (2 domain + 4 application), toàn bộ chạy bằng stub, xác nhận cả business rule lẫn orchestration hoạt động đúng.

Cả SlackMessagingPort và DedupCachePort vẫn chưa có implementation thật — không có adapter nào gọi Slack Web API thật, không có cache TTL thật. Bài 05 chuyển sang phần còn thiếu: tầng HTTP thật sự nhận request từ Slack, và bảo mật — verify request signature để chắc chắn request đến từ Slack chứ không phải ai đó giả mạo webhook.
