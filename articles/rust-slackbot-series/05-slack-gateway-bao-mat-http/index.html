Nhưng use case đó không tự chạy: cần thứ gì đó gọi execute() với 1 ReactionAddedEvent thật, và thứ đó phải lấy event từ đâu ra. Vì sao phải verify chữ ký

/slack/events là 1 URL công khai trên Internet. Slack cấu hình URL này trong Event Subscriptions của app, rồi POST tới đó mỗi khi có sự kiện — nhưng bản thân URL không có gì bí mật cả. Ai biết được URL (đoán ra, soi log, hay chỉ đơn giản domain đó lộ ra ở đâu đó) đều gửi POST request tới được, với body JSON tự bịa, giả dạng y hệt format reaction_added thật.

Không verify gì thì server này không phân biệt được request thật từ Slack với request giả mạo. Hậu quả cụ thể với bot này: ai đó tự soạn 1 payload reaction_added giả, POST thẳng tới /slack/events, và bot sẽ tự động fetch message, dịch, rồi post reply vào thread — hoàn toàn không có reaction thật nào xảy ra trên Slack. Verify chữ ký là điều kiện tối thiểu để đóng lỗ hổng này: chỉ request có chữ ký hợp lệ, ký bằng signing secret mà chỉ Slack và server này biết, mới được xử lý tiếp.

verify_slack_signature: HMAC-SHA256 đúng chuẩn Slack

crates/slack_gateway/src/infrastructure/signature.rs:

use hmac::{Hmac, Mac};
use sha2::Sha256;

type HmacSha256 = Hmac<Sha256>;

/// Verifies Slack's request signature.
/// https://api.slack.com/authentication/verifying-requests-from-slack
///
/// `timestamp` / `signature` come from the `X-Slack-Request-Timestamp` /
/// `X-Slack-Signature` headers, `body` is the raw (unparsed) request body.
pub fn verify_slack_signature(
    signing_secret: &str,
    timestamp: &str,
    body: &str,
    signature: &str,
) -> bool {
    let Ok(request_ts) = timestamp.parse::<i64>() else {
        return false;
    };

    // Reject requests older than 5 minutes to guard against replay attacks.
    if (unix_now() - request_ts).abs() > 60 * 5 {
        return false;
    }

    let base = format!("v0:{timestamp}:{body}");

    let Ok(mut mac) = HmacSha256::new_from_slice(signing_secret.as_bytes()) else {
        return false;
    };
    mac.update(base.as_bytes());
    let computed = format!("v0={}", hex::encode(mac.finalize().into_bytes()));

    constant_time_eq(computed.as_bytes(), signature.as_bytes())
}

fn unix_now() -> i64 {
    use std::time::{SystemTime, UNIX_EPOCH};
    SystemTime::now()
        .duration_since(UNIX_EPOCH)
        .map(|d| d.as_secs() as i64)
        .unwrap_or(0)
}

fn constant_time_eq(a: &[u8], b: &[u8]) -> bool {
    if a.len() != b.len() {
        return false;
    }
    a.iter().zip(b.iter()).fold(0u8, |acc, (x, y)| acc | (x ^ y)) == 0
}

Đây đúng thuật toán Slack mô tả trong tài liệu chính thức của họ (link ngay trong docstring). 4 bước, đi theo đúng thứ tự trong hàm:

  1. Parse timestamp. timestamp đến từ header X-Slack-Request-Timestamp, dạng chuỗi số Unix epoch giây. Parse lỗi (không phải số, hoặc rỗng) thì return false ngay bằng let ... else — không có timestamp hợp lệ thì không có gì để verify tiếp.
  2. Chặn replay theo tuổi request — nói kỹ hơn ở phần sau.
  3. Build chuỗi base và ký bằng HMAC-SHA256. base ghép đúng format Slack quy định: v0:{timestamp}:{body} — tiền tố v0:, dấu :, timestamp dạng chuỗi y hệt header, dấu :, rồi tới toàn bộ raw body. HmacSha256::new_from_slice(signing_secret.as_bytes()) khởi tạo MAC với signing secret (secret riêng của app Slack, cấu hình ở phía server này, không phải thứ gửi qua network) làm key, mac.update(base.as_bytes()) nạp dữ liệu cần ký, mac.finalize().into_bytes() cho ra digest. hex::encode(...) chuyển digest sang chuỗi hex, ghép thêm tiền tố v0= — đúng format Slack gửi trong header X-Slack-Signature.
  4. So sánh computed (chữ ký tự tính ra) với signature (chữ ký Slack gửi kèm) — bằng constant_time_eq, không phải ==.

2 chi tiết bảo mật dễ bỏ sót

Đọc lướt qua, code có vẻ chỉ là “tính HMAC rồi so sánh chuỗi”. 2 chi tiết sau là lý do hàm này không chỉ dừng ở đó.

constant_time_eq thay vì ==. So sánh 2 chuỗi/mảng byte bằng toán tử == thông thường (kể cả trên &str hay &[u8] trong Rust) dừng lại ngay tại byte đầu tiên khác nhau — càng nhiều byte đầu khớp đúng, thời gian so sánh càng dài hơn một chút. Với timing attack, kẻ tấn công không cần đọc được response — chỉ cần đo thời gian phản hồi rất chính xác (gửi hàng ngàn request, thống kê độ trễ), rồi dò từng byte chữ ký một: thử tất cả giá trị cho byte đầu tiên, giữ lại giá trị nào khiến server phản hồi chậm hơn 1 chút (nghĩa là byte đó khớp, so sánh đi xa hơn 1 bước trước khi fail), rồi lặp lại cho byte kế tiếp. Về lý thuyết, cách này giảm độ khó dò 1 chữ ký 64 ký tự hex từ “thử tất cả tổ hợp” xuống “thử từng byte một” — chênh lệch độ khó rất lớn.

constant_time_eq né hoàn toàn vấn đề đó bằng cách không bao giờ dừng sớm:

a.iter().zip(b.iter()).fold(0u8, |acc, (x, y)| acc | (x ^ y)) == 0

zip duyệt cả 2 mảng song song, x ^ y cho ra 0 nếu 2 byte ở vị trí đó khớp nhau, khác 0 nếu không khớp. fold OR dồn tất cả kết quả XOR đó lại vào 1 accumulator — bất kể byte sai nằm ở vị trí nào (đầu, giữa, hay cuối), vòng lặp luôn chạy hết toàn bộ độ dài mảng, không có nhánh nào thoát sớm. Kết quả cuối == 0 đúng khi và chỉ khi mọi byte đều khớp. Thời gian chạy chỉ phụ thuộc độ dài mảng, không phụ thuộc nội dung — không còn tín hiệu thời gian nào để dò. Check độ dài (a.len() != b.len()) vẫn return sớm được, vì độ dài chữ ký đúng là cố định (luôn 64 ký tự hex + tiền tố v0=) và không phải bí mật cần giấu.

Chặn timestamp lệch quá 5 phút. Đây là dòng đứng ngay sau khi parse timestamp, trước khi tính HMAC:

if (unix_now() - request_ts).abs() > 60 * 5 {
    return false;
}

Chữ ký HMAC tự nó không hết hạn — cùng 1 signing_secret, cùng 1 timestamp và body, luôn ký ra đúng 1 chữ ký, mãi mãi. Nếu chỉ verify HMAC mà không verify tuổi request, ai chặn được (sniff) 1 request Slack gửi hợp lệ 1 lần — timestamp, body, chữ ký đều thật — có thể gửi lại y hệt request đó bao nhiêu lần tuỳ thích, verify vẫn pass mỗi lần vì HMAC không đổi. Đó là replay attack. So unix_now() (giờ hiện tại của server) với request_ts (giờ Slack tự ghi lúc ký request), lệch quá 5 phút theo cả 2 chiều (abs(), không chỉ chặn request cũ mà cả request có timestamp tương lai bất thường) thì từ chối — giới hạn cửa sổ có thể replay xuống còn 5 phút, khớp đúng khuyến nghị chính thức của Slack.

axum: router/handlers/state

3 file còn lại lắp verify_slack_signature vào 1 web server thật, dùng axum.

crates/slack_gateway/src/infrastructure/http/state.rs:

use std::sync::Arc;

use crate::application::HandleReactionUseCase;

#[derive(Clone)]
pub struct AppState {
    pub handle_reaction: Arc<HandleReactionUseCase>,
    pub signing_secret: Arc<String>,
}

crates/slack_gateway/src/infrastructure/http/router.rs:

use axum::{
    routing::{get, post},
    Router,
};

use super::handlers::{healthz, slack_events};
use super::state::AppState;

pub fn router(state: AppState) -> Router {
    Router::new()
        .route("/healthz", get(healthz))
        .route("/slack/events", post(slack_events))
        .with_state(state)
}

crates/slack_gateway/src/infrastructure/http/handlers.rs:

use axum::{
    body::Bytes,
    extract::State,
    http::{HeaderMap, StatusCode},
    response::IntoResponse,
    Json,
};
use tracing::{error, warn};

use crate::domain::ReactionAddedEvent;
use crate::infrastructure::dto::{SlackEvent, SlackEventPayload};
use crate::infrastructure::signature::verify_slack_signature;

use super::state::AppState;

pub async fn healthz() -> impl IntoResponse {
    StatusCode::OK
}

pub async fn slack_events(
    State(state): State<AppState>,
    headers: HeaderMap,
    body: Bytes,
) -> impl IntoResponse {
    let Ok(body_str) = std::str::from_utf8(&body) else {
        return (StatusCode::BAD_REQUEST, "invalid utf-8 body").into_response();
    };

    let timestamp = headers
        .get("X-Slack-Request-Timestamp")
        .and_then(|v| v.to_str().ok())
        .unwrap_or_default();
    let signature = headers
        .get("X-Slack-Signature")
        .and_then(|v| v.to_str().ok())
        .unwrap_or_default();

    if !verify_slack_signature(&state.signing_secret, timestamp, body_str, signature) {
        warn!("rejected slack event with invalid signature");
        return (StatusCode::UNAUTHORIZED, "invalid signature").into_response();
    }

    let payload: SlackEventPayload = match serde_json::from_str(body_str) {
        Ok(p) => p,
        Err(e) => {
            error!(error = %e, "failed to parse slack event payload");
            return (StatusCode::BAD_REQUEST, "invalid payload").into_response();
        }
    };

    match payload {
        SlackEventPayload::UrlVerification { challenge } => {
            Json(serde_json::json!({ "challenge": challenge })).into_response()
        }
        SlackEventPayload::EventCallback { event } => {
            if let SlackEvent::ReactionAdded(dto) = event {
                let domain_event = ReactionAddedEvent {
                    emoji: dto.reaction,
                    channel: dto.item.channel,
                    message_ts: dto.item.ts,
                    reacting_user: dto.user,
                };

                // Slack expects a fast 200 OK (within 3s); do the actual work
                // after acking so retries aren't triggered by slow translations.
                let use_case = state.handle_reaction.clone();
                tokio::spawn(async move {
                    if let Err(e) = use_case.execute(domain_event).await {
                        error!(error = %e, "failed to handle reaction_added event");
                    }
                });
            }

            StatusCode::OK.into_response()
        }
    }
}

Chi tiết quan trọng nhất nằm ngay trong signature của slack_events: tham số cuối là body: Bytes, không phải Json<SlackEventPayload>. axum hoàn toàn có extractor Json<T> tự parse JSON ngay tại chỗ khai báo handler — tiện hơn, ít code hơn — nhưng dùng nó ở đây là sai, vì thứ tự xử lý bắt buộc phải là: nhận raw body → verify chữ ký trên raw body đó → mới parse JSON. Chữ ký Slack gửi được tính trên toàn bộ body thô, byte-for-byte, chưa qua bất kỳ biến đổi nào. Nếu để axum tự parse thành SlackEventPayload trước, handler nhận được 1 struct Rust đã deserialize — không còn cách nào lấy lại chuỗi byte gốc y hệt để tính lại HMAC cho khớp. Whitespace, thứ tự field, cách serde format lại số — bất kỳ khác biệt nhỏ nào giữa JSON gốc và JSON serialize lại đều làm HMAC tính ra sai, verify luôn fail dù request là thật. Vì vậy hàm nhận Bytes thô, tự gọi verify_slack_signature trước, xong mới gọi serde_json::from_str(body_str) để parse — đúng thứ tự, đúng dữ liệu ký trên đó.

2 header cần thiết (X-Slack-Request-Timestamp, X-Slack-Signature) lấy qua HeaderMap, unwrap_or_default() về chuỗi rỗng nếu thiếu — chuỗi rỗng chắc chắn verify fail (parse timestamp lỗi, hoặc so sánh chữ ký lệch độ dài), không cần xử lý case thiếu header riêng.

Sau khi verify pass và parse JSON thành công, SlackEventPayload có 2 nhánh: UrlVerification (Slack gửi khi mình cấu hình URL callback lần đầu, chỉ cần echo lại challenge để xác nhận URL sống) và EventCallback (event thật). Trong EventCallback, chỉ event ReactionAdded được map sang ReactionAddedEvent (domain type bài 04) rồi giao cho HandleReactionUseCase; các loại event khác Slack có thể gửi bị bỏ qua ở nhánh if let — im lặng, không lỗi.

AppState (state.rs) là nơi 2 dependency của handler này sống: handle_reaction: Arc<HandleReactionUseCase> (use case bài 04) và signing_secret: Arc<String> (secret dùng verify chữ ký). #[derive(Clone)] bắt buộc vì axum yêu cầu state kiểu này — mỗi request axum nhận đều clone AppState ra để đưa vào handler, nhưng nhờ bọc trong Arc nên clone chỉ tăng reference count, không copy dữ liệu bên trong. router() nhận AppState làm tham số, gọi .with_state(state) trên Router — đây là dependency injection theo kiểu axum: router() không tự tạo HandleReactionUseCase hay đọc signing_secret từ đâu, tất cả được truyền vào từ ngoài (composition root, bài 07 sẽ ráp phần này), handler chỉ cần khai báo State(state): State<AppState> trong tham số để lấy lại đúng instance đó ở mỗi request.

Ràng buộc 3 giây của Slack Events API

Slack quy định: nếu server không trả HTTP 200 trong vòng 3 giây kể từ khi Slack gửi request, Slack coi lần gửi đó thất bại và tự động retry — gửi lại y hệt request đó, tối đa vài lần. Dịch text qua LibreTranslate rồi gọi Slack Web API để post reply hoàn toàn có thể mất hơn 3 giây, đặc biệt khi provider dịch đang tải cao hoặc mạng chậm. Nếu code đợi dịch xong, post reply xong, rồi mới trả response, response đó có nguy cơ tới sau mốc 3 giây — Slack coi là fail, retry, và giờ bot xử lý 2 lần cùng 1 event.

skips_duplicate_reactions_to_the_same_message_and_language ở bài 04 đã test cho trường hợp bị gọi trùng — dedup key chặn được reply lặp lại. Nhưng đó là lưới an toàn thứ 2, không nên là lý do duy nhất ngăn Slack retry. Cách đúng hơn là tránh để retry xảy ra ngay từ đầu: đây là lý do khối xử lý ReactionAdded nằm trong tokio::spawn, không phải .await trực tiếp trong handler.

let use_case = state.handle_reaction.clone();
tokio::spawn(async move {
    if let Err(e) = use_case.execute(domain_event).await {
        error!(error = %e, "failed to handle reaction_added event");
    }
});

StatusCode::OK.into_response()

tokio::spawn đẩy use_case.execute(domain_event) chạy như 1 task nền độc lập trên runtime tokio, không chặn handler đang chạy phải đợi nó xong. Handler tiếp tục ngay xuống dòng StatusCode::OK.into_response() và trả response — verify chữ ký và parse JSON xong là trả 200 ngay, việc dịch + post reply (có thể mất vài giây) chạy song song phía sau, không nằm trên đường trả response nữa. use_case clone ra 1 Arc riêng trước khi move vào closure async move vì task nền sống độc lập với vòng đời của request — handler có thể đã return xong từ lâu trong khi task nền vẫn đang chạy.

Đánh đổi của cách này: lỗi bên trong task nền (dịch fail, Slack API fail) không còn cách nào trả về client nữa — vì response đã gửi trước đó rồi. Đó là lý do có error!(error = %e, ...) log lại thay vì propagate lỗi ra ngoài — chấp nhận fire-and-forget, đổi lấy việc luôn ACK kịp 3 giây bất kể việc dịch chậm tới đâu.

Verify bằng test thật

Test tại chỗ trong handlers.rs:

#[cfg(test)]
mod tests {
    use super::*;

    #[tokio::test]
    async fn healthz_returns_ok() {
        let response = healthz().await.into_response();
        assert_eq!(response.status(), StatusCode::OK);
    }
}

Chỉ 1 test ở tầng HTTP bài này — healthz_returns_ok, gọi thẳng hàm healthz() (không qua axum router thật, không cần mở port nào) và assert status trả về 200 OK. Đủ cho endpoint health-check đơn giản; test có giá trị thật cho slack_events (chữ ký hợp lệ/không hợp lệ, timestamp hết hạn, payload sai định dạng) đòi hỏi build request giả với header + body thật, việc đó thuộc phạm vi test tích hợp — chưa có ở bài này.

Tổng kết & bài tiếp theo

Bài này đóng 2 mảnh còn thiếu của slack_gateway: bảo mật (verify_slack_signature — HMAC-SHA256 đúng chuẩn Slack, so sánh bằng constant-time thay vì == để tránh timing attack, chặn timestamp lệch quá 5 phút để tránh replay) và tầng HTTP (router/handlers/state bằng axum — đọc raw Bytes để verify chữ ký trước khi parse JSON, AppState tiêm dependency qua Router::with_state, tokio::spawn tách việc xử lý chậm ra khỏi đường trả response để luôn ACK kịp 3 giây Slack yêu cầu). Request từ Slack giờ đi được trọn đường: verify → parse → giao cho HandleReactionUseCase bài 04.

Vẫn còn thiếu implementation thật cho 2 outbound port đã định nghĩa ở bài 04: SlackMessagingPort (gọi Slack Web API thật để fetch message và post reply) và DedupCachePort (cache TTL thật, không phải HashSet trong bộ nhớ test). Bài 06 viết 2 adapter đó — phần gọi RA NGOÀI, đối xứng với phần nhận VÀO đã xong ở bài này.
