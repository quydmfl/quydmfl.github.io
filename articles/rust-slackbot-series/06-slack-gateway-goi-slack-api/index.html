dto.rs: map wire format Slack bằng serde tag enum đa hình

crates/slack_gateway/src/infrastructure/dto.rs:

use serde::Deserialize;

/// Slack's outer envelope for anything posted to an Events API request URL.
/// https://api.slack.com/apis/connections/events-api
///
/// Deliberately kept separate from the domain `ReactionAddedEvent` — this is
/// wire format, mapped into domain types in `infrastructure::http::handlers`.
#[derive(Debug, Deserialize)]
#[serde(tag = "type")]
pub enum SlackEventPayload {
    #[serde(rename = "url_verification")]
    UrlVerification { challenge: String },
    #[serde(rename = "event_callback")]
    EventCallback { event: SlackEvent },
}

#[derive(Debug, Deserialize)]
#[serde(tag = "type")]
pub enum SlackEvent {
    #[serde(rename = "reaction_added")]
    ReactionAdded(ReactionAddedDto),
    /// Catch-all for event types we don't act on yet (message, app_mention, ...).
    #[serde(other)]
    Unhandled,
}

#[derive(Debug, Deserialize)]
pub struct ReactionAddedDto {
    pub user: String,
    pub reaction: String,
    pub item: ReactionItemDto,
}

#[derive(Debug, Deserialize)]
pub struct ReactionItemDto {
    pub channel: String,
    pub ts: String,
}

Slack gửi 1 trong 2 dạng payload tới cùng 1 URL: lần đầu cấu hình URL callback, Slack gửi {"type": "url_verification", "challenge": "..."} để xác nhận URL sống; sau đó, mỗi sự kiện thật gửi dạng {"type": "event_callback", "event": {...}}. Cùng 1 endpoint, 2 shape JSON khác hẳn nhau, phân biệt bằng đúng 1 field type. Đây là bài toán #[serde(tag = "type")] giải quyết: field type trong JSON quyết định biến thể (variant) nào của enum Rust được dùng để parse phần còn lại. SlackEventPayload có 2 biến thể, mỗi biến thể gắn #[serde(rename = "...")] để khớp đúng giá trị chuỗi Slack gửi (url_verification, event_callback) — serde đọc field type trước, chọn biến thể tương ứng, rồi parse các field còn lại của JSON object đó vào field của biến thể đó (challenge cho UrlVerification, event cho EventCallback). Không cần match thủ công trên 1 chuỗi rồi tự gọi serde_json::from_value cho từng nhánh — khai báo enum đúng shape là đủ, serde tự làm phần còn lại.

SlackEvent dùng lại đúng kỹ thuật đó cho tầng lồng bên trong, nhưng thêm 1 chi tiết quan trọng: #[serde(other)] trên biến thể Unhandled. Slack Events API có hàng chục loại event (message, app_mention, reaction_added, reaction_removed, channel_created, …), và danh sách đó còn tăng theo thời gian khi Slack thêm tính năng mới. Module này chỉ cần xử lý đúng 1 loại — reaction_added — nên #[serde(other)] đóng vai trò “bắt tất cả còn lại”: bất kỳ giá trị type nào không khớp "reaction_added" đều rơi vào Unhandled thay vì làm serde_json::from_str trả lỗi. Không cần liệt kê hết toàn bộ loại event Slack có thể gửi, cũng không cần lo Slack thêm loại event mới trong tương lai làm code hiện tại crash — parse luôn thành công, Unhandled chỉ đơn giản không mang thông tin gì để xử lý tiếp. ReactionAddedDto và ReactionItemDto là 2 struct thường, map trực tiếp field JSON Slack gửi cho reaction_added (user, reaction, và item.channel/item.ts lồng bên trong) — không có gì đặc biệt, vì bài toán đa hình đã được #[serde(tag = "type")] xử lý xong ở tầng ngoài.

SlackWebApiClient: implement SlackMessagingPort

crates/slack_gateway/src/infrastructure/web_api_client.rs:

use async_trait::async_trait;
use serde::Deserialize;
use serde_json::json;

use crate::application::ports::{SlackApiError, SlackMessagingPort};
use crate::domain::SlackMessage;

/// Adapter over the Slack Web API (https://api.slack.com/web) using a bot
/// token. The only file in the codebase that knows Slack's HTTP shape for
/// fetching/posting messages.
pub struct SlackWebApiClient {
    http: reqwest::Client,
    bot_token: String,
}

impl SlackWebApiClient {
    pub fn new(bot_token: impl Into<String>) -> Self {
        Self {
            http: reqwest::Client::new(),
            bot_token: bot_token.into(),
        }
    }
}

#[derive(Deserialize)]
struct ConversationsHistoryResponse {
    ok: bool,
    error: Option<String>,
    messages: Option<Vec<HistoryMessage>>,
}

#[derive(Deserialize)]
struct HistoryMessage {
    text: String,
    user: Option<String>,
}

#[derive(Deserialize)]
struct SlackApiResponse {
    ok: bool,
    error: Option<String>,
}

#[async_trait]
impl SlackMessagingPort for SlackWebApiClient {
    async fn fetch_message(&self, channel: &str, ts: &str) -> Result<SlackMessage, SlackApiError> {
        let resp = self
            .http
            .get("https://slack.com/api/conversations.history")
            .bearer_auth(&self.bot_token)
            .query(&[
                ("channel", channel),
                ("latest", ts),
                ("inclusive", "true"),
                ("limit", "1"),
            ])
            .send()
            .await
            .map_err(|e| SlackApiError::RequestFailed(e.to_string()))?
            .json::<ConversationsHistoryResponse>()
            .await
            .map_err(|e| SlackApiError::RequestFailed(e.to_string()))?;

        if !resp.ok {
            return Err(SlackApiError::ApiError(
                resp.error.unwrap_or_else(|| "unknown error".to_string()),
            ));
        }

        let message = resp
            .messages
            .and_then(|mut m| if m.is_empty() { None } else { Some(m.remove(0)) })
            .ok_or_else(|| SlackApiError::MessageNotFound {
                channel: channel.to_string(),
                ts: ts.to_string(),
            })?;

        Ok(SlackMessage {
            channel: channel.to_string(),
            ts: ts.to_string(),
            text: message.text,
            user: message.user,
        })
    }

    async fn post_thread_reply(
        &self,
        channel: &str,
        thread_ts: &str,
        text: &str,
    ) -> Result<(), SlackApiError> {
        let resp = self
            .http
            .post("https://slack.com/api/chat.postMessage")
            .bearer_auth(&self.bot_token)
            .json(&json!({
                "channel": channel,
                "thread_ts": thread_ts,
                "text": text,
            }))
            .send()
            .await
            .map_err(|e| SlackApiError::RequestFailed(e.to_string()))?
            .json::<SlackApiResponse>()
            .await
            .map_err(|e| SlackApiError::RequestFailed(e.to_string()))?;

        if !resp.ok {
            return Err(SlackApiError::ApiError(
                resp.error.unwrap_or_else(|| "unknown error".to_string()),
            ));
        }

        Ok(())
    }
}

Đây là implementation thật cho SlackMessagingPort — trait bài 04 đã định nghĩa nhưng chưa có ai gọi HTTP thật. Docstring nói đúng vai trò của file này: “the only file in the codebase that knows Slack’s HTTP shape” — mọi URL, mọi tên field JSON riêng của Slack Web API chỉ xuất hiện ở đây, không rò rỉ ra application hay domain.

fetch_message gọi GET conversations.history — endpoint liệt kê lịch sử tin nhắn của 1 channel. 4 query param ghép lại để lấy đúng 1 tin nhắn: channel (channel cần tìm), latest (mốc timestamp), inclusive=true (bao gồm cả tin nhắn đúng tại latest, không chỉ tin trước nó), limit=1 (chỉ cần 1 kết quả). Kết hợp cả 4 param, Slack trả về đúng 1 tin nhắn tại đúng timestamp ts đã có sẵn (lấy từ item.ts trong reaction_added event) — không phải tìm kiếm mờ, mà là tra cứu chính xác 1 message theo toạ độ đã biết trước.

post_thread_reply gọi POST chat.postMessage với body JSON có thread_ts. Field này là điểm khác biệt giữa “trả lời trong thread” và “gửi tin nhắn mới”: không có thread_ts, message post ra sẽ là 1 tin nhắn độc lập, đứng ngang hàng, chen vào giữa channel; có thread_ts (đặt bằng đúng ts của message gốc bị react), Slack gắn message mới vào làm reply lồng trong thread của message đó — đúng UX bot dịch nên có: người dùng thấy bản dịch nằm ngay dưới message gốc, không loãng ra channel chính.

Cả 2 hàm đều check cùng 1 pattern sau khi nhận response:

if !resp.ok {
    return Err(SlackApiError::ApiError(
        resp.error.unwrap_or_else(|| "unknown error".to_string()),
    ));
}

Đây là quy ước riêng của Slack Web API, khác với REST API thông thường: Slack luôn trả HTTP status 200 OK cho mọi request tới /api/*, kể cả khi logic nghiệp vụ thất bại (token sai, channel không tồn tại, bot không có quyền post vào channel đó, …). Thất bại được báo qua field ok: false cộng thêm error: Some("mã lỗi") nằm trong chính JSON body của response 200 đó — không phải qua status code 4xx/5xx như REST thường làm. Vì vậy reqwest không tự phát hiện được lỗi này (status vẫn 200, .send() không trả Err); code phải tự deserialize response rồi tự kiểm tra field ok. Cả ConversationsHistoryResponse và SlackApiResponse đều có 2 field ok/error y hệt nhau cho đúng lý do này — mỗi endpoint Slack đều tuân theo cùng 1 convention báo lỗi.

fetch_message còn 1 bước sau khi resp.ok pass: resp.messages có thể Some(vec![]) (channel tồn tại, nhưng không có tin nhắn nào khớp latest — ví dụ message đã bị xoá) hoặc None. and_then xử lý cả 2 trường hợp thành None, ok_or_else biến None thành SlackApiError::MessageNotFound { channel, ts } — lỗi cụ thể, phân biệt được với RequestFailed (lỗi mạng) hay ApiError (Slack từ chối request) đã định nghĩa ở bài 04.

InMemoryDedupCache: TTL cache tự viết

crates/slack_gateway/src/infrastructure/dedup.rs:

use async_trait::async_trait;
use std::collections::HashMap;
use std::sync::Mutex;
use std::time::{Duration, Instant};

use crate::application::ports::DedupCachePort;

/// Process-local TTL cache backing `DedupCachePort`. Good enough for a
/// single running instance; if the bot is ever scaled horizontally, swap
/// this for a Redis-backed adapter implementing the same port — nothing
/// else in the codebase needs to change.
pub struct InMemoryDedupCache {
    ttl: Duration,
    claimed: Mutex<HashMap<String, Instant>>,
}

impl InMemoryDedupCache {
    pub fn new(ttl: Duration) -> Self {
        Self {
            ttl,
            claimed: Mutex::new(HashMap::new()),
        }
    }
}

impl Default for InMemoryDedupCache {
    fn default() -> Self {
        // Generous enough to catch duplicate reactions arriving seconds or
        // minutes apart, short enough that memory doesn't grow unbounded on
        // a long-running process.
        Self::new(Duration::from_secs(60 * 60))
    }
}

#[async_trait]
impl DedupCachePort for InMemoryDedupCache {
    async fn try_claim(&self, key: &str) -> bool {
        let now = Instant::now();
        let mut claimed = self.claimed.lock().unwrap();

        // Lazily prune expired entries on every call instead of running a
        // background sweep — simple, and fine at the traffic volume a
        // single Slack bot instance sees.
        claimed.retain(|_, claimed_at| now.duration_since(*claimed_at) < self.ttl);

        if claimed.contains_key(key) {
            false
        } else {
            claimed.insert(key.to_string(), now);
            true
        }
    }

    async fn release(&self, key: &str) {
        self.claimed.lock().unwrap().remove(key);
    }
}

Đây là implementation thật cho DedupCachePort — bài 04 chỉ có test double StubDedup (claimed: Mutex<HashSet<String>>) vốn đã thread-safe sẵn (chính vì vậy nó chạy được dưới #[tokio::test], có thể chạy test đồng thời), nhưng không có TTL/expiry: 1 key đã claim thì bị coi là “đã xử lý” mãi mãi trong suốt vòng đời của test. InMemoryDedupCache thêm đúng phần còn thiếu đó — TTL cộng logic lazy-pruning — thứ 1 tiến trình chạy dài thật sự cần. InMemoryDedupCache giữ đúng 2 thứ cần: ttl (thời gian 1 key còn được coi là “đã claim”) và claimed: Mutex<HashMap<String, Instant>> — map từ key (chuỗi "channel:ts:lang" bài 04 đã dựng) sang thời điểm claim key đó. Mutex bọc quanh HashMap vì try_claim/release có thể bị gọi đồng thời từ nhiều task nền (mỗi request Slack chạy trong 1 tokio::spawn riêng, theo bài 05) — không có Mutex, 2 task cùng lúc đọc-rồi-ghi HashMap là data race.

Logic try_claim gói trong 1 lần lock: dọn dẹp entry hết hạn trước (claimed.retain(...)), sau đó mới check-và-insert key đang xét. Điểm đáng chú ý là “dọn dẹp” ở đây không phải 1 task nền chạy định kỳ (kiểu spawn 1 task tokio::time::interval quét toàn bộ map mỗi vài phút) — mà là lazy prune: mỗi lần try_claim được gọi, nó tiện tay quét sạch mọi entry đã hết hạn trước khi làm việc chính. Đơn giản hơn hẳn so với chạy background sweep — không cần task riêng, không cần lo task đó panic hay bị quên spawn — và đủ dùng ở traffic 1 bot instance thấy: try_claim được gọi đủ thường xuyên (mỗi lần có reaction mới) để map không phình to vô hạn giữa 2 lần dọn.

retain là hàm có sẵn của HashMap, giữ lại entry nào closure trả true: ở đây giữ lại (chưa xoá) những key có now.duration_since(*claimed_at) < self.ttl — nghĩa là còn trong hạn. Sau retain, claimed.contains_key(key) chỉ còn true nếu key đó vẫn còn hạn; nếu có (đã bị claim và chưa hết hạn) trả false (từ chối claim thêm lần nữa); nếu không, insert key mới với now rồi trả true (cho phép claim). release đơn giản hơn — xoá thẳng key ra khỏi map, dùng khi 1 attempt claim rồi nhưng xử lý sau đó lỗi tạm thời (bài 04 đã nói: không nên khoá vĩnh viễn 1 message chỉ vì lỗi thoáng qua).

Giới hạn được nói thẳng ngay trong docstring, không giấu: cache này process-local — sống trong bộ nhớ của đúng 1 tiến trình đang chạy. Chạy 2 instance của bot cùng lúc (ví dụ để load-balance, hoặc trong lúc rolling deploy có cả bản cũ và bản mới chạy song song), mỗi instance có 1 HashMap riêng, không đồng bộ với nhau — 2 người react cùng lúc, request rơi vào 2 instance khác nhau, cả 2 đều try_claim thành công trên map riêng của mình, kết quả là 2 reply trùng nhau vẫn lọt qua được lưới dedup. Hướng mở rộng đã tính sẵn trong thiết kế: DedupCachePort là trait, InMemoryDedupCache chỉ là 1 trong các cách implement nó — thay bằng adapter dùng Redis (SET key value NX EX ttl là đúng 1 lệnh atomic tương đương try_claim, DEL key tương đương release) implement cùng DedupCachePort, và không cần sửa gì khác trong codebase: HandleReactionUseCase chỉ biết Arc<dyn DedupCachePort>, không biết bên dưới là HashMap hay Redis.

Tổng kết & bài tiếp theo

Bài này khép lại 3 mảnh ghép còn thiếu của slack_gateway: dto.rs map wire format Slack sang type Rust bằng #[serde(tag = "type")] (đa hình theo 1 field JSON) và #[serde(other)] (bắt hết mọi loại event chưa xử lý mà không cần liệt kê hay lỗi parse); SlackWebApiClient implement SlackMessagingPort thật, gọi conversations.history để fetch đúng 1 message và chat.postMessage kèm thread_ts để reply đúng vị trí trong thread, cả 2 đều tự kiểm tra field ok/error theo đúng quy ước riêng của Slack Web API; và InMemoryDedupCache implement DedupCachePort bằng Mutex<HashMap<String, Instant>> với chiến lược lazy-prune, kèm giới hạn process-local đã biết trước và hướng thay thế bằng Redis khi cần scale ngang.

Tới đây, mọi thành phần của slack_gateway đã có implementation thật: domain, application (bài 04), HTTP + bảo mật (bài 05), và 2 adapter gọi ra ngoài (bài này). Còn thiếu đúng 1 việc: ráp tất cả lại thành 1 chương trình chạy được — tạo SlackWebApiClient, InMemoryDedupCache, đọc config (bot token, signing secret) từ đâu, rồi lắp vào AppState bài 05 đã định nghĩa. Bài 07 làm đúng việc đó — composition root, chạy test toàn workspace, và đóng gói Docker.
