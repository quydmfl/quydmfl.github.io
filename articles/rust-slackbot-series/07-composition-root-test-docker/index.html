Tới đây, mọi module — kernel, translation, slack_gateway — đều đã có domain, application, infrastructure đầy đủ. Nhưng chưa có gì ráp chúng lại thành 1 chương trình chạy được: chưa ai gọi LibreTranslateAdapter::new(...), chưa ai tạo HandleReactionUseCase, chưa có server nào lắng nghe port nào. Bài này — bài cuối của series — làm đúng việc đó: crates/app/src/main.rs, chạy test + clippy toàn workspace để xác nhận kiến trúc port/adapter trả về lợi ích gì thật, rồi đóng gói bằng Docker.

main.rs: composition root

crates/app/src/main.rs:

use std::sync::Arc;

use kernel::AppConfig;
use slack_gateway::application::HandleReactionUseCase;
use slack_gateway::infrastructure::http::{router, AppState};
use slack_gateway::infrastructure::{InMemoryDedupCache, SlackWebApiClient};
use translation::application::TranslateTextUseCase;
use translation::infrastructure::LibreTranslateAdapter;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    dotenvy::dotenv().ok();
    tracing_subscriber::fmt()
        .with_env_filter(tracing_subscriber::EnvFilter::from_default_env())
        .init();

    let config = AppConfig::from_env()?;

    // --- Composition root -------------------------------------------------
    // The only place that knows concrete adapters (LibreTranslate, the Slack
    // Web API client, axum). Everything below `application` in each module
    // only ever sees traits.

    let translation_provider = Arc::new(LibreTranslateAdapter::new(
        config.libretranslate_url.clone(),
        config.libretranslate_api_key.clone(),
    ));
    let translate_text = Arc::new(TranslateTextUseCase::new(translation_provider));

    let slack_client = Arc::new(SlackWebApiClient::new(config.slack_bot_token.clone()));
    let dedup_cache = Arc::new(InMemoryDedupCache::default());
    let handle_reaction = Arc::new(HandleReactionUseCase::new(
        slack_client,
        translate_text,
        dedup_cache,
    ));

    let state = AppState {
        handle_reaction,
        signing_secret: Arc::new(config.slack_signing_secret.clone()),
    };
    // ------------------------------------------------------------------------

    let app = router(state);
    let listener = tokio::net::TcpListener::bind(("0.0.0.0", config.port)).await?;

    tracing::info!(port = config.port, "slackbot listening");
    axum::serve(listener, app).await?;

    Ok(())
}

Đây là file duy nhất trong toàn bộ codebase biết cả 2 thứ cùng lúc: adapter cụ thể (LibreTranslateAdapter, SlackWebApiClient, InMemoryDedupCache) VÀ framework HTTP cụ thể (axum, qua router/AppState). Comment ngay trong code nói thẳng điều đó — không phải suy diễn của bài viết này, mà là chủ ý của người viết code: “Everything below application in each module only ever sees traits.” TranslateTextUseCase chỉ biết TranslationProviderPort, không biết LibreTranslateAdapter. HandleReactionUseCase chỉ biết SlackMessagingPort, DedupCachePort, và trait TranslateText của module translation — không biết SlackWebApiClient, InMemoryDedupCache, hay LibreTranslateAdapter cụ thể là gì. Toàn bộ dây nối những khoảng trống đó — “trait này thì dùng struct nào” — chỉ tồn tại đúng ở main().

Chuỗi khởi tạo đọc xuôi theo đúng thứ tự phụ thuộc: translation_provider (adapter) bọc vào translate_text (use case của translation); slack_client và dedup_cache (2 adapter của slack_gateway) cộng với translate_text vừa tạo, cả 3 bọc vào handle_reaction (use case của slack_gateway); cuối cùng handle_reaction cộng signing_secret gộp thành AppState — đúng struct router() bài 05 cần để dựng axum Router. Mỗi bước bọc dùng Arc::new(...), và mỗi constructor (TranslateTextUseCase::new, HandleReactionUseCase::new) nhận tham số kiểu Arc<dyn Trait> chứ không phải kiểu cụ thể — nên dù truyền vào Arc<LibreTranslateAdapter>, bên trong use case chỉ giữ lại Arc<dyn TranslationProviderPort>.

Đây chính là dependency injection theo kiểu Rust: không cần framework DI (không container, không annotation, không reflection tra cứu implementation lúc runtime như Spring hay .NET DI hay dùng). Chỉ cần Arc<dyn Trait> truyền tay qua constructor, và người gọi constructor (ở đây là main()) tự quyết định implementation cụ thể nào được truyền vào. Toàn bộ việc “wiring” là code Rust bình thường, compiler kiểm tra kiểu ngay lúc biên dịch — truyền nhầm 1 adapter không implement đúng trait, code không compile, không phải lỗi runtime phát hiện muộn.

Đây không phải trùng hợp có được nhờ viết test cẩn thận — nó là hệ quả trực tiếp của dependency inversion đã học xuyên suốt series: TranslateTextUseCase chỉ phụ thuộc TranslationProviderPort (bài 03); HandleReactionUseCase chỉ phụ thuộc SlackMessagingPort, DedupCachePort, TranslateText (bài 04) — không phụ thuộc thẳng vào LibreTranslateAdapter hay SlackWebApiClient. Vì use case không biết concrete type nào đứng sau trait, test có quyền thay concrete type đó bằng bất cứ gì implement đúng trait, kể cả 1 stub không chạm mạng. Nếu HandleReactionUseCase gọi thẳng reqwest::Client thay vì qua Arc<dyn SlackMessagingPort>, 12 test này không thể chạy trong 0.03s mà không cần Slack thật — sẽ cần mock HTTP server, hoặc bỏ qua, hoặc chấp nhận test chậm và giòn (flaky) vì phụ thuộc mạng.

Docker multi-stage build

Dockerfile:

# syntax=docker/dockerfile:1

# ---- builder --------------------------------------------------------------
FROM rust:1.91-slim-bookworm AS builder
WORKDIR /build

# reqwest's default TLS backend links against OpenSSL on Linux.
RUN apt-get update && apt-get install -y --no-install-recommends \
    pkg-config libssl-dev \
    && rm -rf /var/lib/apt/lists/*

# Workspace-wide manifest + lockfile first so dependency compilation is
# cached across rebuilds that only touch application code.
COPY Cargo.toml Cargo.lock ./
COPY crates crates

RUN cargo build --release -p app --locked

# ---- runtime ----------------------------------------------------------------
FROM debian:bookworm-slim AS runtime
WORKDIR /app

RUN apt-get update && apt-get install -y --no-install-recommends \
    ca-certificates libssl3 \
    && rm -rf /var/lib/apt/lists/* \
    && useradd --system --no-create-home --uid 10001 appuser

COPY --from=builder /build/target/release/slackbot /usr/local/bin/slackbot

USER appuser
EXPOSE 3000
ENTRYPOINT ["/usr/local/bin/slackbot"]

2 stage, 2 mục đích hoàn toàn khác nhau. Stage builder dùng image rust:1.91-slim-bookworm — có sẵn toolchain (rustc, cargo), cộng pkg-config/libssl-dev (build dependency của reqwest, TLS backend mặc định trên Linux link OpenSSL). Stage này copy Cargo.toml/Cargo.lock trước, crates/ sau — thứ tự cố ý để tận dụng layer cache của Docker: sửa code trong crates/app/src/main.rs không làm thay đổi 2 file manifest, nên nếu image đã build 1 lần, layer cài pkg-config/libssl-dev và layer copy manifest được giữ nguyên từ cache, chỉ layer cargo build chạy lại. Sau khi cargo build --release -p app --locked chạy xong, stage này để lại đúng 1 thứ có giá trị: file binary target/release/slackbot.

Stage runtime bắt đầu lại từ đầu, từ debian:bookworm-slim — không có Rust toolchain, không có source code, không có Cargo.toml. Dòng duy nhất mang nội dung từ stage kia sang là COPY --from=builder /build/target/release/slackbot /usr/local/bin/slackbot — đúng 1 file binary, không gì khác. Phần còn lại của stage này chỉ cài ca-certificates (để reqwest verify TLS cert khi gọi Slack API/LibreTranslate qua HTTPS) và libssl3 (thư viện OpenSSL runtime binary cần, không cần header/dev package như builder), tạo 1 user hệ thống không có quyền root (appuser, uid cố định 10001) rồi chuyển sang chạy bằng user đó (USER appuser) thay vì mặc định root.

Kết quả: image cuối cùng — cái thật sự được docker push/deploy — không chứa rustc, không chứa cargo, không chứa 1 dòng source .rs nào, không chứa dependency crate nào ở dạng source. Chỉ có 1 binary đã compile sẵn, chạy bằng user không phải root. 2 lợi ích trực tiếp: kích thước image nhỏ hơn hẳn so với nếu dùng nguyên rust:1.91-slim-bookworm làm base để chạy (image đó cõng theo cả toolchain build chỉ dùng đúng 1 lần lúc build, không cần lúc chạy); và bề mặt tấn công (attack surface) nhỏ hơn — kẻ tấn công chiếm được container không tìm thấy compiler để tự build exploit ngay trong container, không có source code để đọc, không chạy bằng root nên quyền hạn bị giới hạn ngay cả khi khai thác được lỗ hổng nào đó trong chính binary.

Build được không có nghĩa chạy được — verify bằng cách chạy thật, với biến môi trường giả (không có Slack token thật, không LibreTranslate thật chạy — chỉ cần server khởi động và /healthz trả lời được, vì handler đó, theo bài 05, không chạm tới AppState hay bất kỳ adapter nào):

200 OK — container khởi động thành công, AppConfig::from_env() đọc đủ biến môi trường bắt buộc (dù giá trị giả) nên không panic ngay lúc main() chạy, axum server bind cổng 3000 bên trong container (map ra 3099 ở host), và route /healthz trả lời được. Đây là bằng chứng thực nghiệm image chạy được ở dạng container thật, không chỉ build xong rồi để đó — đúng thứ 1 image Docker cần chứng minh trước khi đưa vào bất kỳ pipeline CI/CD hay docker-compose up nào.

docker-compose.yml: chạy bot + LibreTranslate cùng lúc

services:
  libretranslate:
    image: libretranslate/libretranslate:v1.6.2
    container_name: libretranslate
    restart: unless-stopped
    expose:
      - "5000"
    environment:
      LT_LOAD_ONLY: "en,vi"
      LT_DISABLE_WEB_UI: "true"
      LT_THREADS: "4"

    volumes:
      - libretranslate_models:/home/libretranslate/.local:rw

    healthcheck:
      test: ["CMD-SHELL", "./venv/bin/python scripts/healthcheck.py"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 20s

  slackbot:
    build: .
    ports:
      - "3000:3000"
    env_file:
      - .env
    environment:
      LIBRETRANSLATE_URL: http://libretranslate:5000

    depends_on:
      libretranslate:
        condition: service_healthy

volumes:
  libretranslate_models:

docker run phía trên chạy đúng 1 container, với LIBRETRANSLATE_URL giả trỏ vào localhost không tồn tại — đủ để test /healthz, nhưng không đủ để bot thật sự dịch được gì. docker-compose.yml giải quyết bài toán chạy 2 service cùng lúc: libretranslate (image công khai, tự giới hạn LT_LOAD_ONLY: "en,vi" — chỉ load 2 ngôn ngữ bot này cần, tiết kiệm RAM và thời gian khởi động so với load toàn bộ danh sách ngôn ngữ LibreTranslate hỗ trợ) và slackbot (build từ chính Dockerfile vừa mổ xẻ ở trên, qua build: .).

Chi tiết quan trọng nhất nằm ở depends_on. Không viết depends_on: [libretranslate] (dạng list ngắn gọn) mà viết dạng đầy đủ với condition: service_healthy. Khác biệt giữa 2 cách này là toàn bộ vấn đề: depends_on dạng list chỉ đảm bảo Docker Compose khởi động container libretranslate TRƯỚC KHI khởi động slackbot — container libretranslate ở trạng thái “đang chạy” (running), không đồng nghĩa “đã sẵn sàng nhận request” (LibreTranslate cần thời gian nạp model dịch vào bộ nhớ sau khi process khởi động, có thể mất vài giây tới vài chục giây tuỳ phần cứng). Nếu slackbot khởi động ngay khi libretranslate mới chuyển sang running, request dịch đầu tiên gửi tới http://libretranslate:5000 rất có thể bị từ chối kết nối hoặc trả lỗi — 1 race condition kinh điển lúc mới docker compose up, chỉ xảy ra thoáng qua lúc khởi động nên dễ bị bỏ qua khi test thủ công (thường test sau khi cả 2 container đã chạy ổn định 1 lúc) rồi bất ngờ tái hiện khi deploy lại từ đầu.

condition: service_healthy sửa đúng chỗ đó: Compose không khởi động slackbot cho tới khi container libretranslate báo cáo healthy — tức là đã pass healthcheck định nghĩa ngay phía trên (./venv/bin/python scripts/healthcheck.py, chạy mỗi 10s, cho phép start_period: 20s ân hạn trước khi tính retry thất bại vào kết quả, tối đa 10 lần retry). Chỉ khi healthcheck đó trả về thành công lần đầu, Compose mới coi libretranslate là healthy và cho phép slackbot khởi động. Không cần code Rust nào tự retry kết nối LibreTranslate lúc khởi động, không cần sleep cứng đoán mò vài giây — thứ tự khởi động đúng được đảm bảo ở tầng orchestration, tách biệt hoàn toàn khỏi logic ứng dụng.

Tổng kết series “Xây Slack Bot bằng Rust”

Bảy bài, đi qua trọn 1 dự án Rust thật từ kiến trúc tổng quan tới khi chạy được bằng Docker.

Bài 01 đặt nền: Cargo workspace 4 crate (kernel, translation, slack_gateway, app) với ranh giới do compiler ép buộc qua Cargo.toml, không phải quy ước bằng lời — 1 modular monolith, build/deploy như 1 khối nhưng giữ kỷ luật ranh giới module như service tách biệt, mỗi crate nghiệp vụ tổ chức theo Clean Architecture rút gọn domain → application → infrastructure.

Bài 02 mổ xẻ kernel — shared kernel cố tình giữ cực nhỏ, chỉ 3 thứ: AppConfig load từ env bằng thiserror, LanguageCode — value object tự validate ngay ở constructor (không có cách nào tạo ra 1 giá trị sai qua nó), và BoxError dùng đúng ở rìa hệ thống. Bài học cốt lõi: 1 kiểu chỉ xứng vào kernel khi từ 2 bounded context độc lập trở lên cùng cần, và không thiên về nghiệp vụ riêng của bên nào.

Bài 03 xây trọn module translation đầu tiên: domain thuần (Translation, TranslationError), 2 port ngược hướng (TranslationProviderPort outbound, TranslateText inbound) nối nhau bằng TranslateTextUseCase, và LibreTranslateAdapter — nơi duy nhất biết HTTP shape của LibreTranslate. Dependency inversion bằng trait trong Rust: đổi provider dịch không cần sửa use case, chỉ cần viết adapter mới.

Bài 04 chuyển sang slack_gateway — domain (ReactionAddedEvent, business rule emoji→ngôn ngữ) và application (HandleReactionUseCase orchestrate dedup + translate + reply qua 2 outbound port SlackMessagingPort/DedupCachePort cộng TranslateText của translation). Lần đầu tiên series verify bằng test dùng stub — 6 test pass không cần Slack hay LibreTranslate thật, minh chứng sớm cho lợi ích của port/adapter.

Bài 05 đóng phần bảo mật + HTTP: verify chữ ký Slack bằng HMAC-SHA256, so sánh constant-time để tránh timing attack, chặn timestamp lệch quá 5 phút để tránh replay; router/handlers/state bằng axum; và giải quyết ràng buộc “Slack cần ACK trong 3 giây” bằng tokio::spawn fire-and-forget, tách xử lý chậm ra khỏi đường trả response.

Bài 06 hoàn thiện 2 adapter còn thiếu: dto.rs map wire format Slack bằng #[serde(tag = "type")] và #[serde(other)]; SlackWebApiClient gọi thật conversations.history/chat.postMessage; InMemoryDedupCache — TTL cache tự viết bằng Mutex<HashMap>, lazy-prune, kèm giới hạn process-local đã biết trước và hướng thay Redis khi cần scale ngang.

Bài này khép lại bằng đúng việc còn thiếu: main.rs ráp tất cả những mảnh đó lại bằng Arc<dyn Trait> truyền tay qua constructor — dependency injection không cần framework, chỉ cần compiler kiểm tra kiểu; cargo test --workspace xác nhận 12 test pass mà không chạm mạng thật, không phải phép màu mà là hệ quả trực tiếp của kiến trúc port/adapter xuyên suốt 6 bài trước; và Docker multi-stage build đóng gói toàn bộ thành 1 image 159MB không chứa toolchain hay source, chạy thử thật bằng container trả /healthz 200 OK.

Từ 1 thư mục trống tới 1 image Docker chạy được, mọi quyết định kiến trúc trong series này đều quay về đúng 1 câu hỏi: thay đổi 1 thứ (provider dịch, cách lưu dedup cache, framework HTTP) có buộc phải sửa code ở chỗ khác không? Câu trả lời nhất quán xuyên suốt 7 bài là không — miễn ranh giới module, trait, và composition root được giữ đúng chỗ.
