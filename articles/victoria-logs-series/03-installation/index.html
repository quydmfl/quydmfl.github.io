Ở bài trước, chúng ta đã chốt kiến trúc: Vector thu log → đẩy sang VictoriaLogs để lưu trữ → Grafana để truy vấn/hiển thị. Bài này dựng phần khung xương của stack đó: chạy được VictoriaLogs và Vector bằng Docker Compose, kiểm chứng pipeline hoạt động end-to-end. Grafana sẽ được thêm vào ở bài 06 — cố tình tách ra để không phải học quá nhiều thứ cùng lúc.

Vì sao không có file config cho VictoriaLogs?

Nếu bạn để ý thư mục config/ đi kèm bài này, sẽ chỉ thấy vector.yaml chứ không có victorialogs.yaml. Đây không phải thiếu sót — VictoriaLogs (cũng như VictoriaMetrics) không dùng file cấu hình YAML. Toàn bộ hành vi của nó được điều khiển bằng command-line flags khi khởi động binary. Đây là triết lý thiết kế xuyên suốt của hệ sinh thái Victoria*: cấu hình tường minh, dễ diff trong Git, dễ override qua biến môi trường khi chạy trong container — không cần một tầng parser YAML riêng.

Vì vậy, “cấu hình” của VictoriaLogs trong bài này nằm thẳng trong phần command: của service, trong docker-compose.yml.

Docker Compose stack

Toàn bộ file docker-compose.yml dùng cho bài này:

services:
  victorialogs:
    image: docker.io/victoriametrics/victoria-logs:v1.24.0-victorialogs
    container_name: victorialogs
    command:
      - "-storageDataPath=/vlogs-data"
      - "-retentionPeriod=30d"
      - "-httpListenAddr=:9428"
    ports:
      - "9428:9428"
    volumes:
      - vlogs-data:/vlogs-data
    restart: unless-stopped

  vector:
    image: docker.io/timberio/vector:latest-alpine
    container_name: vector
    volumes:
      - ./config/vector.yaml:/etc/vector/vector.yaml:ro
      - /var/run/docker.sock:/var/run/docker.sock:ro
    command: ["--config", "/etc/vector/vector.yaml"]
    depends_on:
      - victorialogs
    restart: unless-stopped

volumes:
  vlogs-data:

Vài điểm đáng chú ý:

  • -storageDataPath=/vlogs-data: thư mục VictoriaLogs lưu dữ liệu log đã nén. Mount qua named volume vlogs-data để dữ liệu không mất khi container bị xoá/tái tạo.
  • -retentionPeriod=30d: giữ log trong 30 ngày rồi tự động xoá partition cũ. Giá trị hợp lệ từ 1d đến 100y; mặc định nếu không set là 1w. Đây là con số quan trọng nhất cần quyết định trước khi lên production — sẽ bàn kỹ hơn ở bài 07.
  • timberio/vector:latest-alpine: dùng latest cho môi trường học/thử nghiệm. Trong production, luôn pin một version cụ thể (ví dụ 0.46.0-alpine) để tránh một bản Vector mới tự động kéo về phá vỡ pipeline đang chạy ổn định.
  • Mount /var/run/docker.sock: Vector cần đọc socket này để lấy log của các container khác trên cùng host qua nguồn docker_logs. Mount :ro (read-only) vì Vector chỉ cần quan sát, không cần quyền điều khiển Docker.
  • Chưa mở port nào cho Vector — nó không phục vụ HTTP request, chỉ chạy nền để thu và đẩy log.

Cấu hình Vector

File config/vector.yaml:

sources:
  docker_logs:
    type: docker_logs

sinks:
  victorialogs:
    type: elasticsearch
    inputs:
      - docker_logs
    endpoints:
      - "http://victorialogs:9428/insert/elasticsearch/"
    mode: bulk
    api_version: v8
    compression: gzip
    healthcheck:
      enabled: false
    query:
      _msg_field: message
      _time_field: timestamp
      _stream_fields: container_name,host

Hai phần cần hiểu rõ:

Nguồn (sources.docker_logs) — Vector có sẵn source type docker_logs, tự động lấy log của mọi container đang chạy trên host thông qua Docker socket, kèm metadata hữu ích: container_name, container_id, image, host, stream (stdout/stderr)… Vì không khai báo include_containers, Vector sẽ thu log của mọi container — kể cả vector và victorialogs chính nó. Đúng như đã bàn ở bài trước: dùng log của chính hạ tầng làm dữ liệu thật để học, thay vì phải dựng thêm một ứng dụng demo.

Đích (sinks.victorialogs) — Đây là phần dễ gây nhầm lẫn nhất khi mới tiếp cận VictoriaLogs: Vector chưa có sink riêng cho VictoriaLogs, nên ta dùng sink elasticsearch có sẵn, trỏ vào endpoint tương thích Elasticsearch bulk API mà VictoriaLogs cung cấp tại /insert/elasticsearch/. Ba tham số trong query là bắt buộc để VictoriaLogs biết cách diễn giải một document Elasticsearch bulk thành log entry của nó:

Tham sốÝ nghĩa
_msg_fieldField nào chứa nội dung log chính, sẽ được lưu vào field đặc biệt _msg
_time_fieldField nào là timestamp, lưu vào field đặc biệt _time
_stream_fieldsTập field định danh một “stream” log — tương tự khái niệm label set trong Loki

Ở bài 04 chúng ta sẽ mổ xẻ sâu hơn khái niệm stream này, vì nó ảnh hưởng trực tiếp đến hiệu năng và cách query.

Chạy thử

docker compose up -d
docker compose ps

Kiểm tra VictoriaLogs đã sẵn sàng nhận request:

curl http://localhost:9428/health
# expected: OK

Đợi khoảng 10-20 giây để Vector kịp đẩy batch log đầu tiên, sau đó thử query trực tiếp bằng LogsQL qua HTTP API (sẽ học cú pháp đầy đủ ở bài 05):

curl http://localhost:9428/select/logsql/query -d 'query=*' | head -n 5

Nếu thấy các dòng JSON trả về chứa _msg, _time, container_name — pipeline đã chạy đúng: log từ container Docker → Vector → VictoriaLogs.

Dừng và dọn dẹp

docker compose down        # dừng, giữ lại volume (giữ dữ liệu log)
docker compose down -v     # dừng và xoá luôn volume (xoá sạch dữ liệu)

Tiếp theo

Pipeline đã chạy, nhưng log đang ở dạng thô — nguyên văn dòng log, chưa được parse hay làm giàu thêm thông tin. Bài 04 sẽ đi sâu vào việc cấu hình Vector để parse, transform và định tuyến log trước khi ghi vào VictoriaLogs.
